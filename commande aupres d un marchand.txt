# Telluris — Implémentation d'un système de commandes et de fabrication dynamique

## Objectif

Ajouter au système d'artisanat de Telluris un mécanisme de **commande auprès des magasins et artisans** permettant de créer des objets qui n'existent pas encore dans la base de données.

Le système actuel repose sur une règle fondamentale :

> Une recette et un item n'existent dans le jeu que s'ils sont présents en base de données.

Cette règle doit rester vraie pour les objets standards.

Le nouveau système introduit une exception contrôlée :

> Un magasin capable de fabriquer sur commande peut produire un objet à partir d'un **item de base existant en base** et de **matières premières apportées ou payées par le client**, en appliquant aux caractéristiques de l'objet de base des **modificateurs et/ou effets déterminés par les matières premières utilisées**.

Une fois la commande effectivement réalisée, le nouvel objet et sa recette doivent être **persistés en base de données** afin qu'ils deviennent de véritables éléments du jeu.

---

# 1. Principes fondamentaux

Le système doit distinguer trois catégories.

### 1.1 Item standard

Item déjà présent en base.

Exemple :

```text
Épée longue
```

Cet item possède sa définition, ses caractéristiques et éventuellement ses recettes normales.

---

### 1.2 Recette standard

Recette déjà présente en base.

Elle permet de fabriquer un item connu à partir de composants connus.

Exemple :

```text
Minerai de fer
+
Bois
+
Cuir
=
Épée longue
```

Aucune modification du fonctionnement existant ne doit être imposée aux recettes standards.

---

### 1.3 Item fabriqué sur commande

Objet qui n'existe pas encore en base au moment où le joueur passe commande.

Il est généré à partir :

```text
ITEM DE BASE
+
MATIÈRES PREMIÈRES
+
MODIFICATEURS / EFFETS
=
NOUVEL ITEM
```

Exemple :

```text
Épée longue
+
Acier
+
Cristal de mana de feu
=
Épée longue en acier embrasé
```

L'objet généré devient ensuite un véritable item persistant.

---

# 2. Concept central : le prototype d'objet

Une commande ne doit jamais générer un objet entièrement arbitraire.

Elle doit obligatoirement partir d'un **item de base existant en base**.

Créer une nouvelle variante consiste donc à prendre cet item comme prototype.

Exemple :

```text
Item de base :
Épée longue

Caractéristiques :
dégâts physiques : 10
poids : 3
portée : 1
type : arme
```

Puis appliquer les propriétés des matériaux.

Exemple :

```text
Acier :
+2 dégâts
+1 poids

Cristal de feu :
effet : dégâts de feu
```

Le résultat devient :

```text
Épée longue en acier embrasé

dégâts physiques : 12
poids : 4
portée : 1
type : arme
effet : dégâts de feu
```

Le système doit conserver le lien avec l'item d'origine.

---

# 3. Matières premières

Les matières premières doivent être des éléments existants dans le système d'items.

Chaque matière première peut posséder des propriétés utilisables lors d'une fabrication.

Prévoir un mécanisme permettant d'associer à une matière :

* des modifications de caractéristiques ;
* des effets ;
* des propriétés spéciales ;
* éventuellement des contraintes de compatibilité ;
* éventuellement une quantité nécessaire ;
* éventuellement un niveau de qualité.

Exemple conceptuel :

```json
{
  "material": "acier",
  "modifiers": {
    "damage": 2,
    "weight": 1
  }
}
```

ou :

```json
{
  "material": "cristal_feu",
  "effects": [
    "fire_damage"
  ]
}
```

Le système ne doit pas coder en dur chaque matériau directement dans le système de commande.

Les propriétés doivent être configurables dans les données.

---

# 4. Compatibilité des matières

Toutes les matières ne doivent pas pouvoir être appliquées à tous les items.

Prévoir un mécanisme de compatibilité.

Exemples :

```text
Acier → arme métallique : compatible
Acier → potion : incompatible

Cristal de feu → arme : compatible
Cristal de feu → nourriture : incompatible

Herbe médicinale → potion : compatible
Herbe médicinale → épée : incompatible
```

La compatibilité peut être déterminée par :

* catégorie de l'item ;
* type de fabrication ;
* emplacement de matériau ;
* tags ;
* règles spécifiques de la matière.

Privilégier un système basé sur des **tags / catégories configurables** plutôt qu'une longue liste de conditions codées en dur.

---

# 5. Slots de matériaux

Une fabrication sur commande devrait idéalement utiliser des **emplacements de matériaux**.

Exemple pour une épée :

```text
Lame
Poignée
Ornement / matériau magique
```

Exemple :

```text
Épée longue
    ├── lame : acier
    ├── poignée : cuir
    └── cristal : cristal de feu
```

Chaque slot peut accepter certaines catégories de matériaux.

Cela permet d'éviter qu'un matériau fournisse arbitrairement n'importe quel effet.

---

# 6. Génération des caractéristiques

Lorsqu'une commande est validée, le système doit calculer les caractéristiques finales.

Conceptuellement :

```text
caractéristiques finales
=
caractéristiques de l'item de base
+
modificateurs des matériaux
+
modificateurs éventuels de qualité
```

Les effets doivent être ajoutés séparément :

```text
effets finaux
=
effets de base
+
effets des matériaux
```

Le calcul doit être déterministe.

Pour une même combinaison :

```text
item de base
+
matériaux
+
quantités
+
qualité
```

le système doit produire exactement le même résultat.

---

# 7. Gestion des conflits

Prévoir un mécanisme de résolution des conflits.

Exemples :

Deux matériaux peuvent donner :

```text
+10% résistance au feu
```

Le système doit savoir s'il faut :

```text
additionner
```

ou :

```text
prendre la meilleure valeur
```

ou :

```text
refuser la combinaison
```

ou :

```text
transformer les deux effets en un effet supérieur
```

Ces règles doivent être centralisées dans le moteur de fabrication.

Ne pas disperser ces règles dans les magasins ou les interfaces.

---

# 8. Qualité de la matière

Si le système actuel possède déjà une notion de qualité, la fabrication sur commande doit pouvoir l'utiliser.

Sinon, ne pas créer inutilement un système complexe de qualité.

Le principe souhaité est :

```text
matière basique
→ résultat basique

matière supérieure
→ résultat supérieur
```

La qualité peut éventuellement modifier :

* les caractéristiques ;
* la durabilité ;
* les effets ;
* le coût ;
* la valeur marchande.

Mais ces mécanismes doivent rester compatibles avec le système d'items existant.

---

# 9. Coût de la commande

Le client doit fournir les matériaux nécessaires.

Deux possibilités doivent être supportées.

### Matériaux apportés par le client

Exemple :

```text
Client fournit :
- 2 lingots d'acier
- 1 cristal de feu
```

Le magasin ne facture pas ces matériaux.

Il facture uniquement :

```text
main-d'œuvre
+
frais éventuels
```

---

### Matériaux fournis par le magasin

Si le magasin possède le matériau requis en stock, le client peut demander au magasin de le fournir.

Dans ce cas :

```text
prix final
=
prix des matériaux consommés
+
main-d'œuvre
+
éventuels frais
```

Le stock du magasin doit être effectivement diminué.

---

# 10. Réservation des ressources

Une commande ne doit pas consommer définitivement les matériaux au moment où elle est simplement créée.

Prévoir plusieurs états.

Exemple :

```text
DRAFT
→ QUOTED
→ ACCEPTED
→ MATERIALS_RESERVED
→ IN_PROGRESS
→ COMPLETED
```

Avec éventuellement :

```text
CANCELLED
```

et :

```text
FAILED
```

Les matériaux doivent être réservés ou consommés selon les règles du système existant.

Une commande annulée doit pouvoir libérer les ressources réservées.

---

# 11. Validation de la commande

Avant de créer l'objet, effectuer une validation complète.

Vérifier :

* que l'item de base existe ;
* que le magasin sait fabriquer cet item ;
* que les matériaux sont compatibles ;
* que les quantités sont suffisantes ;
* que les matériaux existent ;
* que le client peut payer ;
* que le magasin peut fournir les matériaux demandés ;
* que les effets résultants sont valides ;
* que les caractéristiques résultantes respectent les contraintes du jeu.

La validation doit être effectuée côté serveur.

Ne jamais faire confiance aux données envoyées par le client.

---

# 12. Génération du nouvel item

Une fois la commande réalisée, créer un nouvel item dans la base.

Le nouvel item doit être une **variante persistante** de l'item de base.

Prévoir au minimum :

```text
base_item_id
```

afin de conserver l'origine de l'objet.

Exemple :

```text
base_item_id = item:epee_longue
```

Le nouvel item possède ensuite sa propre identité :

```text
item:epee_longue_acier_feu_xxxxx
```

Le système doit éviter les collisions d'identifiants.

Utiliser le mécanisme d'identification déjà présent dans le projet si celui-ci existe.

---

# 13. Ne pas dupliquer inutilement les données

Il faut distinguer :

### Définition du prototype

```text
Épée longue
```

et :

### Définition de la variante

```text
Épée longue en acier embrasé
```

La variante doit conserver les données nécessaires à son fonctionnement mais ne doit pas entraîner une duplication inutile de toutes les données du prototype.

Privilégier une structure permettant de savoir :

```text
variante
→ prototype
→ matériaux utilisés
→ modifications appliquées
→ recette générée
```

---

# 14. Génération de la recette

La création de l'item doit automatiquement créer une recette correspondante.

Exemple :

```text
Recette :
Fabriquer Épée longue en acier embrasé

Prototype :
Épée longue

Composants :
2 × Acier
1 × Cristal de feu

Résultat :
1 × Épée longue en acier embrasé
```

La recette doit être persistée en base en même temps que l'item.

Il ne doit jamais être possible d'avoir :

```text
item généré sans recette
```

ou :

```text
recette générée sans item correspondant
```

L'opération doit donc être transactionnelle.

---

# 15. Recette générée vs recette standard

Ajouter une distinction explicite entre :

```text
STANDARD
```

et :

```text
CUSTOM / GENERATED
```

Une recette générée doit conserver les informations nécessaires pour reconstruire son origine.

Exemple :

```json
{
  "type": "generated",
  "base_item_id": "item:epee_longue",
  "materials": [
    {
      "item_id": "item:acier",
      "quantity": 2,
      "slot": "blade"
    },
    {
      "item_id": "item:cristal_feu",
      "quantity": 1,
      "slot": "magic"
    }
  ]
}
```

---

# 16. Déduplication des variantes

Il faut éviter de créer plusieurs fois exactement le même item.

Exemple :

Un joueur commande :

```text
Épée longue
+
2 acier
+
1 cristal feu
```

Puis un autre joueur passe exactement la même commande.

Le système doit pouvoir reconnaître que la variante existe déjà.

Créer alors :

```text
la même définition d'item
```

plutôt qu'une nouvelle définition.

La clé de déduplication doit être déterministe.

Elle peut être construite à partir de :

```text
base_item_id
+
liste normalisée des matériaux
+
quantités
+
slots
+
qualités
+
paramètres de fabrication
```

Ne pas utiliser le nom de l'objet comme clé d'unicité.

---

# 17. Exemple de clé de variante

Conceptuellement :

```text
variant_key =
hash(
    base_item_id
    + normalized_materials
    + quantities
    + slots
    + qualities
    + recipe_parameters
)
```

Exemple :

```text
epee_longue
acier:2:lame
cristal_feu:1:magie
```

donne une clé déterministe.

Cette clé doit être indexée en base.

---

# 18. Nom de l'objet

Le nom affiché peut être généré à partir :

```text
nom du prototype
+
propriétés principales
```

Exemple :

```text
Épée longue en acier embrasé
```

Mais le nom ne doit pas être utilisé pour déterminer l'identité technique de l'objet.

Deux objets peuvent avoir un nom identique tout en étant techniquement différents.

---

# 19. Description générée

La variante peut également recevoir une description générée.

Exemple :

```text
Épée longue fabriquée à partir d'acier renforcé et d'un
cristal de mana de feu. La lame conserve les propriétés
d'une épée longue classique mais inflige également des
dégâts de feu.
```

Cette description doit rester secondaire par rapport aux données structurées.

Le gameplay ne doit jamais dépendre de l'analyse d'un texte descriptif.

---

# 20. Historique de fabrication

Conserver l'origine de la variante.

Prévoir si possible :

```text
created_from_base_item
created_by_recipe
materials_used
created_at
creator / artisan
shop
```

Cela permettra plus tard de développer :

* traçabilité ;
* réputation des artisans ;
* objets légendaires ;
* signatures d'artisans ;
* historique des objets ;
* commerce de créations uniques.

Ne pas rendre ces fonctionnalités obligatoires si elles n'existent pas encore, mais prévoir une structure extensible.

---

# 21. Magasins capables de fabriquer sur commande

Tous les magasins ne doivent pas nécessairement pouvoir fabriquer des variantes.

Ajouter une capacité du magasin, de l'artisan ou de l'atelier.

Exemple :

```text
custom_crafting = true
```

Mais cette capacité doit idéalement être plus précise.

Exemple :

```text
forge
    catégories : weapon, armor
    matériaux : metal, crystal
```

ou :

```text
atelier_de_cirier
    catégories : candle
    matériaux : wax, herb, crystal
```

La commande doit être refusée si le magasin ne possède pas les capacités nécessaires.

---

# 22. Séparation entre moteur de fabrication et magasin

Le magasin ne doit pas contenir la logique complexe de génération des items.

Architecture recommandée :

```text
Shop
   ↓
CustomOrderService
   ↓
CraftingEngine
   ↓
MaterialResolver
   ↓
ModifierResolver
   ↓
ItemVariantGenerator
   ↓
RecipeGenerator
   ↓
Database
```

Le magasin gère :

* la commande ;
* le prix ;
* le stock ;
* le paiement ;
* le statut de la commande.

Le moteur de fabrication gère :

* la compatibilité ;
* les matériaux ;
* les modificateurs ;
* les effets ;
* la génération de l'item ;
* la génération de la recette.

---

# 23. Transactions

La création finale doit être atomique.

Lors de la finalisation :

```text
BEGIN TRANSACTION

1. vérifier la commande
2. vérifier les matériaux
3. réserver/consommer les matériaux
4. calculer la variante
5. rechercher une variante identique
6. créer l'item si nécessaire
7. créer la recette si nécessaire
8. enregistrer la commande
9. débiter le client
10. mettre à jour le stock

COMMIT
```

En cas d'erreur :

```text
ROLLBACK
```

Il ne doit jamais être possible de consommer les matériaux et de ne pas créer l'objet à cause d'une erreur intermédiaire.

---

# 24. Gestion de l'objet final

Il faut distinguer :

### ItemDefinition

Définition générale d'un type d'objet.

Exemple :

```text
Épée longue en acier embrasé
```

### ItemInstance

Objet concret possédé par un personnage.

Exemple :

```text
Épée longue en acier embrasé
ID instance : 984523
```

La commande doit normalement créer ou récupérer une **ItemDefinition**, puis créer l'instance correspondant au résultat de la commande.

Cela permet à plusieurs joueurs de posséder la même variante sans multiplier les définitions.

---

# 25. Exemple complet

Le joueur entre dans une forge.

Il choisit :

```text
Objet souhaité :
Épée longue
```

La forge détecte que l'objet de base existe.

Elle affiche les matériaux compatibles :

```text
Lame :
- fer
- acier
- mithril

Matériau magique :
- aucun
- cristal de feu
- cristal de glace
```

Le joueur fournit :

```text
2 × acier
1 × cristal de feu
```

Le système calcule :

```text
Base :
Épée longue

Acier :
+2 dégâts physiques
+1 poids

Cristal de feu :
+ effet dégâts de feu
```

Résultat :

```text
Épée longue en acier embrasé

Dégâts physiques : 12
Poids : 4
Effet : dégâts de feu
```

Le système cherche alors :

```text
variant_key
```

Si elle existe :

```text
réutiliser ItemDefinition existante
```

Sinon :

```text
créer ItemDefinition
créer RecipeDefinition
```

Puis créer l'instance de l'objet pour le joueur.

---

# 26. Important : les recettes générées doivent devenir utilisables

Une fois qu'une variante a été créée en base, elle doit être considérée comme un véritable élément du système.

Cela signifie que les systèmes existants qui travaillent avec les items et recettes doivent pouvoir la retrouver normalement.

Exemple :

```text
Commande initiale
→ création de l'épée personnalisée
→ recette persistée
```

Puis :

```text
joueur découvre la recette
→ peut potentiellement la fabriquer à nouveau
```

Le comportement exact concernant l'apprentissage de la recette doit être configurable.

Ne pas supposer automatiquement que toute recette générée devient connue de tous les joueurs.

---

# 27. Découverte de recette

Prévoir trois notions différentes :

```text
RecipeDefinition
```

La recette existe dans la base.

```text
RecipeKnowledge
```

Le personnage connaît la recette.

```text
RecipeAvailability
```

Le personnage peut effectivement la fabriquer compte tenu de ses compétences, de son atelier et des matériaux.

Cette distinction permettra d'éviter de confondre :

> « la recette existe »

avec :

> « le joueur connaît la recette ».

---

# 28. Règles à respecter absolument

Ne pas :

* créer des items totalement arbitraires sans prototype ;
* créer des variantes sans item de base ;
* créer une variante sans recette correspondante ;
* dépendre du nom de l'objet pour son identité ;
* coder en dur les effets de chaque matériau dans le système de commande ;
* permettre au client de déterminer directement les caractéristiques finales ;
* faire confiance aux calculs effectués uniquement côté client ;
* créer des doublons pour des variantes strictement identiques ;
* modifier le comportement des recettes standards sans nécessité ;
* consommer des matériaux hors transaction ;
* créer l'item avant que la commande soit validée.

---

# 29. Compatibilité avec le système existant

Avant toute modification :

1. identifier le modèle actuel des items ;
2. identifier le modèle actuel des recettes ;
3. identifier la manière dont les items sont référencés ;
4. identifier le système actuel de fabrication ;
5. identifier le système de stock ;
6. identifier le système de magasin ;
7. identifier les catégories et tags existants ;
8. identifier le système actuel de caractéristiques ;
9. identifier le système actuel d'effets ;
10. identifier le système de persistance.

Réutiliser les structures existantes autant que possible.

Ne pas créer un deuxième système d'items ou un deuxième moteur de recettes parallèle.

Le nouveau système doit s'intégrer au système existant.

---

# 30. Migration et rétrocompatibilité

La modification doit être rétrocompatible.

Les items et recettes actuellement présents en base doivent continuer à fonctionner sans migration destructrice.

Les nouvelles propriétés doivent être :

* optionnelles lorsque possible ;
* dotées de valeurs par défaut raisonnables ;
* compatibles avec les anciennes données.

Prévoir une migration de base de données si nécessaire.

---

# 31. Tests à implémenter

Ajouter des tests couvrant au minimum :

### Cas standard

* fabrication d'un item avec une recette existante ;
* lecture d'un item existant.

### Commande simple

* commande valide ;
* matériaux fournis par le client ;
* matériaux achetés au magasin.

### Validation

* item de base inexistant ;
* matériau inexistant ;
* matériau incompatible ;
* quantité insuffisante ;
* magasin incapable de fabriquer ;
* paiement insuffisant.

### Génération

* calcul correct des caractéristiques ;
* application correcte des effets ;
* combinaison de plusieurs matériaux ;
* résolution des conflits ;
* génération déterministe.

### Persistance

* création de l'ItemDefinition ;
* création de la RecipeDefinition ;
* lien correct avec le prototype ;
* conservation des matériaux ;
* création de l'ItemInstance.

### Déduplication

Créer deux commandes strictement identiques et vérifier qu'elles utilisent la même définition de variante.

### Transaction

Simuler une erreur pendant la création et vérifier qu'aucune ressource n'est perdue et qu'aucune donnée partielle n'est persistée.

---

# 32. Priorité d'implémentation

Implémenter dans cet ordre :

1. analyser l'architecture existante ;
2. identifier les modèles Item / Recipe / Material / Shop ;
3. définir les extensions minimales nécessaires ;
4. implémenter le modèle de commande ;
5. implémenter la validation ;
6. implémenter la résolution des matériaux ;
7. implémenter le calcul des modificateurs ;
8. implémenter la génération déterministe de variante ;
9. implémenter la persistance ItemDefinition ;
10. implémenter la persistance RecipeDefinition ;
11. implémenter la création de ItemInstance ;
12. implémenter les transactions ;
13. implémenter la déduplication ;
14. intégrer aux magasins ;
15. intégrer à l'interface existante ;
16. ajouter les tests ;
17. documenter l'API et le modèle de données.

---

# 33. Résultat attendu

À terme, le système doit permettre le flux suivant :

```text
ITEM EXISTANT
      ↓
CLIENT PASSE COMMANDE
      ↓
CHOIX DES MATÉRIAUX
      ↓
VALIDATION
      ↓
CALCUL DES MODIFICATEURS
      ↓
GÉNÉRATION D'UNE CLÉ DE VARIANTE
      ↓
┌─────────────────────────────┐
│ Variante déjà en base ?     │
└──────────────┬──────────────┘
               │
       ┌───────┴───────┐
       │               │
      OUI             NON
       │               │
       ↓               ↓
réutiliser        créer ItemDefinition
                  créer RecipeDefinition
       │               │
       └───────┬───────┘
               ↓
       créer ItemInstance
               ↓
       consommer matériaux
               ↓
       finaliser commande
```

Le principe architectural essentiel est :

> **Les recettes standards définissent les objets connus. Les commandes permettent de dériver de nouveaux objets à partir d'un prototype connu et de matériaux connus. Une fois validée, chaque nouvelle combinaison devient une définition persistante et réutilisable du système.**

Le système doit donc transformer progressivement les créations des joueurs en **nouveaux éléments persistants de l'économie et de l'artisanat de Telluris**, sans transformer le jeu en générateur d'objets arbitraires.
