# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Telluris is a browser-based medieval-fantasy RPG. The backend is a FastAPI server serving Jinja2 HTML templates; the database is CouchDB. There is no separate JS framework — all interactivity is vanilla JavaScript embedded in the templates.

## Running the app

```bash
docker compose up
```

FastAPI listens on `http://localhost:8000`. CouchDB listens on `http://localhost:5984`. The compose file installs Python dependencies at container start (no pre-built image).

## Running tests

```bash
pytest tests/
```

Tests only cover pure-Python logic (stats, combat à distance, marché/recettes, consommables, sorts) and have no DB dependency.

**Côté JavaScript** (tout l'interactif est du JS vanilla embarqué dans les templates : ni compilé, ni typé, ni couvert par pytest) — deux harnais **Node sans aucune dépendance**, donc pas de `package.json` ni de second écosystème à entretenir :

```bash
node dev/check_js.js            # syntaxe du JS inline de TOUS les templates/*.html
node dev/test_slots_client.js   # exécution des fonctions de la barre de slots
```

Les deux sortent en **code 1** en cas d'échec. `check_js.js` neutralise les expressions Jinja avant de passer le code au parseur de Node — ⚠️ en `(0)` et non `0`, sinon `{{ liste | tojson }}.forEach(...)` deviendrait `0.forEach(...)`, faux positif garanti. `test_slots_client.js` extrait les fonctions **pures** du template (par nom, accolades équilibrées) et les exécute dans un contexte `vm` : il ferme la classe de bug « à qui appartient ce que j'affiche et ce que j'écris ? », qui a produit le mélange principal/compagnon des barres de slots et qu'aucun test pytest ne pouvait atteindre. **Hors de portée sans jsdom** : le rendu DOM, le clic long, l'ordre inversé en mobile — à vérifier en jeu.

Docker/l'app tournent côté utilisateur (`docker compose up` dans le conteneur).

## Inspecting live DB values

La CouchDB live tourne sur un hôte distant, généralement NON joignable en local. Pour connaître les valeurs réelles des documents (races, espèces, profils, lieux, items…), lire le dump JSON committé à la racine : `telluris-dump-YYYYMMDD-HHmmss.json` (le timestamp change ; produit par l'export admin `GET /admin/exports/couchdb` / `db.config.dump_all_docs()`). C'est un objet `{"db","exported_at","doc_count","docs":[...]}` ; `docs` exclut les `user:*`. Repérer un doc via grep sur `"_id": "rules:races"`, etc. Export ciblé d'un seul type : `GET /admin/exports/by-type?type=<type>` (`find_docs({"type": t})`, `user:*` exclus) → fichier `<type>-AAAAMMJJ-HHMMSS.json` ; la page `/admin/exports` propose une liste à saisie libre des types présents en base. **Édition en tableau** : la page `/admin/table` (`admin_table.html`, carte « Mise à jour en tableau » dans `/admin`) liste les docs d'un type choisi en tableau (colonnes choisies/ordonnées par drag, triables, filtrables, redimensionnables) ; cliquer une ligne ouvre le JSON dans un overlay fixe à droite, **Save** = `PUT /admin/doc` (réattache le `_rev` courant) / **Cancel** ferme / **Delete** = `DELETE /admin/doc?id=…` après `confirm()` (le `_rev` est relu en base, jamais celui du client ; `db.delete_doc` renvoyant `None` succès comme échec, le serveur vérifie par relecture → 409 ; la ligne est retirée localement, sans rechargement du type). Données : `GET /admin/table/data?type=<t>` (`user:*` exclus). Les préférences d'affichage (colonnes/ordre/tri/filtres/largeurs) sont mémorisées **par type** dans `localStorage` (`telluris.admin_table.v1.<type>`). **Export** : deux boutons au-dessus du tableau exportent les lignes **actuellement affichées** (filtres+tri, `computeVisibleRows`) — **⬇ Export JSON** (docs complets, tableau JSON) et **⬇ Export Excel** (`POST /admin/table/export.xlsx` → writer OOXML partagé `utils/xlsx.py`, une colonne par clé de 1er niveau, valeurs imbriquées en JSON). Nom de fichier commun `exportFilename(ext)` = `<type>_filtre_<col>_<val>…_AAAAMMJJ-HHMMSS.(json|xlsx)` (horodatage **UTC**, format `AAAAMMJJ-HHMMSS` aligné sur les exports serveur `datetime.utcnow()`).

## Core Design Patterns

### CouchDB document IDs
Pattern `type:identifier` — e.g. `user:email@example.com`, `lieu:lutecia`, `rules:races`. Characters = `character:<user_id>_<uuid>`.

### Derived stats are never stored
`DerivedStats` recalculated by `compute_derived_stats()` at request time. Never persist derived values.

### Character document vs. Pydantic model
`models/character_document.py` = reference spec. Ground truth = `routers/user.py` creation code. Field names differ: `voc`, `sex`, `caracteristiques_standard`/`current`, `cite`.

## Core Mechanics

### Échelle des caractéristiques (×10, sauf V)
7 caractéristiques à l'échelle ×10 (F/R/Ag/Vol/Int/Cha/Ch ≈ 10-100). V = 1-10 (base raciale ~4-5, max ~7-8), `deplacement = V` cases/tour. Formules (joueur + monstres) : `cc = (F + Ag*3)//4`, `cd = (Ag*3 + V*10)//4`, `initiative = (Ag + V*20)//3`, `actions_max = max(1, ceil(Ag/40 + V/2))` → **Ag est la god-stat**.

### Plafonds de caractéristique — quota racial + dépassement
`compute_stat_cap` (`models/character_stats.py`) donne le plafond effectif d'une caract, sur les caracts **BRUTES** (un buff n'ouvre jamais un plafond — même exclusion anti-exploit que `charge_max_of` et les coûts d'XP). Trois cas : (1) **quota non plein** → `stats_max` racial ; (2) **quota plein** (`nb_max_accessibles`, défaut 3, caracts déjà au max racial) → **sous-plafond** `stats_max − 10` (`−1` pour V) ; (3) **bonus de dépassement engagé sur CETTE caract** → `stats_max + max_bonus[caract]`, qui prime sur tout le reste.

**Le dépassement est un trait de DONNÉE, pas de code** : une race le porte via `max_bonus:{caract:Δ}` sur `rules:races` (seul l'**humain** l'a : `+10`, `+1` pour V — « Peut dépasser 1 maximum »). Il est **unique et irréversible** par personnage : `character["max_bonus_used"]` mémorise la caract choisie (absent ⇒ jamais utilisé, aucune initialisation à la création). `POST /api/spend_xp` prend un **`use_max_bonus`** booléen — 422 si déjà consommé ou si la race n'a pas de bonus —, arme le plafond **avant** de valider la montée, puis persiste le champ. ⚠️ Le bonus ouvre le **plafond**, jamais le **tarif** : `compute_xp_cost` est inchangé. Passe par le chokepoint `_acteur` ⇒ un **compagnon** humain y a droit, sur SON doc.

**Payload** : `utils/fiche.bloc_fiche` publie `max_bonus` + `max_bonus_used` à côté de `stat_caps` (source unique ⇒ contexte `/play` **et** fiche de compagnon, qui ne reçoit pas `race`) ; `spend_xp` renvoie `max_bonus_used`, sans quoi le client continuerait à offrir le geste sur les autres caracts jusqu'au prochain `/play`.

**UI** (`play_town_telluris.html`, onglet ⚔) : bouton `✦ Dépasser +Δ` (`.sh-bonus-btn`, violet pour ne pas se confondre avec le doré du bouton d'XP) offert sur les seules caracts **BLOQUÉES** (`val >= cap` : au max racial, ou coincées au sous-plafond par le quota), tant que le bonus est libre. Il ouvre l'overlay `#max-bonus-overlay` (calque et briques de carte des clauses — décision bloquante de plus, et celle-ci est définitive ; ✕/Échap/backdrop = annuler sans rien engager), qui appelle `spendXp(code, true)`. ⚠️ Le bouton est rendu **même quand il n'est pas offert**, en `display:none` : une caract peut se bloquer en cours de session (montée au max, ou quota qui se remplit et rabaisse un autre plafond) et `_refreshStatBoxes` l'allume par `getElementById` — sans l'élément, il n'aurait rien à allumer ; son `onclick` est donc posé en JS, pas seulement en Jinja.

⚠️ **Jauge : l'échelle et le repère sont DEUX valeurs distinctes.** `échelle` (100 % de la barre) = `max(maxRace, cap)` — sans quoi le remplissage déborderait une fois le plafond dépassé. Le **pip** = `min(cap, maxRace)` : il reste **planté au max naturel de la race**, c'est le repère que le remplissage doit visiblement franchir ; il ne descend en dessous que sous l'effet du quota (`.subcap`, grisé). Les faire bouger ensemble (pip = cap) rend le dépassement **invisible** — la barre d'un 65/70 devient identique à celle d'un 65/70 ordinaire. Trois sites à tenir d'accord : le rendu Jinja (`echelle`/`pip_val`), `_refreshStatBoxes` et `_renderCaractsMod` (qui réécrit la même largeur de remplissage depuis le total buffé).

### Navigation bitmask
8-direction via `nav` dict (bit 1=HAUT, 2=HAUT_DROITE, …, 128=HAUT_GAUCHE). `VALID_MOVES` (source unique, `utils/lieux.py`) → `MOVE_OFFSETS`. **Combat partage** : `_find_path` (A*) et `_reachable_region` (flood fill) utilisent mêmes directions + `nav_allows`. ⚠️ **Pas 4 directions** (îlots diagonaux). `create_combat_doc` : `grid = {dims, cells, nav}` — sans `nav`, placement ≠ déplacement. Même jeu + même masques.

### Références d'items & poids
Entrée d'inventaire = **string legacy** `"item:xxx"` (poids = min) **ou object** `{"item": "item:xxx", "poids": <nb>}`. Doc `item:*` `poids` = nombre OU `[min,max]`. Helpers : `item_ref_id`, `poids_bounds`, `item_ref_weight`, `resolve_item_ref`. Actions client adressent par **index+item_id** (instances d'un même item peuvent peser différemment). Une référence peut aussi porter **`lieu_parent`** = le lieu qui a délivré CET exemplaire (`item_ref_lieu`) : le doc item reste **générique** (une seule `item:carte_aventurier` pour toutes les guildes) et `resolve_item_ref` — chokepoint d'affichage, le client ne rend que `nom` — en dérive le label **« Carte d'aventurier (Auxerre) »** (`item_label`). Jamais de `lieu_parent` sur le doc item.

### Charge & surcharge
`charge_max_of(character)` = `F*5` (dérivée, jamais stockée). `carried_weight(character)` somme les poids effectifs de l'inventaire **+ équipés** (pas le sol). En **exploration**, si `carried_weight > charge_max` le déplacement est bloqué (garde 409 dans `move_character`, flèches désactivées côté client) ; au pickup, le dépassement fait tomber des items **aléatoires** au sol. En **combat**, au-delà de la **demi-charge** le déplacement est divisé par deux (`utils/combat.py`). Les objets au sol (`objets_au_sol`) sont **transitoires** : vidés dès un déplacement réel.

### Combat & butin (`utils/combat.py` + `routers/combat.py`)
Un combat est un doc `combat:*` (snapshots `joueurs[]`/`monstres[]`, `ordre_initiative`, `battle_map_id`). Les **stats dérivées des monstres** viennent de `espece:*` (min/max) modulées par `profil:*` (niveau, deltas). `finalize_combat()` applique XP/PV **et** le butin ramassé en combat, de façon **idempotente atomique** (id du combat dans `character["combats_recompenses"]`, même doc que l'XP). Le butin de victoire n'est **jamais** auto-ajouté : `butin_disponible` (poids tiré au niveau du profil via `random.choices`) est proposé dans l'overlay, encaissé par `POST /api/combat/{id}/collect` (borné par `charge_max`). Carcasses = `item:<sub_id>` (1-pour-1 avec `espece:<sub_id>`), créées à la volée si absentes.

### Attaques par mode — corps à corps / jet / tir
Mode via tag : `tir` (arcs), `jet` (lancer), sinon **cac** (hast = cac `portee ≥ 2`). Champs item : `portee` (défaut 1), `restriction:{caract:min}` (ET). `restriction_satisfaite` → blocage dur `equip_item` (422). `_weapon_attacks` = `joueur["attaque_profils"]` (1 par mode, meilleure portée, poings portée 1 toujours présent). Chaque profil : `mode`, `portee`, `ranged`, `toucher` (cc/cd), `degats` (cc/cd). **cac** = cc/F, portée item ; **jet** = cd/F, portée `item + F//JET_PORTEE_F_DIV` ; **tir** = cd/Ag, portée item. `resolve_action` sélectionne profil. **Règles ranged** : interdit si engagé (1 case), exige ligne de vue (Bresenham `seeThroughCell` — falaise transparente, mur seul bloque —, `nav` ignoré). UI (slots) : **plus de sélecteur de mode ni de boutons d'attaque fixes** — chaque mode est une **entrée assignable** à une case de la barre (`{type:"attaque", ref:"cac"|"jet"|"tir"}`, cf. § Barre d'action de combat). Une case d'attaque garde sa position et se **grise** quand le mode n'est pas équipé (`modesEquipes`) ou n'a aucune cible (`targetableMonsters(mode)`) — elle ne disparaît plus, sinon les cases voisines se décaleraient d'une arme à l'autre. `triggerAttack(mode)` fixe `currentMode` puis attaque directe (1 cible) ou ouvre le sélecteur de cible (les cases d'attaque s'effacent en `visibility` via `.hidden-selecting`, la grille gardant sa forme). `currentMode` pilote la visibilité des cibles ; les **badges du bandeau d'initiative** (`.init-badge.monstre`) servent aussi de ciblage — bordure grise hors portée, **rouge + cliquables** (attaque, `refreshBadgeTargets`) uniquement quand attaquables (tour + action + portée), miroir du clic sur `.monster-token.adjacent`. Monstres = mêlée seule. Tests purs `tests/test_combat_ranged.py`.

**UI panneaux combat** (`combat_telluris.html`, refonte) : panneau perso = reprise du `<section class="character-panel">` de play_town — portrait recadré du joueur (`#left-portrait.pt-crop` via `applyPlayerPortrait`, carré, barres PV/PM verticales), identité, pips d'actions + jauge de charge (pas de mini-stats). Vie des ennemis = **anneaux PV** sur les badges du header (`setRing`/`MONSTER_CIRC`) + grand portrait du dernier ciblé (plus de liste d'ennemis). Carte iso : `MAX_H`=10 rangées, `--step` borné à la **seule largeur** (`max(8, w/17)`) → hauteur agrandie sans toucher la largeur, page défilable.

### Barre d'action de combat — slots configurables
La barre était une **liste flex qui grandissait toute seule** (3 boutons d'attaque + `#quick-sorts` + 🔮 + `#quick-comps` + ⚡ + 🧪 + 🫳 + 🏃) : rien ne bornait le nombre d'icônes, et la position d'un bouton changeait d'un personnage à l'autre, d'un tour à l'autre (les quick-bars se re-rendaient à chaque changement d'acteur) — aucune mémoire musculaire possible. Elle est remplacée par un **nombre FIXE de cases** dont **le joueur décide une à une du contenu** — et la barre devient le **seul accès** aux sorts, compétences et consommables (🔮/⚡/🧪 et leurs sélecteurs ont été supprimés) : ce qui n'a pas été préparé ne se joue pas, sauf à passer par ⚙ en plein combat, au prix d'une action. Logique pure `utils/slots_actions.py` (DB injectée, pattern `utils/sorts.py`), tests `tests/test_slots_actions.py` (28) + `tests/test_combat_slots.py` (12).

**Mise en page par WRAP, pas par grille figée** (`.slot-grid` = `flex` + `flex-wrap`) : la case vaut `clamp(28px, (100% − 45px)/10, 46px)`, soit 1/10 du conteneur plafonné à 46 px. Sur téléphone (~390 px) cela fait exactement **10 cases par rangée**, donc 2 rangées ; au-delà d'environ **1015 px les 20 tiennent sur une seule ligne**. Aucune media query de mise en page — la largeur de la case suffit à décider ; les tailles intermédiaires wrappent librement (assumé).

**Champ `character["slots_actions"]`** = liste **dense positionnelle** de longueur `COMBAT_SLOTS_MAX` (index 0 = slot 1), trous = `None`. Entrée = `{"type", "ref"}` : `attaque` (ref ∈ `cac`/`jet`/`tir`), `sort`, `competence` (ACTIVE seulement), `consommable`, `ramasser`, `fuir`. Une entrée de **sort** porte en plus **`composants` (bool)** : engager ou non les composants **CONSOMMÉS**. ⚠️ Les **catalyseurs** (`consomme:false`) sont **toujours** engagés — ne rien dépenser pour s'en priver n'aurait aucune contrepartie —, donc le flag ne les concerne pas. Défaut **`True`** (comportement historique de l'accès rapide), posé par `normaliser_entree` : une entrée héritée de la migration est donc **égale** à `composants:true` au sens de `_memes_entrees` → déplacée, jamais dupliquée. `true` et `false` sont en revanche **deux entrées distinctes** : le même sort peut occuper deux cases, une qui dépense et une qui économise. Le badge **`+`** en bas à droite de la case s'affiche ssi le flag est posé **ET** qu'il reste un composant consommable disponible (calcul CLIENT depuis `SORTS`, resynchronisé après chaque lancement — `slots_payload` n'expose que le réglage, pas la disponibilité, qui serait périmée dès le premier cast). Porté aussi bien par `character:*` que par `aventurier:*` — **chaque membre du groupe a SA disposition**, rechargée au changement de tour.

⚠️ **Un consommable est référencé par `item_id` (le TYPE), jamais par index d'instance** : le sac bouge à chaque ramassage, un index serait périmé au tour suivant. Le pont vers l'API de combat (qui exige `index + item_id`) se fait dans `slots_payload`, qui **résout l'index du premier exemplaire à chaque rendu** — jamais persisté. Sac vide ⇒ la case **reste** et se grise (racheter des potions ne doit pas obliger à reconfigurer la barre).

⚠️ **INVARIANTE — trois actions obligatoires** (`ENTREES_OBLIGATOIRES` : mêlée `cac`, `ramasser`, `fuir`) présentes **exactement une fois chacune**, à n'importe quelle position : elles se **déplacent** librement mais ne se **retirent** pas — une barre sans bouton de fuite enfermerait le joueur dans le combat. L'invariante est réparée **À LA LECTURE** (`slots_effectifs` → `_reparer_obligatoires` : doublons effacés, manquantes replacées dans la première case libre, et en dernier recours en écrasant la dernière case), pas seulement à l'écriture — un doc bricolé à la main ne peut pas la violer. Conséquences : `vider_slot` **refuse** (422) sur une obligatoire ; `poser_slot` **déplace** une obligatoire déjà placée ailleurs au lieu de la dupliquer, et **échange** les deux entrées si la case cible en portait une (sinon déposer un sort sur 🏃 la supprimerait, et la réparation la remettrait ailleurs à l'insu du joueur).

**Champ absent ⇒ migration À LA LECTURE, aucune migration de base** : ⚔🫳🏃 aux slots 1-2-3 puis `sorts_epingles_effectifs` et `competences_epinglees_effectives` à partir du slot 4 (`_slots_derives`) → un personnage d'avant la refonte retrouve exactement la barre qu'il avait. Les deux helpers d'épinglage **survivent pour ça** ; les endpoints `POST /api/epingler_sort` / `epingler_competence` et le bouton 📌, eux, ont disparu.

⚠️ **Toute écriture de slots doit porter le `compagnon_id` de l'ACTEUR COURANT.** `_acteur` retombe **silencieusement sur le principal** quand le corps n'en porte pas : réorganiser la barre d'un compagnon écrivait alors sur le doc du principal, et la réponse renvoyait la barre du principal, que le client affichait comme celle du compagnon — les deux barres finissaient durablement mélangées (bug historique). ### Critiques pilotés par la Chance
**Ch enfin mécanique.** Tout jet d100 offensif (arme cac/jet/tir, sort, compétence — quel que soit son `jet` cc/cd/magique — et attaque de monstre, y compris monstre→monstre) passe par **deux helpers uniques** de `utils/combat.py`, au lieu du `seuil → roll → if` qui était copié-collé sur 4 sites :
- **`_seuils_critiques(attaquant, defenseur)`** → `(seuil_reussite, seuil_echec)`. `delta = Ch_att − Ch_cible`, les **deux** fenêtres glissent de `delta // CRIT_CHANCE_DIVISEUR` : la chance élargit la réussite critique ET repousse l'échec, **symétriquement**. Les world-vars génériques `CRIT_REUSSITE_MAX` (5) / `CRIT_ECHEC_MIN` (96) restent des **garde-fous bornants** (`max(base_ok, …)` / `min(base_ko, …)`) → le glissement ne peut que jouer en faveur du plus chanceux, un jet ≤ 5 est toujours un crit et un jet ≥ 96 toujours un fumble. `CRIT_CHANCE_DIVISEUR = 0` désactive tout.
- **`_resoudre_jet(attaquant, defenseur, seuil)`** → `{roll, seuil, touche, critique, fumble, mult_degats}`. Le **critique PRIME sur le seuil de toucher** : une réussite critique touche même si le seuil était raté, un échec critique rate même si le seuil passait.

**Réussite critique = dégâts ×2**, multiplicateur appliqué **AUX DÉS, avant la soustraction des PA** (`roll_dice(...) * mult - pa`) : le crit double le coup, pas la pénétration d'armure. La magie n'ayant pas de PA à soustraire, le ×2 y joue seul.

**Échec critique = une action de plus perdue** (`_appliquer_fumble`). ⚠️ `actions_restantes` n'est **jamais décrémenté**, il est **recalculé** par `_refresh_actions` depuis des compteurs → une pénalité DOIT être un compteur (poser `actions_restantes = 0` serait écrasé au prochain refresh). Deux champs : **`penalites`** (compté dans `used`, remis à zéro au reset de tour) et **`dette_actions`** (ce qui n'a pas pu être payé faute d'action restante, **survit au reset** : `_reset_turn_budget` le convertit en `penalites` du nouveau tour puis l'efface — c'est le « reporté au tour suivant »). `penalites` entre aussi dans les **projections de déplacement** (`projected > actions_max`), sinon un fumble serait indolore pour qui se contente d'avancer. Un perso à `actions_max == 1` qui fumble perd donc tout son tour suivant (assumé).

⚠️ **`_do_attack_on` décompte désormais l'action de l'attaquant lui-même** (`attaques += 1` + `_refresh_actions`), au lieu de laisser ses 2 appelants le faire après coup : le test de fumble a besoin d'un budget déjà à jour. Aux 3 sites joueur, `_appliquer_fumble` est appelé **après** l'incrément du compteur d'action.

Snapshots : `ch` ajouté aux **deux** constructeurs (`build_joueur_snapshot` = valeur **avec buffs**, `build_monster_snapshot`). Tous les accès en `.get("ch", 0)` → un combat déjà en base tourne avec delta 0 = comportement d'avant. ⚠️ **Données** : beaucoup d'`espece:*` ont encore `Ch = {min:0, max:0}` → delta large en faveur du joueur, à peupler. Log : nouveaux `kind` **`crit`** (raffiné `j-crit`/`m-crit` côté client, la classe brute `crit` servant au rendu Jinja initial qui ne connaît pas cette bascule) et **`fumble`**. Tests purs `tests/test_combat_crit.py` (18).

### UI — listes scrollables de la fiche perso 
Une liste longue de la fiche ne pousse plus le panneau : elle **scrolle chez elle**. ⚠️ **Deux familles, et le choix se fait sur UN critère : QUI défile, le conteneur ou son enfant ?** Un `position:sticky` dans un conteneur qui ne défile pas ne colle à rien ; un `::after` en `absolute` sur un conteneur qui défile, lui, remonte avec le contenu. Prendre la mauvaise brique donne une ombre qui ne se voit pas ou qui se promène.

**(A) Le conteneur défile lui-même** → `.sh-rel-scroll` + overlay sticky. Onglets 🤝 (relations), 📜 (quêtes) et ⚡ (sorts/écoles/compétences/apprentissages).
- **`.sh-rel-scroll`** = le conteneur scrollable **générique** (`overflow-y:auto`, scrollbar fine, `position:relative` — remonté à la base, il était dupliqué sur chaque modificateur). Une classe de **hauteur** l'accompagne, par famille de liste : `.sh-quest-list-active` (40vh), `.sh-quest-list-ended` (35vh), **`.sh-capa-list` (35vh, onglet ⚡)** — les relations gardent la base (45vh).
- **`<div class="sh-list-shadow-overlay"></div>`** = **l'ombre générique de bas de liste**, `position:sticky; bottom:0` : c'est le **dernier enfant** du conteneur scrollable. ⚠️ Elle est **dans le flux** : un rendu client qui construit la liste doit l'émettre lui-même, après les lignes.
- ⚠️ Conséquence pour les listes à **double rendu** (Jinja au chargement + JS au resync) : le markup wrapper + overlay doit exister **des deux côtés**, sinon l'ombre disparaît au premier resync. C'est le cas de l'onglet 📜 (`renderFicheQuetes` réémet `.sh-quest-list-active` / `.sh-quest-list-ended` + l'overlay). Les 5 listes de l'onglet ⚡ échappent au problème par **enveloppement** : leurs renderers (`_renderSorts`, `_renderCompetences`…) écrasent l'`innerHTML` du div **interne**, l'overlay vit dans le wrapper et survit — aucun JS à toucher pour ajouter une liste.

**(B) Le conteneur est FIXE et c'est son enfant qui défile** → `.sh-scroll` + `::after`. C'est le cas des **sacs** (`.sh-inv-scroll` de hauteur fixe, `.sh-inv-box` interne qui défile sur 10 lignes) : onglet 🎒 (sac + sol), marchand (vente/achat), panneau 👥 Groupe.
- L'ombre est un **`::after` en `absolute`** sur le wrapper, **conditionnée par la classe `.scrollable`** que le JS pose selon `length > INV_VISIBLE` → **pas d'ombre quand il n'y a rien à faire défiler**, ce que la brique sticky ne sait pas faire. Variante `.sh-inv-scroll.sh-scroll.scrollable::after` = hauteur d'**une demi-ligne d'objet** (`--inv-row-h / 2`), pensée pour les sacs.
- ⚠️ **`.sh-scroll` est à poser explicitement** : `.sh-inv-scroll` seul donne le défilement **sans l'ombre**. Le sac et le sol de l'onglet 🎒 sont restés un an dans cet état (corrigé). **Vente/achat du marchand ne l'ont toujours pas.**

**Le tableau tourne — d'autres aventuriers prennent les contrats** : une offre **générée** porte un **`expire_at`** posé à la génération (`_duree_de_vie` = `QUETE_BOARD_DUREE_SECONDES` **jittée** de ±`QUETE_BOARD_DUREE_JITTER` → 30 min-1 h 30 par défaut ; les 6 offres naissant au même instant, sans jitter le tableau basculerait **d'un bloc**). Péremption **PARESSEUSE** (aucun tick de fond) : `remplir_tableau` appelle `purger_offres_perimees` avant de compléter → le doc périmé est **SUPPRIMÉ** (`delete_doc` ; personne ne le référence, celui qui accepte en garde un snapshot) et la place est aussitôt repeuplée. `offre_perimee` ne vise **que** `source:"genere"` + `statut:"offerte"` : une quête **authorée** ne périme jamais, une **acceptée** a déjà quitté le tableau. Repli sans `expire_at` (offres d'avant la feature) : `genere_at` + durée nominale → les tableaux existants tournent sans migration. Tests `tests/test_quetes_board.py` (12 tests).

**Renoncer fâche toute la MAISON du donneur** (`quetes.sanctionner_renoncement`, chokepoint unique) : **abandonner** une quête (n'importe quel type — `POST /api/quetes/abandonner`) **ou** laisser filer le délai d'une course (`transport.traiter_expirations`) coûte `QUETE_TRANSPORT_RELATION_DELTA` de relation chez le donneur **et chez tous les lieux de sa maison**. La **réussite**, elle, ne récompense que le donneur (`+1`, asymétrie assumée : la maison punit collectivement, elle ne remercie pas collectivement). **Maison = donnée, pas code** : `lieux_solidaires` = tous les lieux de **même `sous_categorie`** (champ sur les `lieu:*`, même orthographe que sur les items) **ET de même `lieu_parent`** que le donneur. La **conjonction** est indispensable : le `lieu_parent` des lieux d'une guilde est la **CITÉ** (`lieu:auxerre`), donc seul il ramènerait les 36 lieux d'Auxerre ; et la seule `sous_categorie` ramènerait les guildes des autres cités. Un donneur **sans `sous_categorie`** (un magasin) n'est solidaire que de lui-même → comportement historique inchangé. La **façade** `guilde_aventurier_exterieur` ne porte pas le champ : elle est hors maison (lui poser le champ suffirait à l'y faire entrer, sans toucher au code — toute faction future s'y branche pareil). `find_docs` indisponible → repli gracieux sur le donneur seul. Tests `tests/test_quetes_relation.py` (15 tests).

### Quêtes de transport — magasins + tenancier générique
Un magasin X confie une **cargaison** à livrer à un magasin Y qui **rachète** ces biens (`lieu_buys`), dans un **délai réel** (`QUETE_TRANSPORT_DUREE_SECONDES`, 1 h). Réussite → **+1 relation avec X** (donneur seul) + XP + prime ; **échec (délai dépassé) ou abandon** → **−1 relation avec X *et avec tous les lieux de sa maison*** (cf. `sanctionner_renoncement`, §Quêtes — guilde), la **cargaison reste dans le sac** (revendable — tentation assumée). Logique pure `utils/transport.py` (DB injectée), tests `tests/test_transport.py` (40 tests).

**Magasin** = `marche.besoins_categorie(categorie)` non vide (28 catégories à recettes ; l'auberge n'en est pas une). **Tenancier générique** : aucun doc `lieu:*` marchand ne porte de champ `pnj` → `transport.entree_marchand(lieu)` dérive `pnj:marchand_<categorie>` (proba 1.0), injecté via `marchand_fn` dans `pnj.entrees_pnj` / `tirer_pnj_present` / `entree_pnj_active` (le champ `pnj` explicite prime toujours). Docs générés par `dev/gen_marchands.py` → `jsons/marchands_a_importer.json` (28 marchands, même arbre de dialogue, ambiance par métier). ⚠️ **Portraits = placeholders** (rotation sur les fichiers existants de `templates/resources/pnj/`) — à remplacer par un portrait par métier.

**Offre** : tirée à l'**ENTRÉE** du magasin (`QUETE_TRANSPORT_PROBA` = 10 %), persistée en champ transitoire `character["transport_offert"] = {lieu, quete|None}` — **même sémantique que `pnj_present`** (un refresh ne re-tire pas ; ressortir/rentrer re-tire). Pas d'offre si une course est déjà active (pas d'empilement). **Confiance requise** : `confiance_suffisante` — un marchand ne confie **aucune** cargaison si sa relation est **< `QUETE_TRANSPORT_RELATION_MIN`** (50, la valeur neutre ; 0 = garde-fou désactivé) **OU** si son **marchandage est bloqué** (`marche.marchandage_bloque`, crit d'échec récent : brouille datée, indépendante de la cote — elle ferme la porte même à relation ≥ seuil et même garde-fou désactivé, sa durée a sa propre world-var `MARCHANDAGE_BLOCAGE_SECONDES`). Relation absente en base = neutre → le tout-venant reçoit des offres. Ne vaut que pour les courses **générées** : une course **écrite** est confiée par son scénario, quelle que soit la cote du joueur.

**Deux sources d'offre** (aiguillage dans `poser_transport_offert(…, pnj_doc=…)`, qui reçoit le PNJ déjà arrêté pour cette entrée — `main.py` le résout AVANT le tirage) : (1) **générée** — le donneur est un magasin, tout est tiré au sort ; (2) **AUTHORÉE** — le **PNJ présent** porte une course écrite dans **`services.transport.offre`** = `{id, destination, cargaison:[{item, quantite, poids?}], duree?, proba?, unique?, titre?, description?, recompenses?}` (miroir de `services.soin`/`services.don`). Alors **n'importe quel PNJ peut confier une course** : le donneur n'a **pas** à être un magasin (`est_magasin` n'est plus le seul test) et rien n'est tiré au sort — les bornes `POIDS_MAX`/`NB_MAX` **ne s'appliquent pas** (seul le contrôle de charge à l'acceptation reste). L'`id` doit être **stable** : c'est le gate de `unique:true` (`deja_reussie` — un **échec ne bloque pas**, le donneur repropose). Le **destinataire**, lui, reste un magasin (c'est son tenancier qui a les nœuds `livre`/`incomplet`).

**Course à `retour`** (`spec.retour:true`) : le destinataire prend la marchandise mais **ne paie pas** (`livrer_en_attente_de_retour` → nœud `livre_retour`, repli `livre` ; `livree_at` posé, **`expire_at` retiré** — le délai portait sur la livraison, pas sur le retour) ; la quête **reste active** jusqu'à ce que le joueur revienne **rendre compte au donneur** (op `rapporter` → `rapporter_transport` → nœud `rapporte`), qui solde alors tout : XP, prime **et `recompenses.items`** (entrés au sac par `quetes.appliquer_recompenses`). `transport_a_livrer` exclut les courses déjà livrées ; `retour_attendu(character, lieu)` les retrouve chez le donneur. Flags de dialogue : `transport_a_rapporter`, `transport_en_cours` (confiée par CE lieu, **non encore livrée** → relance) et `transport_accompli` (course `unique` déjà réussie). `porte_effective` (BFS) donne la direction cardinale depuis un lieu **imbriqué** qui n'ouvre pas lui-même sur la grille de la ville (comptoir → réception → façade). **Items de récompense** (`recompenses.items` d'une offre écrite) = des références d'**instances**, fabriquées par `items_recompense(spec_items, giver_doc)` : une entrée peut demander `"lieu_parent": "auto"` (sentinelle `transport.LIEU_PARENT_AUTO`) → l'exemplaire remis porte le **`lieu_parent` du donneur** (repli : son `_id`). L'objet en base reste **générique** (`item:carte_aventurier`, un seul doc pour toutes les guildes) et c'est l'instance qui dit d'où elle vient → label `Carte d'aventurier (Auxerre)` (cf. §Références d'items) ; la même mission copiée dans une autre guilde délivre la carte de **sa** cité. Contenu de la **première mission de la guilde** — **2 fichiers** : `jsons/premiere_mission_a_importer.json` (lieu `le_bastion_de_l_yonne_comptoir`, sa connexion à la réception, `item:viande_sanglier_gobelin`, `item:carte_aventurier` **générique**) et `jsons/pnj-*.json` (**tous les docs PNJ**, Borin + les 28 tenanciers — seule source à jour) ; `jsons/carte_aventurier_correctif.json` = le correctif qui a rendu la carte générique (nouveau doc, `_deleted` de l'ancien `item:carte_aventurier_auxerre`, Borin corrigé). Borin (réceptionniste) confie 2 caisses de viande au fumoir `lieu:fumee_de_l_yonne`, puis **remet au retour** la carte d'aventurier de la cité dont relève son comptoir (`lieu:auxerre`). Le nœud **`livre_retour`** est porté par **les 28 marchands** (gabarit `dev/gen_marchands.py`) : n'importe quel magasin peut donc être la destination d'une course à retour, sans promettre une prime qu'il ne verse pas (le repli sur `livre` le ferait). **Cargaison** : items que X fournit (`stock_vente` + `produits_categorie`) ET que Y rachète ; empilage instance par instance, **arrêt AVANT de franchir** `QUETE_TRANSPORT_POIDS_MAX` (100 kg) **ou** `QUETE_TRANSPORT_NB_MAX` (10 objets) — la borne la plus contraignante gagne ; objet unique trop lourd → **pas d'offre**.

**Géographie** : aucune coordonnée monde sur les `lieu:*`, mais chaque doc `connection` boutique↔ville porte la **porte dans la grille de la ville** → `focalisation.charger_graphe` l'expose déjà, `portes_du_parent` + `direction_cardinale` (8 octants, **y croît vers le BAS** → nord = dy<0) + `repere_proche` (magasin le plus proche de la destination) donnent « au nord-est d'ici, tout près du Fumoir ». Hors ville : nom de la ville + distance BFS. XP = `QUETE_TRANSPORT_XP` (même ville) ou `× (1 + distance)`.

**Dialogue** (`services.transport.noeuds`) : `pnj.condition_ok` traite toute clé inconnue comme un **flag booléen** du contexte → conditions `transport_offert` / `transport_a_livrer` posées par le router ; `_substituer` remplace en plus toute clé de `contexte["placeholders"]` (`{destination}`, `{direction}`, `{colis}`, `{poids}`, `{delai}`, `{xp}`, `{prime}`, `{expediteur}`). Actions : `accepter`, `livrer`, `rapporter` — proposer/informer sont de simples `next` conditionnés. ⚠️ Les enseignes portent leur article (« Le Saloir ») : **jamais de préposition devant `{destination}`** (« à Le Saloir » serait fautif), toujours un deux-points. **Refus parlé** : flag `transport_mefiance` (`transport.mefiance` — magasin, aucune course écrite/en cours, `confiance_suffisante` fausse : relation sous le seuil **ou** marchandage bloqué) → choix `course_refus` des 28 marchands vers le nœud `transport_mefiance` (« je ne confie pas mes colis à n'importe qui »), sinon la sanction serait un simple **silence**, indiscernable d'un tirage négatif. Un **seul** nœud pour les deux causes → son texte parle d'**entente**, jamais d'une cause précise (il doit rester vrai dans les deux cas). **Placeholders hors course** : ils sont posés dès qu'une offre est **écrite** (`spec`), même sans course vivante — `_contexte` reconstruit alors l'aperçu par `generer_transport_authore` (déterministe) ; sans ce repli, un nœud qui ne s'affiche **qu'après** la réussite (le « vétéran » de Borin) rendrait `{destinataire}` en clair.

**⚠️ RÈGLE — un dialogue ne cite JAMAIS un nom de PNJ en dur.** Les docs `pnj:marchand_*` sont **génériques** (un par catégorie, partagé par toutes les boutiques) et **chaque lieu peut rebaptiser son tenancier** via `nom` dans son entrée `pnj` (Lucinda Mortecroix à La Flèche d'Argent, **Hermine Valcorbe** au fumoir…) : un nom écrit dans un texte mentirait. Placeholders de nom, posés par le router : **`{pnj}`** = celui à qui l'on parle (source unique **`pnj.nom_effectif(entree, doc)`** — l'entrée du lieu prime, repli doc ; c'est aussi ce que rend `pnj_payload`), **`{destinataire}`** / **`{donneur}`** = les PNJ des deux bouts d'une course (**`pnj.nom_pnj_du_lieu(lieu, get_doc, marchand_fn)`** — nomme le PNJ d'un lieu **sans y être**, 1re entrée = priorité). `{destination}`/`{expediteur}` restent les **enseignes** (lieux), `{pnj}`/`{destinataire}`/`{donneur}` sont des **personnes**. ⚠️ **Aucun pronom genré** autour d'eux : le tenancier peut être une femme.

**Mise en rayon à la livraison** : `deposer_en_rayon(dest, cargaison, get_doc_fn, rand_fn)` — chaque objet livré a `QUETE_TRANSPORT_STOCK_PROBA` (50 %) de rejoindre le `stock_vente` du destinataire, **à condition qu'il vende ce produit** (`marche.lieu_produit` : ses recettes le produisent). Un item qu'il n'achète que comme **matière première** ne monte jamais sur l'étal. Le doc `lieu` est **annexe** → persisté par `reussir_transport`, comme le doc `relation`.

**Focalisation 🎯 interdite** : `focalisation.OBJECTIFS_FOCALISABLES = ("kill","collect","visite")` + `quete_focalisable(q)` — source unique lue par `/api/focaliser` (422) et par le champ `focalisable` de `quete_detail` (les 3 rendus du bouton).

**Expiration PARESSEUSE** (aucun tick de fond n'existe dans le jeu) : `traiter_expirations(character, now, get_doc, save_doc)` appelé à `/play`, dans les **deux** branches de `move_character`, et à l'entrée du dialogue PNJ. Le doc `relation` est **annexe** (hors character) → persisté séparément, en best-effort. UI : chrono `.sh-quest-timer` dans l'onglet 📜 (deadline **locale** dérivée de `expire_at` + `now` serveur, pattern du blocage de marchandage ; `setInterval` unique, orange < 5 min) + toast d'échec (relayé par `sessionStorage` quand le changement de lieu recharge la page).

### Quêtes de « chasse » (élite à profil élevé) + rang de guilde
Objectif `chasse` : traquer et tuer **UN** ennemi d'une espèce, marqué d'un **profil élevé**, dans un lieu précis. `objectif = {type:"chasse", cible:"espece:x", lieu:"lieu:y", position:{x,y}?, profil:"profil:z", quantite:1}`. Deux canaux : (1) **tableau de guilde** (`guilde_aventurier`) → grade `max−1` ; (2) **PNJ du comptoir** (`guilde_aventurier_comptoir`) → grade `max`, comme **condition de gain de rang** (rang par cité = `lieu_parent`). Logique pure `utils/chasse.py` (DB injectée, pattern `utils/transport.py`), tests `tests/test_chasse.py`.

**Grade résolu À LA GÉNÉRATION** (`resoudre_profil_chasse`), jamais au combat : `position_de_chasse` = centre d'un placement d'une zone qui contient l'espèce (présent seulement si le lieu a une `dimensions`/grille) ; zones actives à ce point → `resolve_profil_weights` (extrait de `routers/combat.py` vers **`utils/zones.py`**, partagé) → profils **filtrés `restriction_tags ⊆ tags espèce`** (un loup sans tag `magie` ne devient jamais un profil `magie`) → niveau `max`/`max−1`, égalité `random.choice`. `profil_id` stocké dans l'objectif ; le combat l'applique tel quel.

**Application combat** (`routers/combat.py::start_combat`) : si un combat tire **naturellement** l'espèce dans le lieu **ET** que le joueur est dans la **zone 3×3** de la position (`chasse.dans_zone_chasse`, Chebyshev ≤ 1 ; sans position → contrainte de lieu seule), **UN** monstre non marqué est promu élite via **`build_monster_snapshot(espece, profil, idx)`** (extrait de la boucle d'`instantiate_monsters`, `utils/combat.py`), portant `quete_chasse=q.id` ; on ne force PAS l'apparition de l'espèce. Variante rang → `chasse_narration` sur le doc combat → **overlay pré-combat** (`combat_telluris.html`, `#chasse-overlay`). Progression : **`maj_progress_chasse`** dans `finalize_combat` juste après `maj_progress_kills` (même fenêtre d'idempotence ; seul le monstre **marqué** complète). Focalisation 🎯 = mode `kill` (biais d'espèce ; `"chasse"` ∈ `OBJECTIFS_FOCALISABLES`).

**Rang de guilde v1 = prestige/affichage seul** : `character["rangs_guilde"] = {"lieu:auxerre":"F"}` (échelle `recrutement.RANGS`, absent ⇒ F, init à la création `add_character`). Épreuve tirée à l'entrée du comptoir (`poser_rang_offert`, proba `QUETE_CHASSE_PROBA_RANG`, champ transitoire `character["rang_offert"]` — même sémantique que `transport_offert` ; `main.py` près de `poser_transport_offert`). Dialogue : service **`rang`** (`routers/pnj.py` : `_contexte` pose flags `rang_offert`/`rang_a_rapporter`/`rang_max` au comptoir ; dispatch op `accepter`→`accepter_rang` (push snapshot avec `source:"rang"`/`rang_vise`/`cite`/`narration`) / op `rapporter`→`solder_rang` : `objectif_atteint` → `promouvoir` + `appliquer_recompenses` → `quetes_terminees`). Placeholders `{espece}/{lieu}/{rang}/{rang_vise}`. Contenu `jsons/rang_guilde_a_importer.json` (Borin `pnj:borin_barbe_de_jais` — `services.rang` + choix gated ; narration « couvert du sang de ses victimes » portée par l'offre, l'espèce variant). **Toutes les quêtes générées portent `"type":"quete"`** (docs board + offre de rang + snapshot actif).

**Carte 🗺️** : `quete_detail` ajoute un champ `carte` (`_carte_chasse`) pour toute chasse **localisée** — image servable du lieu (`marche._lieu_image_route`), `dimensions`, `position`, et **`direction_texte`** « Au \<direction\> du bâtiment de la guilde » (direction PAR AXE `chasse.direction_cardinale_simple`, `y` vers le bas, depuis la **porte du donneur dans la grille de la cité** obtenue par `focalisation.charger_graphe`+`prochaine_etape` — BFS multi-hop, marche pour un comptoir imbriqué). UI (`play_town_telluris.html`) : bouton 🗺️ aux **deux** rendus (Jinja + `renderFicheQuetes`, données en `data-carte`), overlay `#quest-map-overlay` (`showQuestMap`) = **crop 6×6 de l'image du lieu centré sur la case cible** (marqueur 🎯) + la ligne d'orientation. **Limitation v1** : `position` = centre du placement de zone ; si ce centre et ses 8 voisins sont non-accessibles, le joueur ne peut pas déclencher pile dans le 3×3 (repli futur : viser une case accessible proche).

### Recrutement d'aventuriers & combat de groupe (mode opportuniste)
**Recrue = doc `aventurier:*` MIROIR du character** (mêmes champs que consomment `build_joueur_snapshot`/`compute_derived_stats`/`grant_xp`/`carried_weight` + champs propres `statut:"offert"|"embauche"|"parti"`, `giver`, `rang`, `specialite`, `exigences:{part_butin_pct, clauses[]}`, `expire_at`) → tout le moteur de combat marche dessus tel quel. Logique pure `utils/recrutement.py` (pattern quetes/transport, DB module monkeypatchable), router `routers/recrutement.py` (`GET /api/recrutement/board`, `POST …/embaucher`, `POST …/congedier` — congédier autorisé PARTOUT), tests `tests/test_recrutement.py` (35) + `tests/test_combat_groupe.py` (15).

**Tableau de recrues** : lieu recruteur = tag `"recrutement"` OU `categorie:"guilde_aventurier"` (le OU évite une migration). Offre `{nb, niveau_max}` = `RECRUTEMENT_OFFRE_PAR_SOUS_CATEGORIE[sous_categorie de la CITÉ]` (repli `defaut`), surchargée champ à champ par `lieu.recrutement_restrictions`. **Accès** : carte d'aventurier de la cité en sac (`item_ref_lieu == lieu_parent`, `RECRUTEMENT_CARTE_REQUISE` désactivable) → 403 explicite sinon. **Génération procédurale** (`generer_aventurier`) : race/sexe/voc tirés sur `rules:races`/`rules:vocations`, stats = base raciale + budget 10 pts (coût triangulaire, miroir `bonusStats`) + `RECRUTEMENT_NIVEAU_POINTS_PAR_NIVEAU`×niveau, équipement de base **équipé dans les `slots`** (`_equiper_defaut`, 1er slot compatible libre — `_weapon_attacks` ne lit que les slots), portrait par préfixe `{voc}_{sexe}_{race}` sur les 742 existants, PV/PM = max dérivés. **Rotation paresseuse** (miroir du board de quêtes, durée jittée `RECRUTEMENT_BOARD_DUREE_*`) : recrue offerte échue jamais embauchée = doc SUPPRIMÉ ; un **ancien compagnon** ré-offert qui expire repasse `parti` (son doc porte la mémoire du lien). `remplir_tableau_recrues` **ré-offre en priorité** les anciens compagnons `parti` du giver dont l'affinité ≥ `AFFINITE_SEUIL_REMISE`.

**Groupe & contrat** : `character["groupe"]` = liste d'IDS (l'état du compagnon vit sur SON doc ; `groupe_effectif` filtre statut `embauche` + `embauche_par`). Plafond `RECRUTEMENT_GROUPE_TAILLE_MAX` (2). Embauche **gratuite** ; contrat jusqu'au congédiement (+ **départ de lui-même** si affinité < `AFFINITE_SEUIL_DEPART`, check paresseux à `/play` et au board). **Exigences** : `part_butin_pct` (tirée `[MIN,MAX]`, biaisée haut avec le niveau) **prélevée sur le CUIVRE des récompenses de quête au turn-in** via le chokepoint unique `regler_part_butin` (arrondi sol, crédit au doc du compagnon, la phase 2 « salaires » s'y branchera) ; part effective réduite de 1 pt par `AFFINITE_REDUC_PART` pts d'affinité au-dessus de 50 (plancher MIN) ; `clauses` (0-2, tirées dans `CLAUSES_TYPES`) = **à ACCEPTER pour que l'embauche ait lieu** : le bouton Embaucher passe par `demanderEmbauche` (client) qui ouvre l'overlay `#clauses-overlay` — **seulement si la recrue a au moins une clause**, sinon embauche directe. ✔ Accepter → `POST /recrutement/embaucher` (inchangé) ; ✕ Refuser → `POST /recrutement/refuser` → la recrue **quitte le tableau** via le chokepoint **`retirer_du_tableau`** (extrait de `purger_recrues_perimees`, partagé avec la péremption : recrue neuve **supprimée**, ancien compagnon repassé **`parti`** — son doc porte l'affinité mémorisée), place aussitôt repeuplée par `remplir_tableau_recrues`. Le refus **ne coûte aucune affinité** (le character n'est pas muté → pas de `save_doc(character)` dans l'endpoint). ⚠️ **✕/Échap/backdrop = fermer SANS décider** : le refus est irréversible, il ne doit jamais partir d'un geste de sortie. Leur *respect* n'est toujours pas détecté en jeu (v1) : elles engagent moralement, pas mécaniquement. ### Montures de transport (étables)
Premier **moyen de transport de charge** : jusqu'ici seule la Force (`charge_max_of` = `F*5`) et les 2 compagnons augmentaient l'emport d'une expédition. Une **étable** (`categorie:"etable"` OU tag `"montures"` — `montures.lieu_vend_montures`, miroir de `recrutement.lieu_recrute`) vend des montures ; l'entrée `pnj` du lieu porte la liste `montures:[espece:*]` (`especes_offertes` = union des entrées, dédupliquée). Logique pure `utils/montures.py` (DB injectée, pattern `utils/recrutement.py`), router `routers/montures.py`, tests `tests/test_montures.py` (30) + `tests/test_combat_montures.py` (13).

**Doc `monture:*` = MIROIR du character** (comme `aventurier:*`) : `caracteristiques_current` tirées uniformément dans `espece.base_attributes`, `currentPV/PM` = max dérivés, `inventaire`/`slots`/`effets_actifs`/`combats_recompenses` → `compute_derived_stats`, `carried_weight`, `build_joueur_snapshot`, `_apply_world_turn_regen` marchent dessus **sans code neuf**. Type DISTINCT d'`aventurier` → jamais ramassé par les boucles de recrutement (board, affinités, part de butin). Appartenance = `statut:"acquise"` + `acquise_par` (pas de `user_id`), via `montures_effectives` — miroir exact de `groupe_effectif`. ⚠️ Les **`tags` d'espèce ne sont PAS recopiés** sur le doc ni sur le snapshot : plusieurs montures portent `proie`/`predateur`, qui pilotent l'IA de prédation en furtivité (elle ne scanne que `monstres`, mais un acteur rangé dans `joueurs` qui les porterait créerait une interaction qu'aucun code n'attend).

**Charge = chokepoint `montures.charge_max_porteur(porteur)`** : aiguille entre `charge_max_of` (F×5) et `charge_max_of × espece.proprietes.charge_mult` pour une monture. Multiplicateur **relu à chaud** sur le doc espèce (jamais dénormalisé). `recrutement.peut_porter` (l'admission) délègue à lui (la capacité) → **un seul endroit décide de chacun**. Étendus au même chokepoint : `_charge_view` et `_inventory_payload` (sinon le client griserait ses flèches sur 100 kg au lieu de 400). `proprietes` porte aussi `prix_cuivre` (achat via `debit_character`) — les 19 espèces `monture` sont peuplées par `jsons/montures_proprietes_a_importer.json`.

**Groupe** : `character["montures"]` est un index SÉPARÉ de `character["groupe"]`, plafond propre `MONTURE_GROUPE_MAX` (une monture n'est pas une épée : les mettre en concurrence forcerait un arbitrage absurde). Endpoints `GET /api/montures/etable`, `POST …/acheter`, `POST …/relacher` (autorisé partout, **409 si la bête est chargée** — la relâcher pleine ferait disparaître le butin en silence). **Aucun endpoint d'inventaire** : `GET /api/groupe` et `POST /api/groupe/transferer` sont porteur-agnostiques (garde factorisée `_porteur_du_groupe` = compagnons PUIS montures). Régén PV/PM au tour monde via le chokepoint existant `_apply_world_turn_groupe`.

**Combat — ciblable mais pas jouable.** `create_combat_doc(..., montures=[...])` les snapshote dans `joueurs` (donc placées, rendues, **ciblables**) avec `jouable:False`, `est_monture:True`, `deplacement:0` et `charge_max` multiplié, puis **exclut leurs ids d'`ordre_initiative`** → jamais de tour. ⚠️ **DEUX prédicats distincts, à ne surtout pas confondre** : `_joueurs_vivants` (ciblage, inchangé, inclut les montures) vs **`_combattants_vivants`** (défaite, filtré sur `jouable`). Si la défaite comptait la monture, un groupe entièrement à terre avec une bête indemne ne perdrait **jamais** et, plus personne ne pouvant jouer, le combat resterait bloqué indéfiniment (régression couverte par `test_monture_debout_n_empeche_pas_la_defaite`). À 0 PV : `morte:True` sur le snapshot, puis **`_finalize_monture`** (passe dédiée, hors de la boucle des compagnons — sinon XP + affinité + relevé à 1 PV) fait quitter le troupeau et verse la **cargaison dans `butin_disponible`** sous des ids `cargo_<snap_id>_<n>`, récupérables par l'overlay de fin (`/collect` les indexe par `monstre_id` sans exiger de monstre). Placé **APRÈS** l'affectation `butin_disponible = dispo`, qui l'écraserait. `butin_disponible` n'existant qu'en **victoire**, une défaite emporte la cargaison (prix assumé du risque). Une monture morte est exclue des bénéficiaires de `/collect`.

**UI** : bouton sidebar `🐴 Montures` (`est_etable`, `main.py`) → `#montures-panel` (clone du panneau de recrutement ; offres en lignes `.mnt-offre`, pas en cartes — on achète une espèce, pas un individu). Panneau `👥 Groupe` : les montures ferment la marche sous un sous-titre `🐴 Montures` (`_rendreCartesMontures`, cartes **non éditables** — une monture n'est pas dans `groupe_effectif`, `_acteur` refuserait son cadrage — et **non cliquables**, elle n'a pas de fiche) ; le sélecteur de sac les range dans un `<optgroup>`. Le portrait vient de l'image d'**espèce** servie par `/monsters` : `setSujet` accepte une `base` (défaut `/characters`), le serveur la fournit (`image_base`, `portraits_joueurs[].base`) — le client ne devine pas. Jeton de combat `.ally-token.monture` (anneau ocre au lieu du bleu compagnon).

### Contrôle des dialogues PNJ (linter)
Un arbre de dialogue est de la **donnée** : ni typée, ni exécutée à l'import. Un `next` vers un nœud inexistant, un nœud de service mal nommé (`services.transport.noeuds.accepte` pointant à côté) ou une condition mal orthographiée ne se voient **qu'en jouant la branche** — et un choix conditionné qui ne s'affiche jamais est indiscernable d'un tirage malheureux. D'où un contrôle préalable.

**`utils/lint_dialogues.py`** = logique PURE (aucune DB, aucun I/O), **source unique** consommée par deux appelants — même précédent que `utils/xlsx.py` : le CLI **`dev/lint_dialogues.py`** (`python dev/lint_dialogues.py [fichiers]` ; sans argument, tous les `jsons/*.json` **sauf les `telluris-dump-*` qui sont des archives d'états passés** ; sort en code 1 s'il reste une erreur) et le bouton **🔍 Vérifier les dialogues** de la carte d'import de `/admin` (`POST /admin/lint-dialogues`, admin-only, **lecture seule**, mêmes deux formats de corps que `/admin/import-bulk` → il porte sur ce que contient déjà la zone de saisie). `analyser(payload)` → `{analyses, ignores, erreurs, avertissements, trouvailles[]}` ; un doc sans bloc `dialogue` est *ignoré*, pas fautif (la plupart des docs du jeu n'en ont pas).

**Erreurs** : `noeud_depart` absent/introuvable · `next` vers un nœud inexistant · nœud **inatteignable** (ni `next` ni service n'y mène) · nœud sans aucun choix · deux choix de même `id` dans un nœud (`choix_valide` renvoie le premier, le second est mort) · nœud de service déclaré mais absent · placeholder hors liste · **condition inconnue du moteur** (un flag absent vaut False → le choix ne s'affiche JAMAIS) · **action `livrer`/`rapporter` non conditionnée** par son flag (`transport_a_livrer`…) — le PNJ proposerait « je vous apporte une livraison » à qui n'a rien à remettre · **nom de PNJ en dur dans un doc `pnj:marchand_*`** (générique : chaque lieu renomme son tenancier via `nom` dans son entrée `pnj` — cf. la règle ⚠️ du § Transport).

**Avertissements** : choix sans `next` ni `action` (ferme le dialogue comme `fin` — idiome valide, juste implicite) · nœud de service manquant. ⚠️ Le transport a **deux rôles** et presque aucun PNJ ne tient les deux : **donneur** (`accepte`/`trop_charge`, + `rapporte` si `offre.retour`) — n'importe quel PNJ peut l'être ; **destinataire** (`livre`/`incomplet`) — seul un magasin, donc en pratique un `pnj:marchand_*`. Les exiger de tous ferait crier au défaut sur un donneur correct (le réceptionniste de guilde ne reçoit jamais de colis).

⚠️ Les listes de référence (`PLACEHOLDERS_CONNUS`, `FLAGS_CONNUS`, `NOEUDS_REQUIS`, `ACTIONS_A_CONDITIONNER`) décrivent ce que `routers/pnj.py` consomme **réellement** : les tenir à jour en même temps qu'un nouveau service ou un nouveau flag, sinon le linter signalera du code correct. Le `_rev` d'un doc n'est **pas** signalé : `admin_import_bulk` réattache toujours le `_rev` courant, un `_rev` périmé est sans effet.

### Buffs de caractéristiques — chokepoint unique + « Profil modifié »
**3 sources**, toutes au même format `{buffs:{caract:Δ}, regen_pv, regen_pm, esquive}`, repliées par le chokepoint **`utils/consommables._sources_de_buffs`** (donc par `caracts_avec_buffs`/`regen_bonus`/`esquive_bonus`, donc effectives PARTOUT — fiche, exploration, snapshot de combat — sans autre code) :
- **`effets_actifs[]`** — TEMPORAIRE (consommables, sorts, compétences actives), décrémenté au tour monde.
- **`equipment_bonus`** — champ item **`bonus` = `{caract: Δ}`** (147 items en base) **+ `bonus_malus_depl`**, qui est lui aussi un **delta sur V** (données : `-1`/`-2` pour les armures lourdes) et se cumule avec `bonus.V` ; les deux sont agrégés dans `EquipmentBonus.buffs` par `recompute_equipment_bonus`. ⚠️ `compute_derived_stats` **ne soustrait plus** `malus_depl` du déplacement (`deplacement = max(1, V)`) : il est déjà dans V — le soustraire à nouveau le compterait deux fois. Le malus pèse donc désormais aussi sur l'**initiative** et le **cd**. Le champ `EquipmentBonus.malus_depl` reste exposé à titre informatif (fiche objet, marché). ⚠️ **Dénormalisé sur le perso par `utils/characters.sync_equipment_bonus(character)`, à appeler AVANT tout `caracts_avec_buffs`** (source unique : tous les appelants passent par lui, plus jamais `recompute_equipment_bonus` directement → le champ n'est jamais périmé). Distinct des `bonus_pa`/`bonus_cc`/… qui, eux, buffent les **dérivées** (pas de double comptage).
- **`competences_bonus`** — passives permanentes (`recompute_competences_bonus`).

**V est buffable comme les autres** (à son échelle 1-10 : une dague `bonus:{Ag:3,V:1}` donne +1 case de déplacement). Buffs toujours **EXCLUS** de `charge_max_of`, des plafonds/coûts d'XP et de `restriction_satisfaite` (anti-exploit) — ces trois-là lisent `caracteristiques_current` **brut**.

**UI** : les deux agrégats portent un `buffs_sources:[{nom, icon, buffs}]` (détail nommé), ce qui permet à la fonction pure **`consommables.caracts_detail(character)`** → `{code: {base, total, delta, sources:[{origine, nom, icon, delta}]}}` de ventiler par origine sans DB. Rendue dans la **2e grille « ✨ Profil modifié »** de l'onglet ⚔ (`play_town_telluris.html`, `#sh-mod-grid`, rendu 100 % client `_renderCaractsMod` → une seule valeur = la courante, delta coloré, tooltip nommant chaque source). Resync par `caracts_detail` dans les réponses de spend_xp / equip / unequip / consommer / lancer_sort / utiliser_competence / apprendre_competence / déplacement (helper `_caracts_payload`).

### Non-cumul des effets à durée
Tout s'additionnait : reboire la même potion créait une 2ᵉ entrée et les buffs se sommaient — relancer un sort de buff en boucle était un exploit sans autre frein que le coût en PM. **Deux règles, appliquées aux seuls `effets_actifs`** (l'équipement et les compétences passives restent **additifs** entre eux et s'ajoutent au résultat — un casque +2 R et un anneau +3 R font toujours +5 R). Logique pure `utils/consommables.py`, tests `tests/test_effets_non_cumul.py` (24) + volets combat dans `test_combat_effets.py`/`test_combat_debuffs.py`.

**(1) UNE SOURCE = UNE ENTRÉE.** Relancer le même sort, reboire la même potion, réutiliser la même compétence **remplace** l'effet en cours : seuls les effets du **dernier usage** comptent (durée relancée, et un lancement sans composant après un lancement renforcé **rabaisse** bel et bien le buff). Chokepoint **`poser_effet(porteur, entry)`**, par lequel passent les **quatre** writers (`consommables.empiler_effet`, `sorts.empiler_effet_sort`, `competences.empiler_effet_competence`, `combat._empiler_effet_combat`) — donc aussi les **debuffs** posés sur une cible par `_appliquer_effet_sur_cible`. Remplacement **EN PLACE** (même index) : la chip ne saute pas de rang, et le départage des ex æquo (premier arrivé) reste stable. Identité = **`cle_source(entry)`** : `sort_id` / `competence_id` / `item_id` / **`source_id`** (timbré par `identite_source(source)` en combat, où le snapshot ignore la famille de ce qu'il pose), repli `nom:<nom>`. ⚠️ Les ids CouchDB étant préfixés (`sort:`, `competence:`, `item:`), une entrée posée en combat (`source_id`) et la même relancée en exploration (`sort_id`) **se reconnaissent** — sans quoi l'effet se dupliquerait en sortant du combat.

**(2) SUR UNE MÊME CARACTÉRISTIQUE, RIEN NE S'ADDITIONNE** : **meilleur bonus + pire malus** (max des positifs + min des négatifs, +6 et −10 → **−4** — un buff ne peut pas *effacer* un malus, il le contre). Deux effets **DIFFÉRENTS** coexistent avec leurs durées propres : c'est l'**agrégation** qui tranche, donc l'expiration du plus fort fait ressortir le plus faible tant qu'il dure (+5 R/2 tours + 6 R/1 tour → +6 R puis +5 R). Même règle pour **`regen_pv`/`regen_pm`/`esquive`** (normalisées ≥ 0 ⇒ simple max). Chokepoint **`cumul_effets(effets)`** → `{buffs, regen_pv, regen_pm, esquive}`, lu par **tous** les agrégateurs : `caracts_avec_buffs` / `regen_bonus` / `esquive_bonus` (qui scindent d'abord temporaires vs permanents via **`_scinder_sources`**, l'origine étant déjà étiquetée par `_sources_de_buffs_detaillees`), et côté combat `_buffs_des_effets`, l'esquive de `_refresh_snapshot_stats` et la régén de `_tick_effets_combat`.

**UI** : `caracts_detail` pose un **`actif`** par source (un effet dominé est **listé mais marqué inactif** ; équipement et passives toujours actifs) → `_caractTooltipLignes` (`play_town_telluris.html`) suffixe « (ignoré) », sinon le joueur chercherait dans son total un Δ qui n'y est pas. **`extremes_buffs`** est exposé à part de `cumul_effets` exactement pour ça : le tooltip a besoin de savoir **qui** est retenu, pas seulement de combien.

### Effets à durée EN COMBAT
Un effet à durée est un effet à durée, **qu'il soit lancé en exploration ou en combat** — un sort « Armure de givre » (`{esquive, buffs, duree}`) était jusqu'ici refusé par `sort_utilisable_combat`, donc toute la famille buffs/régén/esquive était morte là où elle a le plus de sens.

**Le snapshot devient RECALCULABLE.** `build_joueur_snapshot` figeait les dérivées : `caracts_avec_buffs` une fois, puis `cc`/`pa`/`pv_max`/`degats_cc` dérivés — sans conserver ni les caracts de base ni l'`equipment_bonus`, donc rien n'était recalculable. Il porte désormais **`caracts_base`** (caracts + buffs **permanents** seuls : équipement + passives, via le nouveau paramètre `origines` du chokepoint `consommables._sources_de_buffs`), **`equipment_bonus`**, **`voc_niveau`**, **`esquive_base`** et une liste **`effets_actifs` VIVANTE** (copie de celle du personnage). **`_refresh_snapshot_stats(acteur)`** = chokepoint unique qui recompose `cc/cd/ag/ch/pa/pm_def/toucher_magique/degats_*/initiative/pv_max/pm_max/deplacement_base/esquive` depuis `caracts_base` + Σ buffs des effets vivants, puis re-clampe PV/PM. ⚠️ **Trois valeurs restent FIGÉES à l'entrée** : **`actions_max`** (`_refresh_actions` recalcule `actions_restantes = actions_max − Σ compteurs` → un `actions_max` mouvant offrirait des actions gratuites au cast puis un budget négatif à l'expiration), **`charge_max`** (même exclusion anti-exploit qu'en exploration) et **`attaque_profils`** (les recalculer relirait les docs d'items en base à chaque tour, pour un gain d'une case de portée de jet). Snapshot sans `caracts_base` (combat déjà en base) → la fonction sort sans rien toucher : **aucune migration**.

**Durée = TOURS DU PORTEUR.** `_tick_effets_combat(combat_doc, acteur)` est appelé depuis **`_reset_turn_budget`** (seul hook « début de tour d'acteur ») : (1) régén `regen_pv`/`regen_pm` clampée, (2) décrément + purge, (3) `_refresh_snapshot_stats`. Chaque entrée porte un **`pose_tour`** → le tick du tour de pose l'épargne, sinon un effet lancé pendant son propre tour perdrait un point avant d'avoir servi. Expiration et régén sont **journalisées** (`kind:"sys"`), sans quoi la perte d'un bonus serait invisible.

**Les effets ENTRANTS tickent aussi** : une potion bue juste avant d'entrer ne dure plus tout le combat (exploit fermé). **Les effets restants REMONTENT** : `_finalize_membre` recopie les entrées à `restants > 0` dans `doc["effets_actifs"]` (sans `pose_tour`), pour le principal **et** les compagnons — écrasement, jamais `extend` (ces entrées SONT celles du personnage, copiées à l'entrée).

**Empilement** : `_empiler_effet_combat(acteur, source, effets, tour)` produit **exactement la même forme d'entrée** que `consommables.empiler_effet` — c'est ce qui rend la remontée triviale — et passe par le chokepoint **`poser_effet`** (non-cumul : une source = une entrée, cf. § Non-cumul des effets à durée). Appelé dans les 3 branches « sur soi » de `resolve_action` (sort, compétence, consommer), toujours sur l'**acteur actif** (compagnon compris). Le test « y a-t-il quelque chose à empiler ? » est la SOURCE UNIQUE **`sorts.part_durative(effets)`** (`duree > 0` ET un bénéfice prolongé), partagée par `sort_utilisable_combat`, `competence_utilisable_combat`, `consommables.effet_instantane` et les deux `empiler_effet_*` — un critère qui divergerait entre « lançable » et « empilable » produirait un sort accepté puis sans effet. UI : chips ✨ `#joueur-effets` dans le panneau perso de `combat_telluris.html` (`renderEffetsActifs`, markup repris de `_renderEffetsActifs` de play_town). Tests purs `tests/test_combat_effets.py` (16).

### Debuffs — effets à durée sur une CIBLE ENNEMIE
Un effet à durée est un effet à durée, **qu'il soit posé sur soi ou sur l'ennemi**. Jusqu'ici `resolve_action` n'empilait la part durative que dans ses 3 branches « sur soi » : un sort « Éclat de givre » (`{degats, buffs:{Ag:-10}, duree:2}`) partait, blessait, et **son debuff disparaissait en silence** — donnée écrite, mécanique absente.

**Le monstre devient recalculable.** `_refresh_snapshot_stats` sortait sans rien faire faute de `caracts_base` : `build_monster_snapshot` porte désormais les **mêmes champs de recalcul** qu'un joueur (`caracts_base` = ses stats brutes — un monstre n'a ni équipement ni passive —, `voc_niveau`, `esquive_base: 0`, `effets_actifs: []`). Le tick, lui, était **déjà générique** : `_run_monster_turn` appelle `_reset_turn_budget(monstre, combat_doc)`, donc `_tick_effets_combat` → la `duree` compte en **TOURS DE LA CIBLE**, ce qui est la lecture attendue (« −10 Ag pendant 2 tours » = les 2 prochains tours de l'ennemi). Un combat déjà en base tourne à l'identique (pas de `caracts_base` ⇒ sortie immédiate) : **aucune migration**.

**Chokepoint `_appliquer_effet_sur_cible(combat_doc, cible, source, effets, tour)`** — miroir de la pose « sur soi » (même entrée, même `_empiler_effet_combat`, même recalcul), à trois différences : posé **seulement si le jet TOUCHE** (un sort qui se dissipe ne débuffe personne) ; **jamais sur une cible que le même coup vient d'abattre** ; **ne remonte sur aucun doc** (`_finalize_membre` ne reverse que les membres du groupe). Appelé dans les branches `cible == "ennemi"` du **sort** et de la **compétence**. Le `pose_tour` joue son rôle habituel : le debuff posé pendant le tour du joueur n'est pas décrémenté au tour d'ennemi qui suit immédiatement.

**Ciblage ALLIÉ — `cible: "allie"`.** Troisième valeur de `cible` après `soi` et `ennemi` : viser un **COMPAGNON ou une MONTURE** du groupe. `CIBLES`/`CIBLE_DEFAUT` vivent dans **`utils/sorts.py`** (source unique, `utils/competences.py` les importe, comme `JETS`) et **whitelistent** la valeur — une faute de frappe dans un doc retombe sur `soi` au lieu de créer un troisième comportement silencieux. Chokepoint **`_lancer_sur_allie(combat_doc, lanceur, cible, source, effets, portee, grid)`**, partagé par les deux branches `cible == "allie"` de `resolve_action` (sort et compétence — à cet endroit elles ne diffèrent que par le libellé). Il applique la part instantanée (`pv`/`pm`, clampée aux max **de la cible**), la part durative via `_appliquer_effet_sur_cible(..., hostile=False)` (« bénéficie de » au lieu de « subit »), et la furtivité le cas échéant.

⚠️ **Aucun jet de toucher** : un allié ne se défend pas, on ne rate pas une main tendue. `jet` (cc/cd/magique) ne concerne donc **que** les cibles hostiles. ⚠️ **Pas d'interdiction « engagé au corps à corps »** non plus — elle existe pour les effets OFFENSIFS à distance ; l'appliquer aux soins les rendrait impossibles exactement quand ils servent. La **ligne de vue** reste exigée au-delà du contact. ⚠️ **Un allié à 0 PV n'est pas visable** : le soigner le remettrait en jeu, donc changerait la condition de défaite ET l'ordre du tour — relever un compagnon à terre mérite sa propre mécanique, pas un effet de bord d'un sort de soin. Un allié hors de portée est refusé **avant** tout débit (`return` avant les PM ; le router relit le character, donc aucun composant n'est perdu).

**Montures** : ciblables comme n'importe quel allié (elles vivent dans `joueurs`), et `_finalize_monture` **reverse désormais leurs effets restants** sur le doc `monture:*`, comme `_finalize_membre` le fait pour les membres du groupe. ⚠️ Le garde-fou `est_monture` de `_refresh_snapshot_stats` prend ici tout son sens : buffer une bête ne doit pas lui rendre son déplacement.

**Exploration** (`routers/user.py`) : `sort_utilisable_exploration` / `competence_utilisable_exploration` n'excluent plus que **`ennemi`** (pas de monstre à viser hors combat) → un sort d'allié apparaît dans la fiche. Deux personnages entrent alors en jeu et **il ne faut pas les confondre** : le **LANCEUR** = `_acteur` (`compagnon_id`, la fiche ouverte) — il connaît le sort, paie les PM, fournit les composants ; la **CIBLE** = `cible_id` via **`_cible_alliee(principal, lanceur, body)`** (principal, compagnon ou monture ; preuve d'appartenance = `porteurs_effectifs`, miroir d'`_acteur`).

⚠️ **`_cible_alliee` teste le LANCEUR EN PREMIER.** `porteurs_effectifs` relit les docs en base : viser le lanceur lui-même en passant par là rendrait un **second dict du même document** → deux `save_doc` sur un `_rev` identique, donc une écriture perdue en silence. **`_save_cast(lanceur, cible, principal)`** persiste jusqu'à trois docs, dédoublonnés par **IDENTITÉ (`is`)** et non par id, lanceur autoritatif (409 — c'est lui qui a payé), le reste best-effort comme `_save_acteur`.

⚠️ **Bug corrigé au passage** : `lancer_sort` et `utiliser_competence` lisaient `get_selected_character` et **ignoraient `compagnon_id`** (le client ne l'envoyait pas non plus) — un sort lancé depuis la fiche d'un compagnon débitait les PM du **principal** et le buffait lui. Même classe de bug que le mélange des barres de slots. Les deux passent maintenant par `_acteur` + `_actionBody`.

**UI fiche** (`play_town_telluris.html`) : overlay **`#cible-allie-overlay`** (calque et briques de carte des clauses — c'est aussi une décision bloquante), alimenté par `_alliesCibles()` depuis `_grpEtat` (chargé **paresseusement** par `_assurerGroupe()` : le groupe ne l'est qu'à l'ouverture du panneau 👥). Une seule cible possible ⇒ pas d'overlay. ⚠️ **✕ / Échap / clic hors carte = ANNULER** : la cible est demandée **AVANT** l'envoi (les PM partent à l'envoi), et Échap doit **résoudre la promesse à `null`** — sinon le lancement resterait suspendu et son bouton désactivé pour toujours. Réponse : `lance`/`utilisee` portent `cible_id`/`cible_nom`/`cible_vitaux` **seulement** pour un effet d'allié → `_appliquerVitauxCible` rafraîchit la carte du BÉNÉFICIAIRE (les `vitals` de premier niveau, eux, restent ceux du lanceur). Tests `tests/test_cible_allie_exploration.py` (11).

**UI combat** (`combat_telluris.html`) : **`allyTargets(s)`** (alliés DEBOUT, hors lanceur, à portée, LoS au-delà du contact) et **`capaCibles(c)`** = source unique qui aiguille ennemi/allié, consommée par les **trois** endroits qui doivent s'accorder — case grisée (`sortCastable`/`compCastable`), jetons (`renderTokens`) et badges d'initiative (`refreshBadgeTargets`). Ciblage **VERT** (`.ally-token.spellcast`, `.init-badge.joueur.spellcast`) là où l'offensif est violet : on ne doit jamais confondre « je soigne » et « je frappe ». Les monstres sortent du ciblage pendant un cast bénéfique (pas de tir ami). ⚠️ **Une monture n'est pas dans `ordre_initiative`, donc elle n'a pas de badge** — le **jeton** est le seul canal complet. Le lanceur s'exclut lui-même côté client (un effet sur soi se déclare `cible: "soi"`) ; le serveur, lui, le tolère. Contenu : `jsons/sorts_allies_a_importer.json` (Soin du compagnon, Bénir, **Guérison des animaux** — pensé pour les montures —, Force partagée). Tests purs `tests/test_combat_allie.py` (17).

**Jet de toucher porté par la donnée — `jet` sur les sorts.** Un sort offensif se résolvait toujours sous `toucher_magique` contre la `pm_def`. Les sorts « **au toucher** » (poser la main sur la cible) demandent un jet **martial** : le champ **`jet`** des compétences (`cc`/`cd`/`magique`) est étendu aux sorts, `JETS` remontant dans **`utils/sorts.py`** comme source unique (`utils/competences.py` l'importe). ⚠️ **Le DÉFAUT diffère entre les deux familles, et c'est voulu** : une compétence est martiale par défaut (`cc`), un sort est **magique** par défaut (`JET_SORT_DEFAUT`) — sinon tous les sorts déjà en base changeraient de stat de résolution sans migration. Contrepartie assumée d'un `jet: "cc"` : il contourne la `pm_def` mais **subit les PA**, exactement comme une compétence martiale — sans quoi marquer un sort `cc` serait un pur gain. Le mode de jet ne change **que** la résolution du toucher : la part durative se pose pareil. Nouveau chokepoint **`_defense_physique(defenseur)`** = `ag + esquive`, partagé par les **trois** sites de jet martial (`_do_attack_on`, compétence, sort de contact) — les compétences ne lisaient que l'`ag`, donc un buff d'esquive sur la cible y était ignoré alors qu'il comptait face à une arme. Contenu : les 5 sorts de contact de `jsons/sorts_bataille_illusoire_noire_sainte_a_importer.json`. Tests purs `tests/test_sorts_jet.py` (13).

**Un sort/une compétence peut n'être QUE du debuff** : le garde `if not effets.get("degats")` devient `degats OU part_durative` — `dmg = 0`, ligne de log dédiée (« le sort prend »), effet posé. Rien à changer côté router : `sort_utilisable_combat` / `competence_utilisable_combat` acceptaient déjà `part_durative`, et `bool(eff["buffs"])` est vrai pour des deltas négatifs.

⚠️ **Deux garde-fous ajoutés à `_refresh_snapshot_stats`** :
- **`pv_max` planché à 1** — un debuff de R assez violent l'amenait à 0, donc `currentPV` à 0 au re-clamp, **sans lever `vivant`** : un cadavre debout que `_check_victory` ne ramasse pas et qui bloque le combat.
- **une monture garde `deplacement: 0`** — elle vit dans `joueurs` donc elle est **ciblable** ; recalculer son déplacement depuis V la remettrait en marche alors qu'elle est immobilisée par conception.

Conséquence **assumée** (déjà vraie pour les joueurs) : `pv_max = R*3 + F`, donc un debuff de **F ou de R rogne les PV courants** par le re-clamp — un debuff de constitution fait mal, ce n'est pas un bug. Restent **figés** comme pour un joueur : `actions_max`, `charge_max`, `attaque_profils`. Contenu : les 3 sorts élémentaires de `jsons/sorts_nature_elementaire_a_importer.json` (Jet d'eau, Éclat de givre, Éclat rocheux). Tests purs `tests/test_combat_debuffs.py` (16). **Hors périmètre v1** : le client n'affiche les chips ✨ que pour le joueur — un ennemi debuffé ne se voit que dans le log.

### Compétences de vocation — passives + actives (miroir des sorts)
Doc `competence:*` : `{nom, icon, description, vocation, niveau, mode:"passive"|"active", cout_pm (≥0, contrairement aux sorts), cible:"soi"|"ennemi", jet:"cc"|"cd"|"magique", portee, effets}`. `effets` = **même schéma que les sorts** (`{degats, pv, pm, regen_pv, regen_pm, buffs, duree}`). Pas de composants. Logique pure `utils/competences.py` (DB injectée).

**Choix à la création** : toute vocation **HORS `SORT_VOCATIONS_DEPART`** (complément exact, `vocation_choisit_competence` = source unique ; le client re-dérive de `SORT_VOCS`) choisit **1 compétence niveau 0** — on choisit un sort **OU** une compétence, jamais les deux. Sélecteur `#voc-comp-picker` dans l'étape 3 du wizard (`user_home_telluris.html`), miroir de `#voc-sort-picker` ; champ `characterinfo.competence_initiale`, validé serveur dans `add_character` (même dégradé gracieux : contenu non importé → création sans compétence). Champs perso : `competences_connues[]` + `competences_bonus`.

**PASSIVE = permanente.** Ses buffs/régén sont **dénormalisés** dans `character["competences_bonus"]` (pattern d'`equipment_bonus`), recalculé par `recompute_competences_bonus` à la création et à chaque apprentissage, puis replié par **`utils/consommables._sources_de_buffs`** → `caracts_avec_buffs` / `regen_bonus`. C'est le **chokepoint unique des buffs** : une passive est donc effective partout (fiche, exploration, snapshot de combat) sans autre code, et hérite des exclusions anti-exploit (pas de charge_max, ni plafonds/coûts d'XP, ni restriction d'équipement).

**ACTIVE = 1 action** (+ `cout_pm`). **Combat** : action `"competence"` (`ActionRequest.competence_id`, compteur `competences` — ⚠️ compté dans `_refresh_actions` ET remis à 0 par `_reset_turn_budget`, sinon action gratuite). Part **instantanée** (degats/pv/pm) **et** part à **durée** s'appliquent (cf. § Effets à durée en combat). Cible ennemi → jet **porté par la donnée** : `cc`/`cd` = frappe martiale (seuil `_hit_threshold` vs Ag, **PA soustraits**) ; `magique` = `_magic_hit_threshold` vs `pm_def` (**sans PA**). Portée > 1 → règles ranged (engagé interdit + ligne de vue). **Exploration** : `POST /api/utiliser_competence` (cible soi seulement, buffs → `effets_actifs`). ⚠️ **Règle de contenu** : toute active rendant PV/PM **doit coûter des PM** — il n'y a pas de cooldown, une active gratuite serait spammable à l'infini hors combat.

**Apprentissage** : `POST /api/apprendre_competence` — coût `(niveau+1)×COMPETENCE_COUT_COEFF` points, `vocations_niveaux[voc] ≥ niveau`, compétence de sa vocation, **pas de grimoire**. Onglet ⚡ de `play_town_telluris.html` (rendu client `_renderCompetences`/`_renderCompetencesApprenables`, à côté des sorts). À terme : arbre de compétences (cette étape en pose déjà le coût et l'endpoint). Contenu : `jsons/competences_niveau0.json` (20 vocations × 1 passive + 1 active) + `jsons/new_comp0.json` (furtivités + esquive). Tests purs `tests/test_competences.py` (49 tests).

**Furtivité & esquive** — deux clés d'effets **partagées sorts/compétences/consommables** (dans `_bonus_dict`/`fusionner_effets`, `utils/sorts.py`) : `esquive` (entier, malus au seuil de toucher **physique** des attaques subies — cc/cd via `_hit_threshold`, **jamais la magie** qui passe par `pm_def`) et `furtivite` (>0 = état furtif, valeur = bonus à l'Ag dans la difficulté de détection). Champ **`condition`** top-level partagé : `{"battle_map_tags": [...]}` — actif en combat seulement si intersection avec (tags battle_map ∪ `zone_tags`) ; helper `condition_remplie` ; une passive conditionnée est **exclue** du repli `competences_bonus` (évaluée au snapshot de combat seulement, `furtivite_passive`). **Esquive** : `competences_bonus.esquive` + `esquive_bonus()` (`utils/consommables.py`, somme passives + effets actifs) → snapshot `joueur["esquive"]`, appliqué dans `_do_attack_on`. **Furtivité (règles)** : jet de détection par monstre en début de son tour — seuil `50 + skill − (Ag joueur + bonus + cases × DETECTION_DISTANCE_FACTEUR)` clampé [5,95] (**malus de distance** : chaque case Chebyshev séparant les deux ajoute `DETECTION_DISTANCE_FACTEUR` points de difficulté — on repère mal de loin ; 0 = malus désactivé), `skill` = Vol du monstre, repli Int−10, repli Ag−30 (snapshot monstre porte désormais `vol`/`int`/`tags`/`detecte`) ; **réussite = détection définitive** pour le combat ; raté → le monstre **ne vient pas au joueur** : tag `predateur` → chasse la plus proche `proie` (tags d'espèce, attaque généralisée `_do_attack_on` monstre→monstre ; victime `tue_par_monstre` = **xp_reward 0 mais carcasse au butin**), sinon **errance** (`_wander_step`). **Rupture (chokepoint `_furtivite_apres_offensive`)** : le **corps à corps** révèle à tous (`_briser_furtivite` : attaque `ranged:false` — hast compris —, sort/compétence sur ennemi de portée 1, touché ou raté) ; **à distance** (attaque `ranged:true`, sort/compétence de portée > 1) la furtivité **tient** et seule la **cible** tente un jet de détection (`_tenter_detection`, même seuil, réussite définitive) — cible **déjà détectante** ou **abattue par le coup** = aucun jet, l'embuscade continue. Se déplacer/consommer/ramasser ne brise rien. **Activation** : compétence active ou sort `cible:"soi"` avec `effets.furtivite > 0` (`_activer_furtivite` : re-furtive ET remet `detecte=False` partout) ; furtivité passive posée à l'entrée du combat (`create_combat_doc(furtivite_initiale=…)`, calculée dans `routers/combat.py` contre les tags du terrain). UI : badge 🥷 dans l'en-tête de tour (état global) + **œil barré** `.ib-eye` sur chaque badge d'initiative ennemi non-`detecte` (posé par `updateInitiativeStrip`, le doc combat part brut au client). **UI combat ⚡** : bouton `#btn-comps` + `#comp-row` (sélecteur exhaustif) ; l'accès rapide passe désormais par les **slots d'action** (cf. § Barre d'action de combat) et non plus par `competences_epinglees`. Ciblage violet partagé avec les sorts (`pendingComp` miroir de `pendingSort`).

### Focalisation — 🧭 lieu / 🎯 quête
Personnage focalise **UNE à la fois** : `character["focalisation"]:{type:"lieu"|"quete", cible, posee_at}`. Logique pure (mute sans save, DB injectée). `focalisation_effective` → intention `guidage`/`kill`/`collect`. **Guidage (lieu)** : BFS graphe `connection` (cache TTL 60s) → `prochaine_etape` + direction A\* (import lazy). Payload client = `{cible_nom, etape, link_id, porte, direction|None, distance}`. **Biais (quête)** : `boost_zone_event` ×`FOCUS_EVENEMENT_MULT` poids events visés ; `espece_weights_focus` ×`FOCUS_CIBLE_MULT` tirage espèce. Carcasse (`item:<sub>` ↔ `espece:<sub>`) → boost combats source. **Effacement auto** : arrivée lieu, quête terminée/abandonnée, kill atteint, collect complété. Endpoint `POST /api/focaliser` → `{focalisation, guidage}`. UI : boutons 🧭 lieux (onglet 🤝) + 🎯 quêtes (onglet 📜), classe `.btn-highlight`, sidebar `#guidage-action`. Tests purs `tests/test_focalisation.py` (23 tests).

### PNJ de lieu — dialogues à choix + services
Un doc `lieu:*` porte `pnj:[{character:"pnj:xxx", portrait, image?, probabilite, description}]`. **Tirage de présence à l'ENTRÉE** dans le lieu (`/play` : `poser_pnj_present` + save), persisté en champ **transitoire** `character["pnj_present"]:{lieu, character|null}` → un refresh ne re-tire jamais ; re-tenter = ressortir/rentrer. Si présent : l'`image` de l'entrée remplace celle du lieu (variante avec PNJ visible, repli silencieux sur la version `_vide`), bouton sidebar 🗣. Doc PNJ **`type:"pnj"`** (`_id` préfixe `pnj:`) : `{nom, race, vocation, portrait, description, dialogue, services}`. **Dialogue** = arbre embarqué `{noeud_depart, noeuds:{id:{texte, texte_gratuit?, choix:[{id, label, next?, action:{service}?, condition?}]}}}` ; choix **filtrés serveur** par condition (`relation_min:{lieux[…OU logique], seuil}`, `intro_raison`), adressés par `choix_id`, placeholders `{prenom}`/`{cout}`. **Service soin** data-driven : `services.soin = {cout_cuivre, fraction_pv, gratuit_si:{lieux, seuil (défaut PNJ_REPUTATION_SEUIL), fraction_pv}, noeuds:{fait, sans_fonds, inutile}}` — gratuit ET plus efficace si une relation ≥ seuil ; routage des nœuds de résultat côté serveur (PV pleins = rien débité ; bourse vide = rien débité). **Service don** data-driven : `services.don = {item, quantite, cout_cuivre, gratuit_si:{lieux, seuil}, noeuds:{fait, sans_fonds, trop_charge}}` — remet un objet (ex. eau bénite du temple), gratuit si bonne réputation, sinon débit ; contrôle de **charge** avant remise (surcharge → `trop_charge`, bourse vide → `sans_fonds`). Helpers purs `don_effectif`/`appliquer_don` (miroir soin). ⚠️ `noeud_client` ne reçoit que le service **soin** → **pas de `{cout}`/`texte_gratuit` dans les nœuds de don** (texte statique). Réponse `POST /pnj/dialogue/choix` : `{don, purse, inventaire_payload}` (client `_applyInventoryPayload` rafraîchit le sac). Logique pure `utils/pnj.py` (relation_value_fn injectée) ; endpoints `routers/pnj.py` (`GET /api/pnj/dialogue`, `POST /api/pnj/dialogue/choix` — stateless, actions revalidées/débitées à l'exécution). UI play_town : panneau `#pnj-panel` (pattern quêtes), portraits servis par le mount **`/pnj`** (`templates/resources/pnj/`). Contenu : `jsons/dialogues_a_importer.json` (révérend Malakor + 2 lieux temple ; Malakor donne l'eau bénite via `services.don`). Tests purs `tests/test_pnj.py` (25 tests).
