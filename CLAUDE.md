# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Telluris est un RPG médiéval-fantastique jouable en navigateur. Backend FastAPI servant des templates Jinja2 ; base CouchDB. Pas de framework JS — tout l'interactif est du **JS vanilla embarqué dans les templates**.

## Running the app

```bash
docker compose up
```

FastAPI sur `http://localhost:8000`, CouchDB sur `http://localhost:5984`. Le compose installe les dépendances Python au démarrage du conteneur (pas d'image pré-construite).

## Running tests

```bash
python -m pytest tests/          # logique Python pure, aucune dépendance base
node dev/check_js.js             # syntaxe du JS inline de TOUS les templates/*.html
node dev/test_slots_client.js    # exécution des fonctions pures de la barre de slots
```

Les tests pytest ne couvrent que la logique pure (stats, combat, marché/recettes, consommables, sorts, quêtes…). Les deux harnais Node sont **sans aucune dépendance** (ni `package.json`, ni second écosystème à entretenir) et sortent en **code 1** en cas d'échec.

- `check_js.js` neutralise les expressions Jinja avant de passer le code au parseur de Node — ⚠️ en `(0)` et non `0`, sinon `{{ liste | tojson }}.forEach(...)` deviendrait `0.forEach(...)`, faux positif garanti.
- `test_slots_client.js` extrait les fonctions **pures** du template (par nom, accolades équilibrées) et les exécute dans un contexte `vm` : il ferme la classe de bug « à qui appartient ce que j'affiche et ce que j'écris ? », qu'aucun test pytest ne peut atteindre. **Hors de portée sans jsdom** : rendu DOM, clic long, ordre inversé en mobile — à vérifier en jeu.

**Environnement local de l'agent** : Node dans `C:\Program Files\nodejs\`, Python dans `C:\Python314\`. ⚠️ Les deux peuvent être **hors du `PATH`** — appeler Node par son chemin complet (`"/c/Program Files/nodejs/node.exe"` depuis Bash) et pytest par `python -m pytest` (l'exe vit dans `~/AppData/Roaming/Python/Python314/Scripts`, hors `PATH`). Dépendances nécessaires **rien que pour collecter** les tests purs (ils importent `utils/*` → `routers/*`) : `pytest` + la ligne du `docker-compose.yml` **sans `uvicorn` ni `Pillow`** (`fastapi Jinja2 couchdb2 bcrypt pyjwt[crypto] authlib httpx itsdangerous`). CouchDB est injoignable en local : `db/config.py` tolère l'absence de connexion à l'import (`server`/`db` = `None`, les helpers renvoient `None`) pour que les tests purs se collectent. Docker et l'app tournent côté utilisateur.

## Inspecting live DB values

La CouchDB live tourne sur un hôte distant, généralement NON joignable en local. Pour connaître les valeurs réelles des documents (races, espèces, profils, lieux, items…), lire le dump JSON committé à la racine : **`telluris-dump-*.json`** (produit par `GET /admin/exports/couchdb` / `db.config.dump_all_docs()`). Objet `{"db","exported_at","doc_count","docs":[...]}` ; `docs` exclut les `user:*`. Repérer un doc par grep sur `"_id": "rules:races"`.

- **Export ciblé d'un type** : `GET /admin/exports/by-type?type=<type>` (`find_docs({"type": t})`, `user:*` exclus) → `<type>-AAAAMMJJ-HHMMSS.json` ; la page `/admin/exports` liste les types présents en base.
- **Édition en tableau** : `/admin/table` (`admin_table.html`, carte « Mise à jour en tableau » dans `/admin`) liste les docs d'un type en tableau (colonnes choisies/ordonnées par drag, triables, filtrables, redimensionnables) ; cliquer une ligne ouvre le JSON dans un overlay fixe à droite. **Save** = `PUT /admin/doc` / **Cancel** ferme / **Delete** = `DELETE /admin/doc?id=…` après `confirm()`, la ligne étant retirée localement sans rechargement du type. ⚠️ Le `_rev` est **relu en base**, jamais celui du client ; `db.delete_doc` renvoyant `None` succès comme échec, le serveur vérifie par relecture → 409. Données : `GET /admin/table/data?type=<t>`. Préférences d'affichage (colonnes/ordre/tri/filtres/largeurs) mémorisées **par type** dans `localStorage` (`telluris.admin_table.v1.<type>`).
- **Export du tableau** : deux boutons au-dessus exportent les lignes **actuellement affichées** (filtres+tri, `computeVisibleRows`) — **⬇ Export JSON** (docs complets) et **⬇ Export Excel** (`POST /admin/table/export.xlsx` → writer OOXML partagé `utils/xlsx.py`, une colonne par clé de 1er niveau, valeurs imbriquées en JSON). Nom commun `exportFilename(ext)` = `<type>_filtre_<col>_<val>…_AAAAMMJJ-HHMMSS.(json|xlsx)`, horodatage **UTC** aligné sur les exports serveur (`datetime.utcnow()`).

## Conventions transverses

Onze règles qui valent **partout** ; les sections suivantes ne répètent que ce qui leur est propre.

**1. Chokepoint `_acteur(current_user, body)`** (`routers/user.py`) → `(porteur, principal)`. Sans `compagnon_id` les deux sont le même dict (un seul `save_doc`) ; avec, le porteur est le doc `aventurier:*` ou `monture:*`. ⚠️ Ces docs **n'ont pas de `user_id`** : leur seule preuve d'appartenance est le statut + le lien vers CE personnage (`embauche`/`embauche_par`, `acquise`/`acquise_par`) via `groupe_effectif`/`montures_effectives` → **403** sinon. Côté client, **`_actionBody(extra)`** injecte le `compagnon_id`. Sauvegarde multi-docs **`_save_acteur`** : porteur **autoritatif d'abord** (409), le reste best-effort. ⚠️ **Toute action doit porter le `compagnon_id` de l'ACTEUR COURANT** — `_acteur` retombe **silencieusement sur le principal** quand le corps n'en porte pas, ce qui écrit sur le mauvais doc *et* renvoie l'état du mauvais doc, que le client affiche comme celui du compagnon. Les deux états finissent durablement mélangés. C'est la classe de bug la plus coûteuse du projet.

**2. Modules purs `utils/*`** : DB injectée (`get_doc_fn`/`save_doc_fn`/`find_docs`), **mutent sans sauver** (l'appelant persiste), testés sans dépendance base. Un helper partagé par plusieurs routers vit dans `utils/`, **jamais dans un router** — `routers/recrutement` importe `routers/user`, donc l'inverse créerait un cycle.

**3. Anti-exploit des buffs** : `charge_max_of`, les plafonds et coûts d'XP (`compute_stat_cap`, `compute_xp_cost`) et `restriction_satisfaite` lisent `caracteristiques_current` **BRUT**. Un buff n'ouvre jamais un plafond, n'abaisse jamais un tarif, ne débloque jamais une arme.

**4. Aucune migration de base.** Champ absent ⇒ comportement d'avant ; quand une forme neuve est nécessaire, elle est reconstruite **À LA LECTURE** (`slots_effectifs`, `_slots_derives`, replis `.get(..., 0)` sur les snapshots de combat). Un doc déjà en base doit toujours continuer de tourner.

**5. Péremption et vérification PARESSEUSES** — **aucun tick de fond n'existe dans le jeu**. Tout ce qui expire est contrôlé au passage : tableaux de quêtes et de recrues (`purger_*`), délais de course (`traiter_expirations`, appelé à `/play`, dans les **deux** branches de `move_character` et à l'entrée du dialogue PNJ), départs volontaires de compagnons, laissez-passer.

**6. Champs transitoires du personnage** : `pnj_present`, `transport_offert`, `rang_offert`, `ressource_recoltable`, `objets_au_sol`. Même sémantique — tirés à l'**ENTRÉE** dans le lieu et persistés, donc un refresh ne re-tire pas ; ressortir/rentrer re-tire ; vidés dès un déplacement réel.

**7. Porteurs vs membres — deux listes à ne pas confondre.** `recrutement.porteurs_effectifs(character, get_doc)` = SOURCE UNIQUE de « qui **porte** pour moi » (`groupe_effectif` + `montures_effectives`, compagnons d'abord). `expedition.membres(character, get_doc)` = qui **agit** (principal EN TÊTE puis compagnons) — ⚠️ **JAMAIS de monture** : une bête porte le butin, elle ne négocie pas et ne manie pas une hache. L'ordre compte : plusieurs appelants départagent les ex æquo par « le premier gagne », et c'est le joueur qui doit gagner.

**8. Overlays de décision bloquante** (`#clauses-overlay`, `#engagement-overlay`, `#max-bonus-overlay`, `#cible-allie-overlay`) : ⚠️ **✕ / Échap / clic sur le backdrop = ANNULER sans rien engager** — une décision irréversible ne doit jamais partir d'un geste de sortie. Quand un appel attend la réponse, l'annulation doit **résoudre la promesse à `null`**, sinon le lancement reste suspendu et son bouton désactivé pour toujours.

**9. XSS — on BORNE au serveur, on ÉCHAPPE au rendu.** Les helpers de nettoyage serveur (`recrutement.nettoyer_nom_compagnie`…) valident et bornent mais **n'échappent pas le HTML** (double échappement sinon) ; le client a son `escapeHtml`, obligatoire dès qu'une chaîne saisie par le joueur part dans un template literal `innerHTML`. ⚠️ **Jamais dans un `onclick="…('${x}')"`** (`'` → `&#39;` casserait la chaîne JS) : lire la valeur depuis l'`<input>` en JS. ⚠️ **Jamais pour `showToast`**, qui écrit en `textContent`.

**10. Resync de payload.** Tout endpoint qui bouge un état doit **renvoyer le bloc correspondant recalculé** (`slots`, `relations_lieux`, `caracts_detail`, `inventaire_payload`, `links`…). Le client ne reconstruit jamais un état lui-même ; sans le bloc, l'onglet reste figé sur l'état du dernier chargement de `/play` — symptôme classique et difficile à relier à sa cause.

**11. Import de contenu.** Les docs de contenu vivent dans `jsons/*_a_importer.json`, chargés par la carte d'import de `/admin`. ⚠️ **`admin_import_bulk` fait un PUT COMPLET, jamais un merge** : éditer un champ oblige à reproduire tout le doc — d'où les générateurs `dev/gen_*.py`, qui relisent les docs depuis le **dump** (source unique) et n'y injectent que le champ ajouté, ce qui rend la régénération **idempotente** (une retouche faite à la main en base survit, réimporter ne peut rien annuler en silence). Le `_rev` d'un doc importé est sans effet : il est toujours réattaché depuis la base.

## Core Design Patterns

### CouchDB document IDs
Pattern `type:identifier` — `user:email@example.com`, `lieu:lutecia`, `rules:races`. Personnages = `character:<user_id>_<uuid>`.

### Derived stats are never stored
`DerivedStats` recalculées par `compute_derived_stats()` à chaque requête. Ne jamais persister une valeur dérivée.

### Character document vs. Pydantic model
`models/character_document.py` = spec de référence. **Vérité = le code de création dans `routers/user.py`.** Les noms de champs diffèrent : `voc`, `sex`, `caracteristiques_standard`/`current`, `cite`.

## Core Mechanics

### Échelle des caractéristiques (×10, sauf V)
7 caractéristiques à l'échelle ×10 (F/R/Ag/Vol/Int/Cha/Ch ≈ 10-100). V = 1-10 (base raciale ~4-5, max ~7-8), `deplacement = V` cases/tour. Formules (joueur **et** monstres) : `cc = (F + Ag*3)//4`, `cd = (Ag*3 + V*10)//4`, `initiative = (Ag + V*20)//3`, `actions_max = max(1, ceil(Ag/40 + V/2))` → **Ag est la god-stat**.

### Plafonds de caractéristique — quota racial + dépassement
`compute_stat_cap` (`models/character_stats.py`) donne le plafond effectif d'une caract. Trois cas : (1) **quota non plein** → `stats_max` racial ; (2) **quota plein** (`nb_max_accessibles`, défaut 3, caracts déjà au max racial) → **sous-plafond** `stats_max − 10` (`−1` pour V) ; (3) **bonus de dépassement engagé sur CETTE caract** → `stats_max + max_bonus[caract]`, qui prime sur tout le reste.

**Le dépassement est un trait de DONNÉE, pas de code** : une race le porte via `max_bonus:{caract:Δ}` sur `rules:races` (seul l'**humain** l'a : `+10`, `+1` pour V). **Unique et irréversible** par personnage : `character["max_bonus_used"]` mémorise la caract choisie (absent ⇒ jamais utilisé, aucune initialisation à la création). `POST /api/spend_xp` prend un booléen **`use_max_bonus`** — 422 si déjà consommé ou si la race n'a pas de bonus —, arme le plafond **avant** de valider la montée, puis persiste le champ. ⚠️ Le bonus ouvre le **plafond**, jamais le **tarif** : `compute_xp_cost` est inchangé. Passe par `_acteur` ⇒ un **compagnon** humain y a droit, sur SON doc.

**Payload** : `utils/fiche.bloc_fiche` publie `max_bonus` + `max_bonus_used` à côté de `stat_caps` (source unique ⇒ contexte `/play` **et** fiche de compagnon, qui ne reçoit pas `race`) ; `spend_xp` renvoie `max_bonus_used`.

**UI** (`play_town_telluris.html`, onglet ⚔) : bouton `✦ Dépasser +Δ` (`.sh-bonus-btn`, violet pour ne pas se confondre avec le doré du bouton d'XP) offert sur les seules caracts **BLOQUÉES** (`val >= cap` : au max racial, ou coincées au sous-plafond par le quota), tant que le bonus est libre. Il ouvre `#max-bonus-overlay`, qui appelle `spendXp(code, true)`. ⚠️ Le bouton est rendu **même quand il n'est pas offert**, en `display:none` : une caract peut se bloquer en cours de session (montée au max, ou quota qui se remplit et rabaisse un autre plafond) et `_refreshStatBoxes` l'allume par `getElementById` — sans l'élément, il n'aurait rien à allumer ; son `onclick` est donc posé en JS, pas seulement en Jinja.

⚠️ **Jauge : l'échelle et le repère sont DEUX valeurs distinctes.** `échelle` (100 % de la barre) = `max(maxRace, cap)`, sans quoi le remplissage déborderait une fois le plafond dépassé. Le **pip** = `min(cap, maxRace)` : il reste **planté au max naturel de la race**, c'est le repère que le remplissage doit visiblement franchir ; il ne descend en dessous que sous l'effet du quota (`.subcap`, grisé). Les faire bouger ensemble (pip = cap) rend le dépassement **invisible**. Trois sites à tenir d'accord : le rendu Jinja (`echelle`/`pip_val`), `_refreshStatBoxes` et `_renderCaractsMod` (qui réécrit la même largeur de remplissage depuis le total buffé).

### Navigation bitmask
8 directions via le dict `nav` (bit 1=HAUT, 2=HAUT_DROITE, …, 128=HAUT_GAUCHE). `VALID_MOVES` (source unique, `utils/lieux.py`) → `MOVE_OFFSETS`. **Le combat partage** : `_find_path` (A*) et `_reachable_region` (flood fill) utilisent les mêmes directions + `nav_allows`. ⚠️ **Pas 4 directions** (îlots diagonaux). `create_combat_doc` : `grid = {dims, cells, nav}` — sans `nav`, placement ≠ déplacement.

### Références d'items & poids
Entrée d'inventaire = **string legacy** `"item:xxx"` (poids = min) **ou objet** `{"item": "item:xxx", "poids": <nb>}`. Le champ `poids` d'un doc `item:*` est un nombre OU `[min,max]`. Helpers : `item_ref_id`, `poids_bounds`, `item_ref_weight`, `resolve_item_ref`. ⚠️ Les actions client adressent par **index + item_id** : deux instances d'un même item peuvent peser différemment.

Une référence peut porter **`lieu_parent`** = le lieu qui a délivré CET exemplaire (`item_ref_lieu`) : le doc item reste **générique** (une seule `item:carte_aventurier` pour toutes les guildes) et `resolve_item_ref` — chokepoint d'affichage, le client ne rend que `nom` — en dérive le label « Carte d'aventurier (Auxerre) » (`item_label`). ⚠️ Jamais de `lieu_parent` sur le doc item lui-même.

### Charge & surcharge
`charge_max_of(character)` = `F*5` (dérivée, jamais stockée). `carried_weight(character)` somme l'inventaire **+ les équipés** (pas le sol). En **exploration**, `carried_weight > charge_max` bloque le déplacement (garde 409 dans `move_character`, flèches désactivées côté client) ; au pickup, le dépassement fait tomber des items **aléatoires** au sol. En **combat**, au-delà de la **demi-charge** le déplacement est divisé par deux.

### Combat & butin (`utils/combat.py` + `routers/combat.py`)
Un combat est un doc `combat:*` (snapshots `joueurs[]`/`monstres[]`, `ordre_initiative`, `battle_map_id`). Les **stats dérivées des monstres** viennent de `espece:*` (min/max) modulées par `profil:*` (niveau, deltas). `finalize_combat()` applique XP/PV **et** le butin ramassé en combat de façon **idempotente atomique** (id du combat dans `character["combats_recompenses"]`, même doc que l'XP).

Le butin de victoire n'est **jamais** auto-ajouté : `butin_disponible` (poids tiré au niveau du profil via `random.choices`) est proposé dans l'overlay et encaissé par `POST /api/combat/{id}/collect`, borné par `charge_max`. Carcasses = `item:<sub_id>` (1-pour-1 avec `espece:<sub_id>`), créées à la volée si absentes.

### Attaques par mode — corps à corps / jet / tir
Mode déterminé par tag : `tir` (arcs), `jet` (lancer), sinon **cac** (hast = cac de `portee ≥ 2`). Champs item : `portee` (défaut 1), `restriction:{caract:min}` (ET logique) → `restriction_satisfaite`, blocage dur d'`equip_item` (422).

`_weapon_attacks` produit `joueur["attaque_profils"]` (1 par mode, meilleure portée ; poings portée 1 toujours présent). Chaque profil : `mode`, `portee`, `ranged`, `toucher` (cc/cd), `degats` (cc/cd). **cac** = cc/F, portée item ; **jet** = cd/F, portée `item + F//JET_PORTEE_F_DIV` ; **tir** = cd/Ag, portée item. `resolve_action` sélectionne le profil.

**Règles ranged** : interdit si engagé (1 case), exige une ligne de vue (Bresenham `seeThroughCell` — falaise transparente, mur seul bloque —, `nav` ignoré). Monstres = mêlée seule.

**UI** : chaque mode est une **entrée assignable** de la barre de slots (`{type:"attaque", ref:"cac"|"jet"|"tir"}`) — pas de sélecteur de mode ni de boutons d'attaque fixes. ⚠️ Une case d'attaque **garde sa position et se grise** quand le mode n'est pas équipé (`modesEquipes`) ou n'a aucune cible (`targetableMonsters(mode)`) : la faire disparaître décalerait les cases voisines d'une arme à l'autre, ruinant la mémoire musculaire. `triggerAttack(mode)` fixe `currentMode` puis attaque directement (1 cible) ou ouvre le sélecteur de cible (les cases d'attaque s'effacent en `visibility` via `.hidden-selecting`, la grille gardant sa forme). Les **badges du bandeau d'initiative** (`.init-badge.monstre`) servent aussi de ciblage — bordure grise hors portée, **rouge + cliquables** uniquement quand attaquables (tour + action + portée, `refreshBadgeTargets`), miroir du clic sur `.monster-token.adjacent`.

**UI panneaux combat** (`combat_telluris.html`) : panneau perso repris du `<section class="character-panel">` de play_town — portrait recadré (`#left-portrait.pt-crop` via `applyPlayerPortrait`, carré, barres PV/PM verticales), identité, pips d'actions + jauge de charge. Vie des ennemis = **anneaux PV** sur les badges du header (`setRing`/`MONSTER_CIRC`) + grand portrait du dernier ciblé. Carte iso : `MAX_H`=10 rangées, `--step` borné à la **seule largeur** (`max(8, w/17)`) → hauteur agrandie sans toucher la largeur, page défilable.

### Barre d'action de combat — slots configurables
Un **nombre FIXE de cases** dont le joueur décide une à une du contenu. La barre est le **seul accès** aux sorts, compétences et consommables : ce qui n'a pas été préparé ne se joue pas, sauf à passer par ⚙ en plein combat, au prix d'une action. Logique pure `utils/slots_actions.py`.

**Mise en page par WRAP, pas par grille figée** (`.slot-grid` = `flex` + `flex-wrap`) : la case vaut `clamp(28px, (100% − 45px)/10, 46px)`, soit 1/10 du conteneur plafonné à 46 px. Sur téléphone (~390 px) cela fait exactement **10 cases par rangée** ; au-delà d'environ **1015 px les 20 tiennent sur une ligne**. Aucune media query de mise en page — la largeur de la case suffit à décider ; les tailles intermédiaires wrappent librement (assumé).

**Champ `character["slots_actions"]`** = liste **dense positionnelle** de longueur `COMBAT_SLOTS_MAX` (index 0 = slot 1), trous = `None`. Entrée = `{"type", "ref"}` : `attaque` (ref ∈ `cac`/`jet`/`tir`), `sort`, `competence` (ACTIVE seulement), `consommable`, `ramasser`, `fuir`. Porté aussi bien par `character:*` que par `aventurier:*` — **chaque membre du groupe a SA disposition**, rechargée au changement de tour.

Une entrée de **sort** porte en plus **`composants` (bool)** : engager ou non les composants **CONSOMMÉS**. ⚠️ Les **catalyseurs** (`consomme:false`) sont **toujours** engagés — ne rien dépenser pour s'en priver n'aurait aucune contrepartie —, le flag ne les concerne pas. Défaut **`True`**, posé par `normaliser_entree` : une entrée héritée de la migration est **égale** à `composants:true` au sens de `_memes_entrees` → déplacée, jamais dupliquée. `true` et `false` sont en revanche **deux entrées distinctes** : le même sort peut occuper deux cases, une qui dépense et une qui économise. Le badge **`+`** s'affiche ssi le flag est posé **ET** qu'il reste un composant consommable disponible — calcul **CLIENT** depuis `SORTS`, resynchronisé après chaque lancement : `slots_payload` n'expose que le réglage, pas la disponibilité, qui serait périmée dès le premier cast.

⚠️ **Un consommable est référencé par `item_id` (le TYPE), jamais par index d'instance** : le sac bouge à chaque ramassage, un index serait périmé au tour suivant. Le pont vers l'API de combat (qui exige `index + item_id`) se fait dans `slots_payload`, qui **résout l'index du premier exemplaire à chaque rendu** — jamais persisté. Sac vide ⇒ la case **reste** et se grise (racheter des potions ne doit pas obliger à reconfigurer la barre).

⚠️ **INVARIANTE — trois actions obligatoires** (`ENTREES_OBLIGATOIRES` : mêlée `cac`, `ramasser`, `fuir`), présentes **exactement une fois chacune**, à n'importe quelle position : elles se **déplacent** librement mais ne se **retirent** pas — une barre sans bouton de fuite enfermerait le joueur dans le combat. L'invariante est réparée **À LA LECTURE** (`slots_effectifs` → `_reparer_obligatoires` : doublons effacés, manquantes replacées dans la première case libre, en dernier recours en écrasant la dernière case), pas seulement à l'écriture — un doc bricolé à la main ne peut pas la violer. Conséquences : `vider_slot` **refuse** (422) sur une obligatoire ; `poser_slot` **déplace** une obligatoire déjà placée ailleurs au lieu de la dupliquer, et **échange** les deux entrées si la case cible en portait une (sinon déposer un sort sur 🏃 la supprimerait, et la réparation la remettrait ailleurs à l'insu du joueur).

**Champ absent ⇒ migration à la lecture** : le socle **`ENTREES_DERIVEES`** — ⚔🫳🏃 aux slots 1-2-3 **puis 🪃🏹 en 4-5** — puis `sorts_epingles_effectifs` et `competences_epinglees_effectives` à partir du slot 6 (`_slots_derives`). ⚠️ Les trois modes d'attaque doivent être dérivés, pas seulement la mêlée : un archer se retrouverait **sans case 🏹**, invisible, puisque le seul geste qui pourrait l'ajouter est le mode ⚙, qui coûte une action. Jet et tir restent **optionnels** (hors `ENTREES_OBLIGATOIRES`) : une fois la barre configurée, ils se retirent comme n'importe quelle case. Les deux helpers d'épinglage survivent uniquement pour alimenter cette migration.

**Endpoints** (`routers/user.py`) : `POST /api/slot_action {position, entree|null}` (poser/vider) et `POST /api/slot_deplacer {source, cible}` (échange — **seul geste capable de bouger une obligatoire**, d'où l'échange plutôt que l'écrasement). Les deux renvoient `{slots}` **recalculé**. Payloads : `slots`/`slots_max` dans le contexte `/combat/{id}` (`main.py`) et `GET /api/combat/{id}/acteur` ; ⚠️ **`barre_slots`/`barre_slots_max`** dans `utils/fiche.bloc_fiche` — la clé `slots` y désigne déjà l'**ÉQUIPEMENT** du compagnon (`_recrue_view` fusionne le bloc), l'écraser viderait son paperdoll.

⚠️ Côté combat, `acteurCompagnonId()` résout l'acteur **à chaque appel** (jamais figé) depuis `activePlayer(state).character_id`, comparé à `SERVER_DATA.character_id`. Le repli pendant un tour de monstre doit rester cohérent des deux côtés : le client replie sur `joueurs[0]`, le serveur sur `combat["character_id"]` — `create_combat_doc` construisant `joueur_0` depuis le principal, les deux désignent le même personnage.

**UI combat** : `renderSlots()` ; `activerSlot(slot)` **aiguille seulement** — toute la logique (cast direct vs ciblage violet, portée) reste dans `triggerAttack`/`startSortCast`/`startCompUse`/`doAction`, `slotComposants` décidant seulement de ce qui est engagé. `slotJouable` pilote `updateButtons` en réutilisant tels quels `sortCastable`/`compCastable`/`canLoot`/`canConsume`/`targetableMonsters`. `#target-row` sert à la sélection de cible d'une attaque. **Mobile** : ordre **totalement inversé 20→1** pour amener le slot 1 sous le pouce — deux variables CSS posées par case (`--o` desktop, `--o-rev` mobile) plutôt qu'un recalcul au `resize`.

**Glisser-déposer = CLIC LONG, gratuit, hors mode ⚙** (`attacherDragLong`, ~400 ms) : Pointer Events et non drag & drop HTML5, qui **ne fonctionne pas au doigt**. Un mouvement > 10 px avant l'armement annule (c'est un défilement) ; `touch-action:none` sur la case empêche le défilement de voler le geste ; un drapeau `dragJustEnded` **avale le `click` qui suit**, sinon relâcher déclencherait l'action de la case. Réordonner sa barre sous le feu est libre — seul changer le **contenu** d'une case coûte.

⚠️ **Entrer en mode ⚙ coûte UNE ACTION** (action de combat `editer_barre`) ; les modifications qui suivent et la sortie sont gratuites. Trois points dans `utils/combat.py`, comme les compteurs existants : `_refresh_actions` additionne `editions`, **`_reset_turn_budget` le remet à zéro** (sans quoi l'édition serait gratuite dès le 2ᵉ tour — même piège que `competences`), et la branche `editer_barre` incrémente + journalise. Le moteur ne débite que le **temps** : le contenu des cases reste écrit par `/api/slot_action`, qui ignore tout du combat. La garde `actions_restantes <= 0` en tête de `resolve_action` interdit d'entrer sans action. ⚠️ Côté client, `doAction` **retourne son `data`** et `toggleSlotEdit` teste **`action_result.error`** : un refus du moteur revient en **200**, pas en 4xx — tester `res.ok` seul ouvrirait le mode sans avoir payé. Cas limite assumé : entrer avec exactement 1 action restante **termine le tour**. `#btn-slot-assign`/`#btn-slot-done` sont réactivés explicitement par `updateButtons` — ce sont des `.action-btn`, que `doAction` désactive en bloc.

**UI fiche** (`play_town_telluris.html`, onglet ⚡) : grille éditable `#sh-slot-grid` (même clic long, `_attacherDragLong`) + un `<select class="sh-slot-select">` par compétence active / consommable de combat, **et par mode d'attaque optionnel** (section `#sh-modes-attaque`, `_renderModesAttaque` appelée par `_renderBarreSlots` → resync à chaque écriture) : ⚔ n'y figure pas (obligatoire, donc toujours posé), 🪃 et 🏹 s'y assignent **sans avoir l'arme en main**. Un **sort à composants consommables porte DEUX sélecteurs** (sans `+` / avec `+`). Configurer y est **toujours gratuit** — le coût en action ne concerne que le mode ⚙ du combat. ⚠️ Deux collisions de noms à ne pas rejouer : les globales sont préfixées **`_barreSlots`** (`_slots` = slots d'ÉQUIPEMENT du paperdoll) et les classes CSS **`.sh-barre-*`** (`.sh-slot` = emplacement d'équipement de la silhouette ; réutiliser ce nom faisait fuir `aspect-ratio`/curseur/police sur le paperdoll).

### Critiques pilotés par la Chance
Tout jet d100 offensif (arme cac/jet/tir, sort, compétence quel que soit son `jet`, attaque de monstre y compris monstre→monstre) passe par **deux helpers uniques** de `utils/combat.py` :

- **`_seuils_critiques(attaquant, defenseur)`** → `(seuil_reussite, seuil_echec)`. `delta = Ch_att − Ch_cible`, les **deux** fenêtres glissent de `delta // CRIT_CHANCE_DIVISEUR` : la chance élargit la réussite critique ET repousse l'échec, **symétriquement**. Les world-vars `CRIT_REUSSITE_MAX` (5) / `CRIT_ECHEC_MIN` (96) restent des **garde-fous bornants** (`max(base_ok, …)` / `min(base_ko, …)`) → le glissement ne peut que jouer en faveur du plus chanceux ; un jet ≤ 5 est toujours un crit, un jet ≥ 96 toujours un fumble. `CRIT_CHANCE_DIVISEUR = 0` désactive tout.
- **`_resoudre_jet(attaquant, defenseur, seuil)`** → `{roll, seuil, touche, critique, fumble, mult_degats}`. ⚠️ Le **critique PRIME sur le seuil de toucher** : une réussite critique touche même si le seuil était raté, un échec critique rate même si le seuil passait.

**Réussite critique = dégâts ×2**, multiplicateur appliqué **AUX DÉS, avant la soustraction des PA** (`roll_dice(...) * mult - pa`) : le crit double le coup, pas la pénétration d'armure. La magie n'ayant pas de PA à soustraire, le ×2 y joue seul.

**Échec critique = une action de plus perdue** (`_appliquer_fumble`). ⚠️ `actions_restantes` n'est **jamais décrémenté**, il est **recalculé** par `_refresh_actions` depuis des compteurs → une pénalité DOIT être un compteur (poser `actions_restantes = 0` serait écrasé au prochain refresh). Deux champs : **`penalites`** (compté dans `used`, remis à zéro au reset de tour) et **`dette_actions`** (ce qui n'a pas pu être payé faute d'action restante, **survit au reset** : `_reset_turn_budget` le convertit en `penalites` du nouveau tour puis l'efface). `penalites` entre aussi dans les **projections de déplacement** (`projected > actions_max`), sinon un fumble serait indolore pour qui se contente d'avancer. Un perso à `actions_max == 1` qui fumble perd tout son tour suivant (assumé).

⚠️ **`_do_attack_on` décompte l'action de l'attaquant lui-même** (`attaques += 1` + `_refresh_actions`) plutôt que de laisser ses appelants le faire après coup : le test de fumble a besoin d'un budget déjà à jour. Aux 3 sites joueur, `_appliquer_fumble` est appelé **après** l'incrément du compteur d'action.

Snapshots : `ch` porté par les **deux** constructeurs (`build_joueur_snapshot` = valeur **avec buffs**, `build_monster_snapshot`), tous les accès en `.get("ch", 0)`. ⚠️ **Données** : beaucoup d'`espece:*` ont encore `Ch = {min:0, max:0}` → delta large en faveur du joueur, à peupler. Log : `kind` **`crit`** (raffiné `j-crit`/`m-crit` côté client, la classe brute `crit` servant au rendu Jinja initial qui ne connaît pas cette bascule) et **`fumble`**.

### Monnaie & marché
3 paliers : Or/Argent/Cuivre (1 or = 100 ag = 10 000 cu). Helpers : `money_to_cuivre`, `cuivre_to_purse`, `credit_character`/`debit_character` (mutent, **sans save**).

**Éligibilité marchand** : `lieu_buys(lieu, item)` = sous-catégorie de l'item ∈ recettes du lieu OU produit du lieu (rachat ≤ pmin ≤ achat). `params_vente_lieu` = source unique des prix.

**Vente des objets du groupe** : `_marchand_vendables(character, lieu, relation, porteurs_tiers)` agrège le sac du principal PUIS de chaque porteur — compagnon **ou monture** (une bête de somme est là pour rapporter du butin lourd : ce qu'elle porte doit être vendable sans transfert préalable). Chaque entrée porte `compagnon_id` (None = principal) + `porteur_nom` + `porteur_icon`. Les 4 endpoints du marchand (`marchand_quotes`, `sell_item`, `buy_item`, `marchander_item`) passent **`recrutement.porteurs_effectifs`** — ⚠️ les quatre, sans exception : en utiliser un autre à un seul endroit fait **disparaître de la liste de vente** les objets portés par une monture. `sell_item`/`marchander` passent par `_acteur` → l'objet quitte le sac du **porteur** mais **l'argent va TOUJOURS au principal** (`credit_character(principal)` : il rétribue déjà ses compagnons par la part de butin, et une monture n'a pas de bourse). UI : badge `.sell-owner` `👤 <prénom>` / `🐴 <nom>` selon `porteur_icon`, posé **serveur** via `montures.est_monture` (le client ne devine pas) ; `compagnon_id` fileté par `_cgArg`.

**Coût de revient** : champ `valeur` explicite du doc → autoritaire ; sinon récursif via les recettes (les transformations coûtent bien plus cher). Feuilles (matières brutes) = `poids × MULT_RARETE × PRIX_DERIVE_BASE`. **Prix marché** = `prix_courant × facteur_stock`, re-clampé `[pmin,pmax]`. Cible de stock = `stock_cible_pour(lieu, item)` (item > sous-cat > catégorie > défaut).

**Tick atelier** (à la vente, à l'achat, à la visite) : (0) appro des feuilles ; (1) production (multi-matières, tirage pondéré ; **pool unifié** — consomme `stock_matieres` PUIS le **surplus du rayon** au-dessus du `stock_cible`, donc un intermédiaire produit est à la fois **en vente ET réutilisable comme matière** pour la recette de niveau supérieur, chaînage intra-tick sans duplication ; `resolve_fn` injectable) ; (2) **écoulement PNJ objet par objet** (chaque produit en rayon tire indépendamment sa demande `VENTE_PNJ_PROBA` ; surplus au-dessus de la cible seulement).

**Dépeçage** : poids de l'instance × poids/REF (plus lourd = plus de matière). Tendons/boyaux/foie… sont **gated par tags d'espèce** (`DEPECAGE_TAGS`) — la recette de boucherie ne fixe que la *quantité*, pas l'appartenance. Une entrée de `DEPECAGE_TAGS` peut être une **sous-catégorie** OU une **clé item-ref `item:*`** ciblant un item précis (ex. `demon` → `item:Sang_demon_seche` : la matière traverse jusqu'au rayon telle quelle, `matiere_item_id` la laisse intacte). Les matières de dépeçage qu'aucune recette du lieu ne consomme sont **déplacées en rayon (`stock_vente`) et vendues au joueur** — c'est le canal par lequel le joueur obtient sang/griffes/os.

### Armement & matières premières (contenu)
**Un modèle d'arme = UN doc.** ⚠️ Ne pas recréer de paliers de qualité en documents (`item:X_2`…`_7`) : ce seraient des clones stricts que rien ne produit et que rien ne lit. Une échelle de qualité devra être une **mécanique** — un modificateur porté par l'instance, comme le `poids` d'instance.

**`manche` vs `hampe`** : deux sous-catégories distinctes de fût, et **c'est le fût qui décide de la portée**. `manche` (0.2 kg, ← `branche`/`petit_rondin`, armurerie et fletcher) = armes de portée 1 et arcs ; **`hampe`** (1.2 kg, ← `rondin` ×1 → 1, `gros_rondin` ×1 → 2, armurerie) = armes d'**hast** (cac `portee ≥ 2`). Les deux sont des **intermédiaires produits sur place** → pool unifié du tick atelier.

⚠️ **Toute matière consommée par une catégorie de lieu devient une feuille auto-approvisionnée, donc ACHETABLE sur place** (`appro_leaves_categorie` → `approvisionner`) : écrire une recette, c'est ouvrir un point de vente pour chacun de ses intrants bruts. Ne jamais y mettre une matière dont la **rareté fait le sel d'une quête ou d'un don** — les armes bénies consomment de l'`argent` et **pas** `item:Eau_benite`, sinon l'eau bénite se vendrait au comptoir de l'armurier et le don du révérend Malakor ne vaudrait plus rien. Symétriquement, c'est le bon levier pour **ouvrir un débouché** à du butin de dépeçage (plumes, crins → rachetés par l'armurier).

⚠️ Une clé matière **sous-catégorie** est résolue en `item:<sous_categorie>` par `matiere_item_id` (prix, appro) : ce doc doit exister, sinon la matière est valorisée à vide. Quand l'item générique n'existe pas ou porte un autre id (`item:Poudre_os` pour la sous-cat `poudre_d_os`, `item:Chiffon` pour `chiffon`, `item:Seve_de_chene` pour `seve`), utiliser la forme **`{"item": "item:XXX", "quantite": n}`**, qui circule telle quelle.

Contenu : `jsons/armes_hast_a_importer.json` (armes d'hast, tags `["cac","hast"]`, deux mains ; matières `item:hampe` + `item:argent` ; recettes des armes qui n'en avaient aucune → armurerie et tabletterie).

### Marchandage & relations
`prix_courant` = prix négocié OU prix de base pondéré par la relation (0-100, neutre 50, `frac = 0.5 + (val−50)·coeff/100`). **Prix appliqué** = `prix_marche` (courant × facteur_stock, re-clampé). ⚠️ La négociation est persistée comme **FRACTION de la fourchette**, pas comme montant fixe → un poids d'instance différent donne un prix différent.

**Relation** = doc CouchDB `type:"relation"` (char × lieu, 0-100, `prix_negocies`, blocage epoch). `POST /api/marchander` : jet avec bonus `(rel−50)·coeff` ; **réussite** = prix persisté ; **crit ok** = +1 relation ; **crit fail** = −1 relation + blocage (`MARCHANDAGE_BLOCAGE_SECONDES`). UI : badge relation, bouton 🤝 ; ⚠️ le toast affiche `prix_marche` exact, pas `prix_negocie` (qui ignore le `facteur_stock`).

**Fidélité — commercer répare une brouille.** Sans elle, une relation dégradée ne remonte que par un **crit** de marchandage : le client régulier n'avait aucun recours. Chokepoint pur **`marche.compter_transaction(relation_doc)`** → `{compteur, restant, gain, relation, modifie}` : compteur `fidelite_transactions` sur le doc relation (absent ⇒ 0, aucune migration), **+1 de relation tous les `RELATION_FIDELITE_TRANSACTIONS` échanges** (ventes **et** achats confondus) tant que la cote est **sous `RELATION_FIDELITE_SEUIL`**. ⚠️ Le compteur **ne tourne QUE sous le seuil** et est **remis à zéro au-dessus** : il faut 10 échanges *depuis* la brouille pour regagner un point, un client déjà bien vu ne capitalise pas d'avance. ⚠️ Un **banni** (0) est exclu — la fidélité n'est pas la porte de sortie d'un bannissement. Le seuil est réglable **au-dessus du neutre** (la fidélité mènerait alors jusqu'à « Estimé ») sans une ligne de code.

⚠️ **`sell_item`/`buy_item` ne sauvegardaient JAMAIS le doc relation** (seul `/api/marchander` le faisait) : le compteur les y oblige. Chokepoint router **`_appliquer_fidelite(character, relation, payload)`**, appelé juste après `_inventory_payload` dans les **deux** endpoints — donc **APRÈS** le calcul du prix (la transaction se règle à la cote d'avant) et **AVANT** `_marchand_vendables`/`resolve_stock_vente` (les listes renvoyées reflètent la nouvelle cote). Le doc relation y est **annexe** : écrit best-effort et **seulement s'il a bougé** (`modifie`) ; `relations_lieux` n'est recalculé **qu'en cas de gain** (il relit tous les docs relation + lieu). Effet de bord assumé : la 1re transaction chez un marchand **crée** son doc relation. ⚠️ Côté client, le gain est **suffixé au toast de vente/achat** (`_fideliteSuffixe`) et non émis à part — `#toast` est unique, un second appel écraserait le premier.

### Capacités mises en commun par l'expédition (`utils/expedition.py`)
Ce que le groupe sait faire **ensemble**, et non ce que chacun sait faire seul. Chaîne d'import acyclique `bois → expedition → recrutement`. Trois fonctions : **`membres`** (cf. Conventions §7) ; **`porteur_avec_tag(get_doc, porteurs, tag)`** = scan du sac **ET** des slots (une hache est le plus souvent en main) ; **`meilleur_negociateur(character, compagnons, seuil_min=None)`** → `(doc, cha, est_compagnon)`.

`bois.a_outil_coupe` en est le premier appelant ; sa signature publique reste `(character, get_doc_fn, compagnons=None)`, `compagnons=None` valant comportement historique.

**Marchandage mené par le groupe** (`routers/user._negociateur`) : le jet est celui du membre au plus haut **Cha buffé**, un compagnon ne prenant la parole que si son affinité atteint **`MARCHANDAGE_COMPAGNON_AFFINITE_MIN`**. ⚠️ Ce seuil ne filtre **que les compagnons** (le principal n'a pas d'affinité envers lui-même) : `0` = tous les compagnons éligibles, **pas** « principal seul » (miroir de `QUETE_TRANSPORT_RELATION_MIN`). ⚠️ Le Cha doit passer par `caracts_avec_buffs` et non par `caracteristiques_current` brut, sinon les compétences de charisme n'ont aucun effet ; ⚠️ `sync_equipment_bonus(m)` sur **chaque** membre AVANT `caracts_avec_buffs`, sinon les buffs d'équipement sont périmés. **Inchangés** : relation, blocage et prix négocié restent ceux du **principal** — seul le jet change. Le résultat est **parlé** (`negociateur:{nom, cha, compagnon}` → `_negoPrefixe`/`marchToast`) **uniquement quand c'est un compagnon**.

Contenu : `jsons/competences_allie_a_importer.json` — compétences actives `cible:"allie"`, **niveau 1 et non 0** (offrir un soin au choix de création déséquilibrerait le départ ⇒ absentes de `competences_depart_par_vocation`).

### Onglet 🤝 Relations
Panneau `#sh-relations` : 🏪 **Lieux connus** + 👥 Personnages. **`relations_lieux_payload(character)`** (source unique, `utils/marche.py`) = **tous les lieux CONNUS** = `lieux_visites` ∪ lieux ayant un doc `relation` → liste **à plat**, chaque entrée `{lieu_id, nom, categorie, est_ville, image, image_route, value, bloque, lieu_parent, parent_nom, parent_image…}` ; lieu sans relation = valeur neutre `RELATION_INITIALE` ; tri par `value` décroissant.

**Rendu 100 % client** (`renderFicheRelations`) : payload injecté `RELATIONS_LIEUX_INIT` à l'init, puis **resynchronisé par tout endpoint qui bouge une relation** — `/api/marchander`, le dialogue PNJ (`POST /pnj/dialogue/choix`), et l'expiration paresseuse d'une course, qui frappe aux trois points de passage sans reload (branche « pas » de `move_character`, `GET /pnj/dialogue`, `POST /pnj/dialogue/choix`) ; le payload n'y est calculé **que si** une course a échu, puisqu'il relit les docs `relation`. La branche « lien » de `move_character` n'a rien à renvoyer : elle recharge `/play`.

**Groupé par ville** (`lieu_parent` → lieu `categorie:"ville"`, sinon groupe « Autres lieux ») en **accordéon** (`toggleVilleGroup` : une ville ouverte à la fois, mémorisée par perso dans `localStorage` `telluris.play.rel_ville_open.<char_id>`, en-tête = score de la ville + compteur). **Filtre** `#sh-rel-filter` (nom de lieu OU catégorie, `applyRelFilter` auto-déplie les groupes correspondants). **Portrait** : cliquer une ligne plie/déplie son image (une ouverte à la fois), l'image **zoome au survol** (`scale(2)`, overflow recadré).

Échelle **0-100, neutre 50** : Banni(0) / Hostile(<35) / Méfiant(<50) / Neutre(50) / Cordial(<70) / Estimé(<90) / Honoré(≥90). Badge 🚫 si `marchandage_bloque`, bouton 🧭 de focalisation par ligne. L'affinité PNJ suit la même échelle.

### Animation des déplacements — carte d'exploration & jetons de combat
**Exploration** (`play_town_telluris.html`) : `move()` écrit `--x`/`--y` sur le `:root` ; `img#bg-image` se décale par **`transform: translate3d(calc(…var(--x)…), calc(…var(--y)…), 0)`** avec `top:0; left:0` → la transition et le `will-change` déclarés sont vivants et le glissement est composité (aucun relayout). ⚠️ Décaler par `top`/`left` alors que la transition porte sur `transform` est une **déclaration morte** : rien n'est interpolé. ⚠️ `--x`/`--y` ne sont **pas** des custom properties enregistrées (`@property`), donc non interpolables — mais on ne les anime pas : c'est la valeur **calculée** de `transform` qui l'est. Durée dans `--map-anim` (260 ms) ; `.token` (jeton du joueur) reste fixe au centre ; `img#bg-image-fit` (lieux sans grille) intact.

**Combat** (`combat_telluris.html`) : ⚠️ **une transition n'a rien à interpoler sur un élément qui vient de naître** — un `renderTokens()` qui fait `layer.innerHTML = ''` tue l'animation. Les jetons sont donc **persistants**, indexés par id d'acteur dans une `Map` (`_tokens`) : ce qui varie (classes, position, barre de PV, `onclick`) est réécrit à chaque rendu, ce qui est figé (portrait, structure interne) n'est bâti qu'à la création, et les jetons sans objet sont retirés en fin de passe. ⚠️ `onclick` est remis à **`null`** explicitement — un `if (adj)` laisserait en place le gestionnaire du rendu précédent sur une cible devenue hors de portée. ⚠️ L'ordre du DOM ne suivant plus celui de l'état, l'ordre de peinture est fixé par un **`z-index`** explicite (monstres 1, alliés 2).

⚠️ **La ROTATION impose de tourner PUIS translater, en coordonnées MONDE.** Le CSS interpole une liste de `transform` **fonction par fonction** (l'angle pour `rotate`, le vecteur pour `translate`). Avec des positions calculées en coordonnées écran, un pivot ferait changer ce vecteur → les jetons interpoleraient la **corde** (ligne droite à travers la carte) pendant que le décor tourne. Carte et jetons s'écrivent donc `rotate(a) translate(vecteur_MONDE)` : pendant un pivot le vecteur monde **ne bouge pas**, seul l'angle varie ⇒ tout décrit le **même arc**, autour du même point — la case de l'acteur actif, déjà pivot de `#rotation-pivot`. Au repos la matrice est **rigoureusement** l'ancienne (`T(-50%,-50%)·R(a)·T(u) = T(-50%,-50%)·T(R(a)·u)·R(a)`) ; seule l'interpolation diffère.

- `_placerToken(tok, wx, wy)` = `translateX(-50%) rotate(a) translate(w) rotate(-a)`. Le `rotate(-a)` final **annule la rotation subie par le jeton lui-même** (les deux angles s'interpolant au même rythme, ils se compensent à chaque instant : le portrait reste debout pendant tout le quart de tour). ⚠️ `translateX(-50%)` reste **en tête, hors rotation** — c'est un recentrage sur la largeur propre du jeton, le tourner le décalerait. L'ancre `left:50%` / `bottom:var(--floor)` pose déjà le centre du jeton **sur** le pivot.
- `updateCamera()` = `translate(-50%,-50%) rotate(a) translate(u)`, `u` en coordonnées monde.
- ⚠️ **`angleCamera()` = angle CUMULÉ.** `facing` (0/90/180/270, snapshot serveur) repasse par 0 après 270° : interpoler `rotate(-270deg) → rotate(0deg)` ferait faire au monde trois quarts de tour **à l'envers**. L'angle est donc continu, avancé du plus court chemin, et **idempotent** (facing inchangé ⇒ écart nul) → `renderTokens` et `updateCamera` peuvent l'appeler l'un après l'autre sans le faire dériver.
- `screenToWorld` subsiste pour la saisie des déplacements ; la conversion inverse est le travail du `rotate()` CSS.

**`sansAnimationCarte()`** pose `.no-anim` sur `#viewport` le temps d'une frame (double `rAF`) pour les re-rendus qui **ne sont pas un mouvement de jeu** : redimensionnement (`--step` change, donc TOUTES les positions) et **premier cadrage** (sans quoi la carte partirait du centre — valeur de la feuille de style — pour rejoindre la position du joueur si le navigateur a déjà peint). Le pivot du monde, lui, est animé.

⚠️ Les deux pages partagent le nom `--map-anim` et portent chacune **leur propre** garde `@media (prefers-reduced-motion: reduce)` : ni `play_town_telluris.html` ni `combat_telluris.html` n'incluent `part-accessibility-css.html`, qui porte pourtant la règle globale. **Artefact assumé** : au changement d'acteur, le portrait du jeton central et l'apparition/disparition des jetons alliés sont instantanés pendant que le monde pivote.

### UI — listes scrollables de la fiche perso
Une liste longue ne pousse plus le panneau : elle **scrolle chez elle**. Une seule brique, la même pour les sacs et pour les listes de la fiche : **un wrapper `.sh-scroll` qui NE DÉFILE PAS + UN enfant qui défile**.

⚠️ **L'ombre est un `::after` en `absolute` sur le WRAPPER, jamais sur le scroller** : posée sur l'élément qui défile, elle remonterait avec le contenu. C'est toute la raison d'être du niveau de wrapper — ne pas le supprimer en croyant simplifier.

- **`.sh-scroll`** = le wrapper (`position:relative`, hauteur donnée par son enfant) ; **`.sh-scroll.scrollable::after`** = l'ombre (20 px, dégradé vers `--panel-bg`). Variante `.sh-inv-scroll.sh-scroll.scrollable::after` = **une demi-ligne d'objet** (`--inv-row-h / 2`), pensée pour les sacs.
- **L'enfant qui défile** est `.sh-inv-box` (sacs) ou **`.sh-rel-scroll`** (listes de la fiche) — une règle groupée leur donne `overflow-y:auto` + scrollbar fine. La classe de **hauteur** est portée par le **wrapper** et s'applique au scroller : `.sh-quest-list-active > .sh-rel-scroll` (40vh), `.sh-quest-list-ended >` (35vh), `.sh-capa-list >` (35vh, onglet ⚡) ; les relations gardent la base (45vh).
- **`.scrollable` = « il reste quelque chose à faire défiler »**. Deux régimes : **compté en JS** (`length > INV_VISIBLE`) là où un compteur existe (sac, sol, marchand vente/achat, les deux sacs du panneau 👥 via `_grpRemplirSac`) ; **posé EN DUR dans le markup** pour les listes de la fiche (hauteur en `vh`, contenu de taille variable, accordéon et filtre : aucun compteur ne s'applique) → l'ombre y est toujours visible.
- ⚠️ **`.sh-scroll` est à poser explicitement** : `.sh-inv-scroll` seul donne le défilement **sans l'ombre**.
- ⚠️ Listes à **double rendu** (Jinja au chargement + JS au resync) : le markup wrapper + scroller doit exister **des deux côtés**, sinon l'ombre disparaît au premier resync — cas de l'onglet 📜 (`renderFicheQuetes` réémet `.sh-quest-list-*` + le `.sh-rel-scroll` interne). Les listes de l'onglet ⚡ et celle des relations y échappent par **enveloppement** : le div que le renderer écrase **EST** le scroller (il garde son `class`), l'ombre vit dans le wrapper au-dessus — aucun JS à toucher pour ajouter une liste.

### Carte de personnage & portraits — composant unique
**`templates/part-character-card.html`** = macro Jinja **`character_card(...)`**, **SOURCE UNIQUE** du markup d'une carte (portrait cadré + barres PV/PM + identité + 2 emplacements libres : `footer` / `actions`). ⚠️ **Aucun id** dans la carte, uniquement des **`data-role`** : une page en porte N (joueur, compagnons, recrues), des ids seraient dupliqués. Racine = `.character-card[data-card][data-porteur]`.

**Un markup, deux consommateurs** : Jinja rend les cartes fixes (sidebar `card_id="sidebar"`, fiche `card_id="charac-sheet"` — le mode compagnon rebascule cette dernière sur un autre porteur) ; le client **clone** les gabarits `<template id="tpl-character-card">` / `…-ro` (rendus par la **même** macro, à vide) via **`renderCharacterCard(container, p, opts)`** (`opts = {editable, footer, actions}`) → **le JS n'écrit jamais de HTML de carte**. Usages : `#grp-compagnons-list`, `#rec-groupe-list`, `#rec-recrues-list`. Registre `_cardViewports` (clé = **la carte**, pas le porteur : un compagnon peut avoir une carte dans deux panneaux), purgé par `clearCharacterCards`.

**Portrait = `makePortraitViewport(card)`** : une instance PAR carte, état propre (`W`/`H` **mesurés dans le navigateur** — `naturalWidth/Height`, jamais côté serveur —, `zoom`, `offset`), éléments résolus par `data-role` DANS la carte. `setSujet({image, portrait_zoom, portrait_translate, compagnon_id})` change de porteur et accepte une `base` (défaut `/characters`) — ⚠️ fournie par le **serveur** (`image_base`, `portraits_joueurs[].base`), le client ne devine pas où vit l'image (une monture vient de `/monsters`). ⚠️ **`portrait_translate` = la translation CSS, soit l'OPPOSÉ de l'offset interne** (on écrit `translate(-x,-y)`) → conversion de signe **dans `defaultOffset` seulement**. `bornes()` : image plus grande que la fenêtre → défilement `[0, débord]` ; plus petite → offset fixe `(taille−fenêtre)/2` (centrée).

**`editable`** = la carte porte le curseur + ✏️/💾, rendus par la macro **uniquement là où le cadrage est enregistrable** → une recrue n'est **PAS** éditable (statut `offert` ⇒ hors `groupe_effectif` ⇒ `_acteur` 403) et son portrait s'affiche **entier** (`zoomFit`, centré), sans survol ni animation. Sauvegarde : `POST /api/update_character_portrait` via `_acteur` → le cadrage d'un compagnon vit sur SON doc, que les jetons alliés du combat relisent.

⚠️ **Les vitaux appartiennent à quelqu'un.** `updateVitals(v, porteurId = PRINCIPAL_ID)`, `_refreshDerivedStats` et `spendXpVocation` n'écrivent QUE dans les cartes du porteur visé (`cartesDuPorteur(id)` sur `data-porteur`) — un `querySelectorAll('.pv-val')` global recopierait les PV du joueur sur toutes les cartes de compagnons. Les actions de fiche (`consommer`, `lancer_sort`, `utiliser_competence`, `apprendre_competence`) passent par `_actionBody` → elles visent **`porteurActifId()`**. `_setCardVitals` / `_setCardIdentite` = seules fonctions qui écrivent dans une carte. `_identiteJoueur()` (globales + `_vitalsJoueur`) reconstruit la carte du joueur à la sortie du mode compagnon — rien n'est snapshotté en HTML.

**Payload** : `routers/recrutement.py::_recrue_view` = source unique des recrues ET du groupe → porte `voc_niveau`, `portrait_zoom`, `portrait_translate`, `permanent` et les **vitaux** (`vitaux_de`), tout ce que la carte affiche.

### Quêtes — guilde + moteur
**Lieu guilde** : `categorie:"guilde_aventurier"` + `lieu_parent` (ex. `auxerre`) ; l'extérieur intermédiaire (`guilde_aventurier_exterieur`) est inerte. Tableau généré = espèces des rencontres → quêtes `kill` ; `ressources` du lieu + carcasses → quêtes `collect`. Docs `quete:*` = générées (`source:"genere"`, max `QUETE_BOARD_TAILLE`) + authorées (`source:"authoree"`, affichées à côté). ⚠️ **Toutes les quêtes générées portent `"type":"quete"`** (docs du board, offre de rang, snapshot actif).

**État joueur** : `quetes_actives[]` (snapshot + `progress`), `quetes_terminees[]`. **Hooks de progression** : `kill` en combat (exactly-once), `visite` en déplacement, `collect` au dépôt à la guilde. **Dépôt progressif** : `POST /api/quetes/deposer` retire les pièces portées et incrémente `progress` (plusieurs voyages OK). **Pas d'arbre entier** : `cibles_collect` découpe si `> QUETE_COLLECT_POIDS_MAX`. UI : bouton 📜, panneau AJAX, onglet fiche resync client `renderFicheQuetes` ; CSS factorisé `.panel-frame`/`.board-panel`. Mode Ressources de l'éditeur → `PUT /api/lieu/{id}/ressources`.

**Le tableau tourne — d'autres aventuriers prennent les contrats** : une offre **générée** porte un **`expire_at`** posé à la génération (`_duree_de_vie` = `QUETE_BOARD_DUREE_SECONDES` **jittée** de ±`QUETE_BOARD_DUREE_JITTER`). ⚠️ Sans jitter, les offres naissant au même instant, le tableau basculerait **d'un bloc**. Péremption paresseuse : `remplir_tableau` appelle `purger_offres_perimees` avant de compléter → le doc périmé est **SUPPRIMÉ** (`delete_doc` ; personne ne le référence, celui qui accepte en garde un snapshot) et la place est aussitôt repeuplée. `offre_perimee` ne vise **que** `source:"genere"` + `statut:"offerte"` : une quête **authorée** ne périme jamais, une **acceptée** a déjà quitté le tableau. Repli sans `expire_at` : `genere_at` + durée nominale.

**Renoncer fâche toute la MAISON du donneur** (`quetes.sanctionner_renoncement`, chokepoint unique) : **abandonner** une quête (n'importe quel type, `POST /api/quetes/abandonner`) **ou** laisser filer le délai d'une course (`transport.traiter_expirations`) coûte `QUETE_TRANSPORT_RELATION_DELTA` de relation chez le donneur **et chez tous les lieux de sa maison**. La **réussite**, elle, ne récompense que le donneur (`+1`) — asymétrie assumée : la maison punit collectivement, elle ne remercie pas collectivement.

⚠️ **Maison = donnée, pas code** : `lieux_solidaires` = les lieux de **même `sous_categorie`** **ET** de même `lieu_parent` que le donneur. La **conjonction** est indispensable — le `lieu_parent` des lieux d'une guilde est la **CITÉ**, donc seul il ramènerait tous les lieux de la ville ; et la seule `sous_categorie` ramènerait les guildes des autres cités. Un donneur **sans `sous_categorie`** (un magasin) n'est solidaire que de lui-même. La façade `guilde_aventurier_exterieur` ne porte pas le champ : elle est hors maison — lui poser le champ suffirait à l'y faire entrer, sans toucher au code, et toute faction future s'y branche pareil. `find_docs` indisponible → repli gracieux sur le donneur seul.

### Quêtes de transport — magasins + tenancier générique
Un magasin X confie une **cargaison** à livrer à un magasin Y qui **rachète** ces biens (`lieu_buys`), dans un **délai réel** (`QUETE_TRANSPORT_DUREE_SECONDES`). Réussite → **+1 relation avec X** + XP + prime ; **échec ou abandon** → sanction de maison (cf. `sanctionner_renoncement`), la **cargaison reste dans le sac** (revendable — tentation assumée). Logique pure `utils/transport.py`.

**Magasin** = `marche.besoins_categorie(categorie)` non vide (l'auberge n'en est pas un). **Tenancier générique** : aucun doc `lieu:*` marchand ne porte de champ `pnj` → `transport.entree_marchand(lieu)` dérive `pnj:marchand_<categorie>` (proba 1.0), injecté via `marchand_fn` dans `pnj.entrees_pnj` / `tirer_pnj_present` / `entree_pnj_active` ; ⚠️ le champ `pnj` explicite prime toujours. Docs générés par `dev/gen_marchands.py` → `jsons/marchands_a_importer.json`. ⚠️ **Portraits = placeholders**, à remplacer par un portrait par métier.

**Offre** : tirée à l'**ENTRÉE** du magasin (`QUETE_TRANSPORT_PROBA`), persistée en champ transitoire `character["transport_offert"] = {lieu, quete|None}`. Pas d'offre si une course est déjà active (pas d'empilement). **Confiance requise** : `confiance_suffisante` — un marchand ne confie **aucune** cargaison si sa relation est **< `QUETE_TRANSPORT_RELATION_MIN`** **OU** si son **marchandage est bloqué** (`marche.marchandage_bloque` : brouille datée, indépendante de la cote — elle ferme la porte même à relation ≥ seuil et même garde-fou désactivé). Relation absente en base = neutre → le tout-venant reçoit des offres. ⚠️ Ne vaut que pour les courses **générées** : une course **écrite** est confiée par son scénario, quelle que soit la cote.

**Deux sources d'offre** (aiguillage dans `poser_transport_offert(…, pnj_doc=…)`, qui reçoit le PNJ déjà arrêté pour cette entrée — `main.py` le résout AVANT le tirage) :
1. **Générée** — le donneur est un magasin, tout est tiré au sort.
2. **AUTHORÉE** — le PNJ présent porte une course écrite dans **`services.transport.offre`** = `{id, destination, cargaison:[{item, quantite, poids?}], duree?, proba?, unique?, titre?, description?, recompenses?}` (miroir de `services.soin`/`services.don`). Alors **n'importe quel PNJ peut confier une course** : le donneur n'a **pas** à être un magasin, rien n'est tiré au sort, et les bornes `POIDS_MAX`/`NB_MAX` **ne s'appliquent pas** (seul le contrôle de charge à l'acceptation reste). ⚠️ L'`id` doit être **stable** : c'est le gate de `unique:true` (`deja_reussie` — un **échec ne bloque pas**, le donneur repropose). Le **destinataire** reste un magasin (c'est son tenancier qui porte les nœuds `livre`/`incomplet`).

**Cargaison** : items que X fournit (`stock_vente` + `produits_categorie`) ET que Y rachète ; empilage instance par instance, **arrêt AVANT de franchir** `QUETE_TRANSPORT_POIDS_MAX` **ou** `QUETE_TRANSPORT_NB_MAX` — la borne la plus contraignante gagne ; objet unique trop lourd → **pas d'offre**.

**Course à `retour`** (`spec.retour:true`) : le destinataire prend la marchandise mais **ne paie pas** (`livrer_en_attente_de_retour` → nœud `livre_retour`, repli `livre` ; `livree_at` posé, **`expire_at` retiré** — le délai portait sur la livraison, pas sur le retour) ; la quête **reste active** jusqu'à ce que le joueur revienne **rendre compte au donneur** (op `rapporter` → `rapporter_transport` → nœud `rapporte`), qui solde alors XP, prime **et `recompenses.items`**. `transport_a_livrer` exclut les courses déjà livrées ; `retour_attendu(character, lieu)` les retrouve chez le donneur. ⚠️ Le nœud `livre_retour` est porté par **tous les marchands génériques** (gabarit `dev/gen_marchands.py`) : sans lui, le repli sur `livre` ferait promettre une prime que le destinataire ne verse pas.

**Items de récompense** (`recompenses.items`) = des références d'**instances**, fabriquées par `items_recompense(spec_items, giver_doc)` : une entrée peut demander `"lieu_parent": "auto"` (sentinelle `transport.LIEU_PARENT_AUTO`) → l'exemplaire remis porte le `lieu_parent` du donneur (repli : son `_id`). L'objet en base reste **générique** et c'est l'instance qui dit d'où elle vient → la même mission copiée dans une autre guilde délivre la carte de **sa** cité.

**Géographie** : aucune coordonnée monde sur les `lieu:*`, mais chaque doc `connection` boutique↔ville porte la **porte dans la grille de la ville** → `focalisation.charger_graphe` l'expose, `portes_du_parent` + `direction_cardinale` (8 octants, ⚠️ **`y` croît vers le BAS** → nord = dy<0) + `repere_proche` donnent « au nord-est d'ici, tout près du Fumoir ». Hors ville : nom de la ville + distance BFS. `porte_effective` (BFS) donne la direction depuis un lieu **imbriqué** qui n'ouvre pas lui-même sur la grille de la ville (comptoir → réception → façade). XP = `QUETE_TRANSPORT_XP` (même ville) ou `× (1 + distance)`.

**Dialogue** (`services.transport.noeuds`) : `pnj.condition_ok` traite toute clé inconnue comme un **flag booléen** du contexte → conditions `transport_offert` / `transport_a_livrer` posées par le router ; `_substituer` remplace en plus toute clé de `contexte["placeholders"]` (`{destination}`, `{direction}`, `{colis}`, `{poids}`, `{delai}`, `{xp}`, `{prime}`, `{expediteur}`). Actions : `accepter`, `livrer`, `rapporter` ; proposer/informer sont de simples `next` conditionnés. Flags : `transport_a_rapporter`, `transport_en_cours` (confiée par CE lieu, non encore livrée → relance), `transport_accompli` (course `unique` déjà réussie).

⚠️ **Les enseignes portent leur article** (« Le Saloir ») : **jamais de préposition devant `{destination}`** (« à Le Saloir » serait fautif), toujours un deux-points.

**Refus parlé** : flag `transport_mefiance` (`transport.mefiance` — magasin, aucune course écrite/en cours, `confiance_suffisante` fausse) → choix `course_refus` des marchands vers le nœud `transport_mefiance`, sinon la sanction serait un **silence**, indiscernable d'un tirage négatif. ⚠️ Un **seul** nœud pour les deux causes (relation sous le seuil, marchandage bloqué) → son texte parle d'**entente**, jamais d'une cause précise : il doit rester vrai dans les deux cas.

⚠️ **Placeholders hors course** : ils sont posés dès qu'une offre est **écrite** (`spec`), même sans course vivante — `_contexte` reconstruit alors l'aperçu par `generer_transport_authore` (déterministe). Sans ce repli, un nœud qui ne s'affiche **qu'après** la réussite rendrait `{destinataire}` en clair.

⚠️ **RÈGLE — un dialogue ne cite JAMAIS un nom de PNJ en dur.** Les docs `pnj:marchand_*` sont **génériques** (un par catégorie, partagé par toutes les boutiques) et **chaque lieu peut rebaptiser son tenancier** via `nom` dans son entrée `pnj` : un nom écrit dans un texte mentirait. Placeholders de nom, posés par le router : **`{pnj}`** = celui à qui l'on parle (source unique **`pnj.nom_effectif(entree, doc)`** — l'entrée du lieu prime, repli doc ; c'est aussi ce que rend `pnj_payload`) ; **`{destinataire}`** / **`{donneur}`** = les PNJ des deux bouts d'une course (**`pnj.nom_pnj_du_lieu(lieu, get_doc, marchand_fn)`**, qui nomme le PNJ d'un lieu **sans y être**, 1re entrée prioritaire). `{destination}`/`{expediteur}` sont des **enseignes** (lieux), `{pnj}`/`{destinataire}`/`{donneur}` des **personnes**. ⚠️ **Aucun pronom genré** autour d'eux : le tenancier peut être une femme.

**Mise en rayon à la livraison** : `deposer_en_rayon(dest, cargaison, get_doc_fn, rand_fn)` — chaque objet livré a `QUETE_TRANSPORT_STOCK_PROBA` de rejoindre le `stock_vente` du destinataire, **à condition qu'il vende ce produit** (`marche.lieu_produit`). ⚠️ Un item qu'il n'achète que comme **matière première** ne monte jamais sur l'étal. Le doc `lieu` est **annexe** → persisté par `reussir_transport`, comme le doc `relation`.

**Focalisation 🎯 interdite** : `focalisation.OBJECTIFS_FOCALISABLES` + `quete_focalisable(q)` — source unique lue par `/api/focaliser` (422) et par le champ `focalisable` de `quete_detail` (les 3 rendus du bouton).

**Expiration** : `traiter_expirations(character, now, get_doc, save_doc)` (cf. Conventions §5). Le doc `relation` est **annexe** → persisté séparément, best-effort. UI : chrono `.sh-quest-timer` dans l'onglet 📜 (deadline **locale** dérivée d'`expire_at` + `now` serveur, `setInterval` unique, orange < 5 min) + toast d'échec, relayé par `sessionStorage` quand le changement de lieu recharge la page.

Contenu (2 fichiers) : `jsons/premiere_mission_a_importer.json` (comptoir, sa connexion à la réception, les items) et `jsons/pnj-*.json` (**tous les docs PNJ** — seule source à jour). `jsons/carte_aventurier_correctif.json` a rendu la carte d'aventurier générique.

### Quêtes de « chasse » (élite à profil élevé) + rang de guilde
Objectif `chasse` : traquer et tuer **UN** ennemi d'une espèce, marqué d'un **profil élevé**, dans un lieu précis. `objectif = {type:"chasse", cible:"espece:x", lieu:"lieu:y", position:{x,y}?, profil:"profil:z", quantite:1}`. Deux canaux : (1) **tableau de guilde** (`guilde_aventurier`) → grade `max−1` ; (2) **PNJ du comptoir** (`guilde_aventurier_comptoir`) → grade `max`, comme **condition de gain de rang** (rang par cité = `lieu_parent`). Logique pure `utils/chasse.py`.

**Grade résolu À LA GÉNÉRATION** (`resoudre_profil_chasse`), jamais au combat : `position_de_chasse` = centre d'un placement d'une zone qui contient l'espèce (présent seulement si le lieu a une grille) ; zones actives à ce point → `resolve_profil_weights` (`utils/zones.py`, partagé avec le combat) → profils **filtrés `restriction_tags ⊆ tags espèce`** (un loup sans tag `magie` ne devient jamais un profil `magie`) → niveau `max`/`max−1`, égalité `random.choice`. `profil_id` stocké dans l'objectif ; le combat l'applique tel quel.

⚠️ **Le libellé de l'élite ne vient PAS du `nom` du doc `profil:*`** (taillé pour un aventurier — « Novice », « Seigneur mage » —, absurde collé sur une bête) mais de l'échelle de bestiaire **`chasse.QUALIFICATIFS`** indexée par le **niveau** du profil (bornée aux deux extrémités). Source unique `chasse.qualificatif_de(profil)`, lue par les **deux** sites de génération (`chasse._construire_quete_rang` et `quetes._generer_chasse`) et **figée** dans `titre`/`description`/`narration` à la génération. Le doc `profil:*` n'est pas modifié : son `nom` sert partout ailleurs. Le qualificatif reste **entre guillemets** (épithète invariable en genre : « la Vipère « Impitoyable » »).

**Application en combat** (`routers/combat.py::start_combat`) : si un combat tire **naturellement** l'espèce dans le lieu **ET** que le joueur est dans la **zone 3×3** de la position (`chasse.dans_zone_chasse`, Chebyshev ≤ 1 ; sans position → contrainte de lieu seule), **UN** monstre non marqué est promu élite via `build_monster_snapshot(espece, profil, idx)`, portant `quete_chasse=q.id`. ⚠️ On ne force **pas** l'apparition de l'espèce. Variante rang → `chasse_narration` sur le doc combat → overlay pré-combat `#chasse-overlay`. Progression : **`maj_progress_chasse`** dans `finalize_combat` juste après `maj_progress_kills` (même fenêtre d'idempotence ; seul le monstre **marqué** complète). Focalisation 🎯 = mode `kill` (biais d'espèce).

**Rang de guilde = prestige/affichage seul** : `character["rangs_guilde"] = {"lieu:auxerre":"F"}` (échelle `recrutement.RANGS`, absent ⇒ premier cran, init à la création). Épreuve tirée à l'entrée du comptoir (`poser_rang_offert`, proba `QUETE_CHASSE_PROBA_RANG`, champ transitoire `character["rang_offert"]`). Dialogue : service **`rang`** — `_contexte` pose les flags `rang_offert`/`rang_a_rapporter`/`rang_max` au comptoir ; op `accepter` → `accepter_rang` (push du snapshot avec `source:"rang"`/`rang_vise`/`cite`/`narration`), op `rapporter` → `solder_rang` (`objectif_atteint` → `promouvoir` + `appliquer_recompenses` → `quetes_terminees`). Placeholders `{espece}/{lieu}/{rang}/{rang_vise}`. Contenu : `jsons/rang_guilde_a_importer.json`.

**Carte 🗺️** : `quete_detail` ajoute un champ `carte` (`_carte_chasse`) pour toute chasse **localisée** — image servable du lieu (`marche._lieu_image_route`), `dimensions`, `position`, et **`direction_texte`** « Au \<direction\> du bâtiment de la guilde » (direction PAR AXE `chasse.direction_cardinale_simple`, `y` vers le bas, depuis la **porte du donneur dans la grille de la cité** obtenue par `focalisation.charger_graphe` + `prochaine_etape` — BFS multi-hop, qui marche pour un comptoir imbriqué). UI : bouton 🗺️ aux **deux** rendus (Jinja + `renderFicheQuetes`, données en `data-carte`), overlay `#quest-map-overlay` (`showQuestMap`) = **crop 6×6 de l'image du lieu centré sur la case cible** (marqueur 🎯) + la ligne d'orientation. ⚠️ **Limitation** : `position` = centre du placement de zone ; si ce centre et ses 8 voisins sont non-accessibles, le joueur ne peut pas déclencher pile dans le 3×3 (repli futur : viser une case accessible proche).

### Recrutement d'aventuriers & combat de groupe
**Recrue = doc `aventurier:*` MIROIR du character** : mêmes champs que consomment `build_joueur_snapshot`/`compute_derived_stats`/`grant_xp`/`carried_weight`, + champs propres `statut:"offert"|"embauche"|"parti"`, `giver`, `rang`, `specialite`, `exigences:{part_butin_pct, clauses[]}`, `expire_at` → **tout le moteur de combat marche dessus tel quel**. Logique pure `utils/recrutement.py`, router `routers/recrutement.py` (congédier autorisé **PARTOUT**).

**Tableau de recrues** : lieu recruteur = tag `"recrutement"` OU `categorie:"guilde_aventurier"` (le OU évite une migration). Offre `{nb, niveau_max}` = `RECRUTEMENT_OFFRE_PAR_SOUS_CATEGORIE[sous_categorie de la CITÉ]` (repli `defaut`), surchargée champ à champ par `lieu.recrutement_restrictions`. **Accès** : carte d'aventurier de la cité en sac (`item_ref_lieu == lieu_parent`, `RECRUTEMENT_CARTE_REQUISE` désactivable) → 403 explicite sinon. Prélude commun des endpoints = `_acces_tableau` + `_recrue_du_tableau`.

**Génération procédurale** (`generer_aventurier`) : race/sexe/vocation tirés sur `rules:races`/`rules:vocations` ; stats = base raciale + budget de points (coût triangulaire, miroir de `bonusStats`) + `RECRUTEMENT_NIVEAU_POINTS_PAR_NIVEAU`×niveau ; équipement de base **équipé dans les `slots`** (`_equiper_defaut`, 1er slot compatible libre) — ⚠️ `_weapon_attacks` ne lit **que** les slots, un équipement laissé au sac ne donnerait aucune attaque ; portrait par préfixe `{voc}_{sexe}_{race}` ; PV/PM = max dérivés.

**Rotation paresseuse** (durée jittée `RECRUTEMENT_BOARD_DUREE_*`) : recrue offerte échue jamais embauchée = doc SUPPRIMÉ ; un **ancien compagnon** ré-offert qui expire repasse `parti` — son doc porte la mémoire du lien. `remplir_tableau_recrues` **ré-offre en priorité** les anciens compagnons `parti` du giver dont l'affinité ≥ `AFFINITE_SEUIL_REMISE`. Chokepoint **`retirer_du_tableau`**, partagé par la péremption et le refus.

**Groupe & contrat** : `character["groupe"]` = liste d'IDS, l'état du compagnon vivant sur SON doc (`groupe_effectif` filtre statut `embauche` + `embauche_par`). Plafond `RECRUTEMENT_GROUPE_TAILLE_MAX`. Embauche **gratuite** ; contrat jusqu'au congédiement, + **départ de lui-même** si affinité < `AFFINITE_SEUIL_DEPART` (check paresseux à `/play` et au board).

**Exigences** : `part_butin_pct` (tirée `[MIN,MAX]`, biaisée haut avec le niveau) **prélevée sur le CUIVRE des récompenses de quête au turn-in** via le chokepoint unique `regler_part_butin` (arrondi sol, crédit au doc du compagnon) ; part effective réduite d'1 pt par `AFFINITE_REDUC_PART` pts d'affinité au-dessus de 50 (plancher MIN). `clauses` (0-2, tirées dans `CLAUSES_TYPES`) = **à ACCEPTER pour que l'embauche ait lieu** : le bouton Embaucher passe par `demanderEmbauche`, qui ouvre `#clauses-overlay` **seulement si la recrue a au moins une clause**, sinon embauche directe. ✔ Accepter → `POST /recrutement/embaucher` ; ✕ Refuser → `POST /recrutement/refuser` → `retirer_du_tableau`, place aussitôt repeuplée. ⚠️ Le refus **ne coûte aucune affinité** (le character n'est pas muté → pas de `save_doc(character)` dans l'endpoint). Le *respect* des clauses n'est pas détecté en jeu : elles engagent moralement, pas mécaniquement.

**Affinités** (`character["affinites"]`, 0-100 neutre 50) : +`AFFINITE_DELTA_QUETE` par quête réussie ensemble, +`_VICTOIRE`/−`_KO` en fin de combat, −`_CONGEDIE`(`_EN_QUETE`) au renvoi et à l'abandon de quête. `compagnons_connus` = mémo borné → onglet 🤝 section 👥 (`renderFicheCompagnons`, payload `affinites_detail`, resync à l'embauche/au congédiement/au turn-in). UI : bouton sidebar 🤝 Recrues (`est_recrutement`) → `#recrutement-panel`.

**Combat de groupe — le joueur joue TOUS les personnages** : `start_combat` passe `compagnons=groupe_effectif(...)` à `create_combat_doc` (snapshots `joueur_1..N`, +1 monstre par 2 compagnons) ; furtivité initiale sur `joueur_0` seul. **IA monstre** : `_cible_joueur` = joueur VIVANT le plus proche (furtif non détecté exclu s'il y a une autre cible ; tous furtifs → jet de détection sur le plus proche puis chasse/errance), cible re-résolue si KO en cours de tour. **Défaite = TOUS à terre** (KO d'un membre = log « à terre », le combat continue) ; `_resolve_until_player` saute les joueurs KO ; ⚠️ **0 PV chez un compagnon = KO seulement**, relevé à 1 PV en fin de combat, jamais de mort.

**`finalize_combat` multi-docs** : compagnons d'abord, principal en dernier, **idempotence PAR DOC** (`combats_recompenses` de chacun), XP pleine pour chacun, `butin_ramasse` → sac de CE membre ; quêtes/focalisation/affinités sur le principal seul.

**Butin de victoire réparti** : `/collect` reçoit des `attributions:[{monstre_id, beneficiaire_id}]` (repli legacy `monstre_ids` → tout au principal), chaque carcasse allant au sac de SON bénéficiaire (un membre du combat, validé contre `joueurs[]`), borné par SA charge (snapshot). ⚠️ La garde d'idempotence `butin_collectes[combat_id]` **mémorise** les carcasses encaissées au lieu de purger, et le principal est sauvé d'abord → sans atomicité multi-docs, jamais de doublon (au pire une carcasse de compagnon perdue sur conflit). UI de l'overlay de fin : **une rangée de pastilles-portrait par carcasse** (`buildLootList`/`recomputeCharge`, un membre + « ✕ personne », défaut = principal), pastille grisée si l'objet dépasse la charge du membre (miroir du serveur), **jauge de charge par membre** (`renderLootCharges`).

**`combat_action` par acteur** : `_actor_character_id` → consommer/sort/compétence chargent et sauvent le doc du MEMBRE ACTIF (le compagnon boit SES potions) ; fuir = tout le groupe (1 jet). **`GET /api/combat/{id}/acteur`** = ressources du membre actif. **Client** : `me() = activePlayer(state)` remplace `joueurs[0]` partout (caméra centrée sur le membre actif, le monde re-pivote au changement d'acteur) ; membres non actifs = `.ally-token` bleus (portrait + mini-barre PV) ; bandeau d'initiative résolu par id (`ib-pv-<id>`, portraits par membre via `portraits_joueurs`) ; hook `lastActorId` → `updateJoueur(me())` + portrait + fetch `/acteur`.

**Gestion du groupe hors combat** — bouton **👥 Groupe** → `#groupe-panel`, accessible **PARTOUT** (contrairement au board de recrutement). Deux sections en accordéon (une ouverte à la fois, mémorisée par perso en `localStorage`) : **👥 Compagnons** (fiche + congédier) et **🎒 Inventaire du groupe** (sac du joueur et sac d'UN porteur **côte à côte**, sélecteur si ≥2 — les montures rangées dans un `<optgroup>` —, dernier choix mémorisé ; une **flèche** par ligne transfère l'objet, **grisée** quand il ne rentre pas chez le destinataire, même arithmétique que le contrôle serveur via `_grpRentre`).

**Fiche objet dans les deux sacs** : icône + nom ouvrent `#item-detail-overlay` via deux sources supplémentaires d'`openItemDetail` — `grp_principal` / `grp_compagnon` (`_GRP_SENS` ↔ `_GRP_SOURCE`, `_grpPorteurs(source)` → `{src, dest}` selon le porteur **sélectionné**). ⚠️ La fiche s'ouvre en mode **mono, sans comparaison** : `_slots` est l'équipement du **joueur**, comparer avec un objet du sac d'un compagnon afficherait un delta faux (pour comparer : ouvrir la fiche du compagnon, où `_slots` est le sien). Seule action offerte = le **transfert** (`_cardTransferer`), miroir exact de la flèche de la ligne.

**Fiche d'un compagnon = le MÊME `#sheet-panel`, en « mode compagnon »** (`openCompagnonSheet` / `closeCompagnonSheet`) : les globales du joueur sont mises de côté (`_sheetSnap`), remplacées par le payload de **`GET /api/groupe/compagnon/{id}`**, et **toutes les fonctions de rendu existantes sont rappelées telles quelles** (zéro duplication). Onglets 📜/🤝/📖 masqués (`.tab-principal-only`) ; les 3 restants offrent les **mêmes actions**. ⚠️ `_RACE_MIN`/`_RACE_MAX` sont des **`let`** (un compagnon peut être d'une autre race). ⚠️ `_objetsAuSol` n'est **PAS** snapshotté : le sol appartient au LIEU, pas au porteur — ce qu'un compagnon y pose doit rester visible au retour. **Silhouette du paperdoll** (`.sh-paperdoll-img` = `equipement_<race>_<sexe>.png`, mount `/icons`) : rendue **100 % client** par `_refreshPaperdollImg()` depuis les globales `_raceNom`/`_sexe`, appelée par `_refreshPaperdoll()` → à jour partout où les slots le sont, dans les deux sens du mode compagnon. ⚠️ Le gabarit livre l'`<img>` **sans `src`** : posé par Jinja, il resterait figé sur la race et le sexe du joueur.

**Fiche = source unique `utils/fiche.py`** (`bloc_fiche`, `derived_de`, `stat_caps`, `race_de`) : le contenu des onglets Stats et ⚡ est bâti **une seule fois**, consommé par `/play` (contexte Jinja) ET par la fiche de compagnon — un onglet ajouté apparaît des deux côtés. Contexte `/play` : `**fiche_bloc` + `vocations_labels` (le compagnon n'a pas forcément la vocation du joueur).

**Transfert** : logique pure `recrutement.transferer_ref(source, cible, idx, item_id)` + `peut_porter` — adressage **index + item_id**, refus **AVANT** de retirer (une source refusée n'est jamais amputée), **409** si la charge max du destinataire est dépassée (⚠️ rien ne tombe au sol, contrairement au pickup). Endpoints `GET /api/groupe`, `GET /api/groupe/compagnon/{id}`, `POST /api/groupe/transferer` (`routers/recrutement.py`, qui réutilise `_inventory_payload` de `routers/user.py`). ⚠️ Un bout du transfert est **toujours** le principal. ⚠️ **Le sol appartient au principal** → `_inventory_payload(character, sol_doc=None)` et `drop_item` sauvent **deux** docs.

### Compagnie permanente — engagement durable d'un compagnon
Au-delà d'**`AFFINITE_SEUIL_ENGAGEMENT`** (aligné sur le palier « Dévoué » de `_affLabel`, pour que le joueur lise dans la fiche quand c'est possible), un compagnon cesse d'être un **contrat** : il **renonce à sa part de butin**, **sort du plafond de groupe**, et rejoint la **COMPAGNIE** du joueur, qu'il **baptise** au premier engagement. Déclenché par un **bouton** du panneau 👥 : pas de tirage, pas de champ transitoire, pas de flag de dialogue.

**État** : `av["permanent"] = True` sur le doc `aventurier:*` (l'appartenance vit sur le doc du compagnon, comme `statut`/`embauche_par` — ⚠️ `statut` reste `"embauche"` pour ne pas casser `groupe_effectif`) ; `character["compagnie"] = {"nom", "fondee_at"}`. ⚠️ **Deux fuites à colmater dès l'écriture**, sans quoi le flag survivrait à la rupture du lien et un ancien permanent ré-embauché redeviendrait permanent **gratuitement** : `departs_volontaires` (**un permanent ne part JAMAIS de lui-même** — l'engagement l'emporte sur l'humeur) et `embaucher` (`av.pop("permanent", None)` en filet).

**Part nulle** : ⚠️ `conditions_effectives` sort **AVANT tout calcul** (`{"part_butin_pct": 0, …}`) — passer par le calcul ordinaire ferait **remonter** la part au plancher `RECRUTEMENT_PART_BUTIN_MIN`. `regler_part_butin` traverse déjà ce chokepoint. Les **clauses**, elles, tiennent toujours.

**Hors plafond** : **`places_occupees(character, get_doc_fn=None)`** = compagnons de `groupe_effectif` **non permanents** ; `peut_embaucher`/`embaucher` prennent un `get_doc_fn=None`. ⚠️ **Migrer la liste ET le garde ensemble** : le client recomptait le plafond à 3 endroits (`#rec-plafond`, le `disabled` d'Embaucher, `#grp-plafond`) → tous lisent `data.places_occupees` via le helper client `_placesOccupees` (repli `groupe.length`). ⚠️ Ne pas toucher `#mnt-plafond` : plafond des montures, séparé. **Effet de bord assumé** : compter les DOCS fait qu'un **id périmé ne retient plus une place**.

**Rupture** : `congedier` applique `AFFINITE_DELTA_CONGEDIE_PERMANENT` puis `av.pop("permanent")`. ⚠️ **Les deltas NE SE CUMULENT PAS** — un seul s'applique, **priorité au permanent** sur « en quête ». ⚠️ **`character["compagnie"]` n'est PAS effacée** quand le dernier permanent part : la compagnie est une **identité du joueur**, pas un agrégat de membres — sinon un renvoi accidentel perdrait le nom et redemanderait une saisie.

**Endpoints** : `POST /api/recrutement/engager {aventurier_id, nom_compagnie?}` — autorisé **PARTOUT** comme congédier (geste privé) ; ⚠️ gardes **ordonnées** `404 → 403 (_compagnon) → 409 (peut_engager : déjà engagé / pas assez dévoué) → 422 (nom manquant, au PREMIER engagement seulement)`, pour que le premier message soit le vrai motif ; `save_doc(character)` **autoritatif** (409), `save_doc(av)` best-effort. `POST /api/groupe/compagnie {nom}` = renommage, **409 si aucune compagnie** (on ne fonde pas une compagnie sans membre). `_payload` expose `places_occupees`, `seuil_engagement` et `compagnie` (une seule fois, pas par carte). ⚠️ `main.py` met `compagnie` au contexte `/play`, sinon le badge n'apparaîtrait qu'après ouverture du panneau 👥.

**UI** : bouton `✦ Engager durablement` composé dans `renderGroupe` **seulement** (jamais `renderRecrutement` — on n'engage pas quelqu'un qu'on vient d'embaucher) ; ⚠️ `c.affinite` peut être `null` → repli sur 50, comme `_piedCompagnon`. Badge `✦ <compagnie>` **à la place** de « 💰 part 0% » dans le pied de carte (la bonne valeur serait la mauvaise information), nom pris dans la globale **`_compagnieNom`** (posée par `_majCompagnie` depuis tout payload qui la porte + init Jinja). `_btnCongedier(c)` prend la **carte** et non un id, pour porter `c.permanent` jusqu'au `confirm()`. Overlay `#engagement-overlay` calqué sur `#clauses-overlay`, ⚠️ **z-index au-dessus** et **avant lui dans la cascade Échap** : il porte un champ de saisie, c'est lui que le joueur ferme en premier. ⚠️ La réponse d'engagement ne portant pas les inventaires, le client **re-tire `GET /api/groupe`**, sinon la section 🎒 se viderait.

### Montures de transport (étables)
Premier **moyen de transport de charge** au-delà de la Force et des compagnons. Une **étable** (`categorie:"etable"` OU tag `"montures"` — `montures.lieu_vend_montures`, miroir de `recrutement.lieu_recrute`) vend des montures ; l'entrée `pnj` du lieu porte la liste `montures:[espece:*]` (`especes_offertes` = union des entrées, dédupliquée). Logique pure `utils/montures.py`, router `routers/montures.py`.

**Doc `monture:*` = MIROIR du character** (comme `aventurier:*`) : `caracteristiques_current` tirées uniformément dans `espece.base_attributes`, `currentPV/PM` = max dérivés, `inventaire`/`slots`/`effets_actifs`/`combats_recompenses` → `compute_derived_stats`, `carried_weight`, `build_joueur_snapshot`, `_apply_world_turn_regen` marchent dessus **sans code neuf**. Type DISTINCT d'`aventurier` → jamais ramassé par les boucles de recrutement (board, affinités, part de butin). Appartenance = `statut:"acquise"` + `acquise_par`, via `montures_effectives`. ⚠️ Les **`tags` d'espèce ne sont PAS recopiés** sur le doc ni sur le snapshot : plusieurs montures portent `proie`/`predateur`, qui pilotent l'IA de prédation en furtivité — un acteur rangé dans `joueurs` qui les porterait créerait une interaction qu'aucun code n'attend.

**Charge = chokepoint `montures.charge_max_porteur(porteur)`** : aiguille entre `charge_max_of` (F×5) et `charge_max_of × espece.proprietes.charge_mult`. Multiplicateur **relu à chaud** sur le doc espèce, jamais dénormalisé. `recrutement.peut_porter` (l'admission) délègue à lui (la capacité) → **un seul endroit décide de chacun**. ⚠️ `_charge_view` et `_inventory_payload` passent par le même chokepoint, sinon le client griserait ses flèches sur la charge d'un humain. `proprietes` porte aussi `prix_cuivre` (achat via `debit_character`). Contenu : `jsons/montures_proprietes_a_importer.json`.

**Groupe** : `character["montures"]` est un index **SÉPARÉ** de `character["groupe"]`, avec son plafond propre `MONTURE_GROUPE_MAX` — une monture n'est pas une épée, les mettre en concurrence forcerait un arbitrage absurde. Endpoints `GET /api/montures/etable`, `POST …/acheter`, `POST …/relacher` (autorisé partout, ⚠️ **409 si la bête est chargée** — la relâcher pleine ferait disparaître le butin en silence). **Aucun endpoint d'inventaire** : `GET /api/groupe` et `POST /api/groupe/transferer` sont porteur-agnostiques (garde factorisée `_porteur_du_groupe` = compagnons PUIS montures). Régén PV/PM au tour monde via `_apply_world_turn_groupe`.

**Combat — ciblable mais pas jouable.** `create_combat_doc(..., montures=[...])` les snapshote dans `joueurs` (donc placées, rendues, **ciblables**) avec `jouable:False`, `est_monture:True`, `deplacement:0` et `charge_max` multiplié, puis **exclut leurs ids d'`ordre_initiative`** → jamais de tour. ⚠️ **DEUX prédicats distincts, à ne surtout pas confondre** : `_joueurs_vivants` (ciblage, inclut les montures) vs **`_combattants_vivants`** (défaite, filtré sur `jouable`). Si la défaite comptait la monture, un groupe entièrement à terre avec une bête indemne ne perdrait **jamais** et, plus personne ne pouvant jouer, le combat resterait bloqué indéfiniment.

À 0 PV : `morte:True` sur le snapshot, puis **`_finalize_monture`** — passe **dédiée, hors de la boucle des compagnons** (sinon XP + affinité + relevé à 1 PV) — fait quitter le troupeau et verse la **cargaison dans `butin_disponible`** sous des ids `cargo_<snap_id>_<n>`, récupérables par l'overlay de fin (`/collect` les indexe par `monstre_id` sans exiger de monstre). ⚠️ Placé **APRÈS** l'affectation `butin_disponible = dispo`, qui l'écraserait. `butin_disponible` n'existant qu'en **victoire**, une défaite emporte la cargaison (prix assumé du risque). Une monture morte est exclue des bénéficiaires de `/collect`.

**UI** : bouton sidebar `🐴 Montures` (`est_etable`, `main.py`) → `#montures-panel` (offres en lignes `.mnt-offre`, pas en cartes — on achète une espèce, pas un individu). Panneau 👥 : les montures ferment la marche sous un sous-titre `🐴 Montures` (`_rendreCartesMontures`), cartes **non éditables** (hors `groupe_effectif`, `_acteur` refuserait leur cadrage) et **non cliquables** (pas de fiche). Jeton de combat `.ally-token.monture` (anneau ocre au lieu du bleu compagnon).

### Contrôle des dialogues PNJ (linter)
Un arbre de dialogue est de la **donnée** : ni typée, ni exécutée à l'import. Un `next` vers un nœud inexistant, un nœud de service mal nommé ou une condition mal orthographiée ne se voient **qu'en jouant la branche** — et un choix conditionné qui ne s'affiche jamais est indiscernable d'un tirage malheureux.

**`utils/lint_dialogues.py`** = logique PURE (aucune DB, aucun I/O), **source unique** de deux appelants : le CLI **`dev/lint_dialogues.py`** (`python dev/lint_dialogues.py [fichiers]` ; sans argument, tous les `jsons/*.json` ⚠️ **sauf les `telluris-dump-*`, qui sont des archives d'états passés** ; code 1 s'il reste une erreur) et le bouton **🔍 Vérifier les dialogues** de `/admin` (`POST /admin/lint-dialogues`, admin-only, **lecture seule**, mêmes deux formats de corps que `/admin/import-bulk` → il porte sur ce que contient déjà la zone de saisie). `analyser(payload)` → `{analyses, ignores, erreurs, avertissements, trouvailles[]}` ; un doc sans bloc `dialogue` est *ignoré*, pas fautif.

**Erreurs** : `noeud_depart` absent/introuvable · `next` vers un nœud inexistant · nœud **inatteignable** · nœud sans aucun choix · deux choix de même `id` dans un nœud (`choix_valide` renvoie le premier, le second est mort) · nœud de service déclaré mais absent · placeholder hors liste · **condition inconnue du moteur** (un flag absent vaut False → le choix ne s'affiche JAMAIS) · **action `livrer`/`rapporter` non conditionnée** par son flag · **nom de PNJ en dur dans un doc `pnj:marchand_*`**.

**Avertissements** : choix sans `next` ni `action` (ferme le dialogue comme `fin` — idiome valide, juste implicite) · nœud de service manquant. ⚠️ Le transport a **deux rôles** et presque aucun PNJ ne tient les deux : **donneur** (`accepte`/`trop_charge`, + `rapporte` si `offre.retour`), que n'importe quel PNJ peut être ; **destinataire** (`livre`/`incomplet`), en pratique un `pnj:marchand_*`. Les exiger de tous ferait crier au défaut sur un donneur correct.

⚠️ Les listes de référence (`PLACEHOLDERS_CONNUS`, `FLAGS_CONNUS`, `NOEUDS_REQUIS`, `ACTIONS_A_CONDITIONNER`, `SOUS_FILTRES_CONNUS`) décrivent ce que `routers/pnj.py` consomme **réellement** : les tenir à jour en même temps qu'un nouveau service ou un nouveau flag, sinon le linter signalera du code correct.

### Récolte de ressources
Les lieux portent `ressources:[{ressource:"item:x", zones:[…]}]` (mode Ressources de l'éditeur → `PUT /api/lieu/{id}/ressources`). En déplacement, `resolve_zone_event` → `resolve_recolte` = matcher les tags de `table_evenements` contre `{categorie, sous_categorie, tags}` de l'item → `random.choice`. Résultat = champ transitoire `character["ressource_recoltable"]` (réf `{item, poids}`). `POST /api/recolter` refuse la surcharge (409) et ajoute au sac. UI : bouton 🌿 Récolter.

### Découpe du bois
Chaîne joueur, distincte des recettes PNJ. Item coupable = tag `a_couper` + sous-catégorie ∈ `BOIS_A_COUPER` (ordre petit→grand) ; les tailles d'une même essence partagent un tag `essence_<xxx>`. `cible_coupe` = le tier immédiatement plus petit de l'essence. **Couper = 1 niveau** : `repartir_poids` découpe l'instance en pièces ≈ max du tier (⚠️ **poids conservé exact**, borné par `COUPE_MAX_PIECES`) ; les pièces vont au sol. Terminal = `branche` (pas de tag `a_couper`).

**Outil requis, PARTAGÉ par le groupe** : `bois.a_outil_coupe(character, get_doc, compagnons=None)` scanne sac + équipement du personnage ET de chaque compagnon → il suffit qu'**un** membre porte le tag `outil_coupe_bois`. `/couper` et `/recolter` passent `groupe_effectif(...)` ; ⚠️ l'acteur reste le **principal** (les pièces tombent au sol du lieu). Endpoints : `POST /api/couper` (409 sans outil, 422 non coupable), `/api/recolter` étendu (ressource coupable → abat un niveau vers le sol). UI : boutons 🪓 Couper / 🪓 Abattre.

### Effets à durée
**Un effet à durée est un effet à durée**, qu'il vienne d'un sort, d'une compétence, d'une potion ou d'un coup d'arme ; sur soi, sur un allié ou sur un ennemi ; en exploration ou en combat. Format unique `{buffs:{caract:Δ}, regen_pv, regen_pm, esquive, furtivite, duree}` (+ `pv`/`pm`/`degats` pour l'instantané). Logique pure `utils/consommables.py` + `utils/sorts.py`.

#### Trois sources, un chokepoint
`consommables._sources_de_buffs` replie **trois** origines → `caracts_avec_buffs` / `regen_bonus` / `esquive_bonus` sont effectifs **partout** (fiche, exploration, snapshot de combat) sans autre code :

1. **`effets_actifs[]`** — temporaire (consommables, sorts, compétences actives), décrémenté au tour monde.
2. **`equipment_bonus`** — champ item **`bonus:{caract:Δ}`** **+ `bonus_malus_depl`**, lui aussi un delta sur V qui se cumule avec `bonus.V` ; les deux sont agrégés dans `EquipmentBonus.buffs` par `recompute_equipment_bonus`. ⚠️ `compute_derived_stats` **ne soustrait pas** `malus_depl` du déplacement (`deplacement = max(1, V)`) : il est déjà dans V, le soustraire le compterait deux fois. Le malus pèse donc aussi sur l'**initiative** et le **cd** ; `EquipmentBonus.malus_depl` reste exposé pour information. ⚠️ Dénormalisé par **`characters.sync_equipment_bonus(character)`, à appeler AVANT tout `caracts_avec_buffs`** — passer par lui et jamais par `recompute_equipment_bonus` directement. Distinct des `bonus_pa`/`bonus_cc`/… qui buffent les **dérivées** (pas de double comptage).
3. **`competences_bonus`** — passives permanentes (`recompute_competences_bonus`), recalculées à la création et à chaque apprentissage. ⚠️ Une passive **conditionnée** (champ `condition`) en est **exclue** : elle n'est évaluée qu'au snapshot de combat.

**V est buffable**, à son échelle 1-10 (`buffs:{V:-2}` retire un tiers du déplacement d'un humain, `−5` l'immobilise à peu près). Planchers : V ≥ 0 et `deplacement = max(1, V)` — une cible entravée avance toujours d'une case. ⚠️ Les buffs restent exclus de `charge_max_of`, des plafonds/coûts d'XP et de `restriction_satisfaite` (Conventions §3).

**UI « ✨ Profil modifié »** : les agrégats portent `buffs_sources:[{nom, icon, buffs}]` → la fonction pure **`caracts_detail(character)`** → `{code:{base, total, delta, sources:[{origine, nom, icon, delta, actif}]}}` ventile par origine sans DB. Rendue dans la 2ᵉ grille de l'onglet ⚔ (`#sh-mod-grid`, client `_renderCaractsMod`). Resync par `caracts_detail` dans spend_xp / equip / unequip / consommer / lancer_sort / utiliser_competence / apprendre_competence / déplacement (`_caracts_payload`).

#### Non-cumul — deux règles
Elles ne visent que les **`effets_actifs`** ; équipement et passives restent **additifs** entre eux et s'ajoutent au résultat (casque +2 R et anneau +3 R = +5 R).

**(1) UNE SOURCE = UNE ENTRÉE.** Relancer le même sort, reboire la même potion **remplace** l'effet en cours : seul le dernier usage compte (durée relancée ; un lancement sans composant après un lancement renforcé **rabaisse** le buff). Chokepoint **`poser_effet(porteur, entry)`**, traversé par les **quatre** writers (`consommables.empiler_effet`, `sorts.empiler_effet_sort`, `competences.empiler_effet_competence`, `combat._empiler_effet_combat`), donc aussi par les debuffs. ⚠️ Remplacement **EN PLACE** (même index) : la chip ne saute pas de rang et le départage des ex æquo (premier arrivé) reste stable. Identité = **`cle_source(entry)`** : `sort_id` / `competence_id` / `item_id` / **`source_id`** (timbré par `identite_source(source)` en combat), repli `nom:<nom>`. ⚠️ Les ids étant préfixés, une entrée posée en combat (`source_id`) et la même relancée en exploration (`sort_id`) **se reconnaissent** — sans quoi l'effet se dupliquerait en sortant du combat.

**(2) SUR UNE MÊME CARACT, RIEN NE S'ADDITIONNE** : **meilleur bonus + pire malus** (+6 et −10 → **−4** : un buff ne peut pas *effacer* un malus, il le contre). Deux effets **différents** coexistent avec leurs durées propres — l'expiration du plus fort fait ressortir le plus faible. Même règle pour `regen_pv`/`regen_pm`/`esquive` (normalisés ≥ 0 ⇒ simple max). Chokepoint **`cumul_effets(effets)`**, lu par tous les agrégateurs : `caracts_avec_buffs`/`regen_bonus`/`esquive_bonus` (qui scindent d'abord temporaires vs permanents via `_scinder_sources`), et côté combat `_buffs_des_effets`, l'esquive de `_refresh_snapshot_stats`, la régén de `_tick_effets_combat`.

⚠️ **`extremes_buffs` est exposé à part de `cumul_effets` pour l'UI** : `caracts_detail` pose un **`actif`** par source (effet dominé = listé mais marqué inactif) → `_caractTooltipLignes` suffixe « (ignoré) », sinon le joueur chercherait dans son total un Δ qui n'y est pas.

#### Consommables
Item `categorie:"consommable"` + champ `effets`. `pv`/`pm` instantanés ; `buffs`/`regen_*` posés sur `effets_actifs[]`, tick monde = décrément. **Régén PM naturelle** = `ceil(Vol/20)` par déplacement. Exploration : `POST /api/consommer` (index + item_id). Combat : action `"consommer"` (1 action, parts instantanée **et** durative). UI : bouton 🍽️, chips ✨. ⚠️ Ordre d'écriture : combat → character → finalize.

#### En combat — le snapshot est RECALCULABLE
`build_joueur_snapshot` porte **`caracts_base`** (caracts + buffs **permanents** seuls, via le paramètre `origines` de `_sources_de_buffs`), **`equipment_bonus`**, **`voc_niveau`**, **`esquive_base`** et une liste **`effets_actifs` VIVANTE** (copie de celle du personnage). `build_monster_snapshot` porte les **mêmes champs** (`caracts_base` = stats brutes, `esquive_base: 0`, `effets_actifs: []`) — c'est ce qui rend les debuffs sur ennemi possibles.

**`_refresh_snapshot_stats(acteur)`** recompose `cc/cd/ag/ch/pa/pm_def/toucher_magique/degats_*/initiative/pv_max/pm_max/deplacement_base/esquive` depuis `caracts_base` + Σ buffs vivants, puis re-clampe PV/PM. ⚠️ Snapshot sans `caracts_base` → sortie immédiate (aucune migration).

⚠️ **Trois valeurs restent FIGÉES à l'entrée** : **`actions_max`** (`_refresh_actions` calcule `actions_restantes = actions_max − Σ compteurs` → un `actions_max` mouvant offrirait des actions gratuites au cast puis un budget négatif à l'expiration), **`charge_max`** (anti-exploit) et **`attaque_profils`** (les recalculer relirait les docs d'items à chaque tour).

⚠️ **Deux garde-fous dans `_refresh_snapshot_stats`** : **`pv_max` planché à 1** — sinon un debuff de R violent met `currentPV` à 0 au re-clamp **sans lever `vivant`** : un cadavre debout que `_check_victory` ne ramasse pas, et le combat se bloque ; **une monture garde `deplacement: 0`** — elle vit dans `joueurs` donc elle est ciblable, la recalculer depuis V la remettrait en marche. Conséquence **assumée** : `pv_max = R*3 + F`, donc un debuff de F ou de R **rogne les PV courants** par le re-clamp.

**Durée = TOURS DU PORTEUR.** `_tick_effets_combat(combat_doc, acteur)` est appelé depuis **`_reset_turn_budget`**, seul hook « début de tour d'acteur » et donc générique (`_run_monster_turn` l'appelle aussi) : régén clampée → décrément + purge → `_refresh_snapshot_stats`. ⚠️ Chaque entrée porte un **`pose_tour`** : le tick du tour de pose l'épargne, sinon un effet lancé pendant son propre tour perdrait un point avant d'avoir servi. Expiration et régén sont **journalisées** (`kind:"sys"`), sans quoi la perte d'un bonus serait invisible.

⚠️ **Les effets ENTRANTS tickent aussi** (une potion bue juste avant d'entrer ne dure plus tout le combat). **Les effets restants REMONTENT** : `_finalize_membre` recopie les entrées à `restants > 0` dans `doc["effets_actifs"]` (sans `pose_tour`), principal **et** compagnons — **écrasement, jamais `extend`** (ces entrées SONT celles du personnage, copiées à l'entrée) ; `_finalize_monture` fait de même.

**Empilement** : `_empiler_effet_combat(acteur, source, effets, tour)` produit **la même forme d'entrée** que `consommables.empiler_effet` (c'est ce qui rend la remontée triviale) et passe par `poser_effet`. Appelé dans les 3 branches « sur soi » de `resolve_action`, toujours sur l'acteur actif. ⚠️ Le test « y a-t-il quelque chose à empiler ? » est la source unique **`sorts.part_durative(effets)`**, partagée par `sort_utilisable_combat`, `competence_utilisable_combat`, `consommables.effet_instantane` et les deux `empiler_effet_*` : un critère divergent entre « lançable » et « empilable » produirait un sort accepté puis sans effet.

UI : chips ✨ `#joueur-effets` (`renderEffetsActifs`). ⚠️ **Hors périmètre** : le client n'affiche les chips que pour le joueur — un ennemi debuffé ne se voit que dans le log.

#### Sur une CIBLE ENNEMIE (debuffs)
Chokepoint **`_appliquer_effet_sur_cible(combat_doc, cible, source, effets, tour, hostile=True)`** — miroir de la pose « sur soi », à trois différences : posé **seulement si le jet TOUCHE** ; ⚠️ **jamais sur une cible que le même coup vient d'abattre** ; ne remonte sur aucun doc. Appelé dans les branches `cible == "ennemi"` du sort et de la compétence.

**Un sort ou une compétence peut n'être QUE du debuff** : le garde est `degats OU part_durative` → `dmg = 0`, ligne de log dédiée, effet posé. Rien à changer côté router (`bool(eff["buffs"])` est vrai pour des deltas négatifs).

#### Sur un ALLIÉ — `cible: "allie"`
Vise un **compagnon ou une monture**. ⚠️ `CIBLES`/`CIBLE_DEFAUT` vivent dans **`utils/sorts.py`** (source unique, `competences.py` les importe comme `JETS`) et **whitelistent** la valeur : une faute de frappe retombe sur `soi` au lieu de créer un troisième comportement silencieux.

**Combat** : chokepoint **`_lancer_sur_allie(combat_doc, lanceur, cible, source, effets, portee, grid)`**, partagé par les deux branches `cible == "allie"` (sort et compétence, qui à cet endroit ne diffèrent que par le libellé) : part instantanée (`pv`/`pm` clampés aux max **de la cible**), part durative via `_appliquer_effet_sur_cible(..., hostile=False)` (« bénéficie de » au lieu de « subit »), furtivité le cas échéant.

⚠️ **Aucun jet de toucher** : on ne rate pas une main tendue — `jet` ne concerne que les cibles hostiles. ⚠️ **Pas d'interdiction « engagé au corps à corps »** : elle vise les effets OFFENSIFS à distance, l'appliquer aux soins les rendrait impossibles quand ils servent. La **ligne de vue** reste exigée au-delà du contact. ⚠️ **Un allié à 0 PV n'est pas visable** : le soigner changerait la condition de défaite ET l'ordre du tour — relever un compagnon mérite sa propre mécanique. Un allié hors de portée est refusé **avant** tout débit (`return` avant les PM).

**Exploration** : `sort_utilisable_exploration`/`competence_utilisable_exploration` n'excluent que **`ennemi`**. ⚠️ Deux personnages entrent en jeu, à ne pas confondre : le **LANCEUR** = `_acteur` (il connaît le sort, paie les PM, fournit les composants) ; la **CIBLE** = `cible_id` via **`_cible_alliee(principal, lanceur, body)`** (preuve d'appartenance = `porteurs_effectifs`).

⚠️ **`_cible_alliee` teste le LANCEUR EN PREMIER** : `porteurs_effectifs` relit les docs en base, donc viser le lanceur en passant par là rendrait un **second dict du même document** → deux `save_doc` sur un `_rev` identique, écriture perdue en silence. **`_save_cast(lanceur, cible, principal)`** persiste jusqu'à trois docs, dédoublonnés par **IDENTITÉ (`is`)** et non par id, lanceur autoritatif (409), le reste best-effort.

**UI fiche** : overlay **`#cible-allie-overlay`** alimenté par `_alliesCibles()` depuis `_grpEtat` (chargé **paresseusement** par `_assurerGroupe()`). Une seule cible ⇒ pas d'overlay. ⚠️ La cible est demandée **AVANT** l'envoi (les PM partent à l'envoi) → Échap doit résoudre la promesse à `null` (Conventions §8). Réponse : `cible_id`/`cible_nom`/`cible_vitaux` **seulement** pour un effet d'allié → `_appliquerVitauxCible` rafraîchit la carte du BÉNÉFICIAIRE ; les `vitals` de premier niveau restent ceux du lanceur.

**UI combat** : **`allyTargets(s)`** (alliés DEBOUT, hors lanceur, à portée, LoS au-delà du contact) et **`capaCibles(c)`** = source unique aiguillant ennemi/allié, consommée par les **trois** endroits qui doivent s'accorder : case grisée (`sortCastable`/`compCastable`), jetons (`renderTokens`), badges (`refreshBadgeTargets`). Ciblage **VERT** (`.ally-token.spellcast`, `.init-badge.joueur.spellcast`) là où l'offensif est violet. Les monstres sortent du ciblage pendant un cast bénéfique (pas de tir ami). ⚠️ **Une monture n'est pas dans `ordre_initiative`, donc pas de badge** — le jeton est le seul canal complet. Le lanceur s'exclut côté client (un effet sur soi se déclare `cible:"soi"`) ; le serveur le tolère. Contenu : `jsons/sorts_allies_a_importer.json`.

#### Portés par une ARME (`effets` sur un `item:*`)
Un `item:*` de catégorie `arme` peut porter le **même bloc `effets`** + un **`cible`** top-level : bolas qui entravent (`cible:"ennemi"`, `buffs:{V:-2}`, `duree:2`), lame avide qui nourrit (`cible:"soi"`).

⚠️ **Seule la part DURATIVE est exploitée** : les dégâts passent par `bonus_degats`/`bonus_degats_dice`, jamais par ce bloc. Normalisation par **`sorts.effets_d_arme(item)` → `(effets, cible)`**. `CIBLES_ARME = ("ennemi","soi")`, défaut `ennemi` — ⚠️ **`allie` retombe sur `ennemi`** : aucun jet de toucher n'a désigné d'allié, et clamper vaut mieux qu'un troisième comportement silencieux (miroir de `normaliser_sort`).

**Le profil d'attaque transporte l'effet** : `_weapon_attacks` pose `effets`/`effets_cible`/`effets_source_id` sur le profil du mode gagné — **seul** moment où les docs d'items sont relus, `attaque_profils` restant figé ensuite. Profil sans `effets` (arme ordinaire ou combat déjà en base) ⇒ rien.

**`_appliquer_effet_arme(combat_doc, attaquant, cible, profil)`**, appelé dans la branche `attaquer` **après** la mise à jour de `vivant`. Le seuil de toucher est le seul jet : un effet d'arme n'a pas de résistance propre. ⚠️ **`effets_source_id` = l'`_id` de l'arme, pas son `nom`** : c'est ce que lit `identite_source` (`id`/`item`/`_id` — surtout pas une clé `source_id` inventée, qui retomberait sur le repli `nom:`), et c'est ce qui fait qu'une arme frappant trois fois **relance** son effet au lieu de l'empiler à −6 en V. ⚠️ **Hors périmètre** : `_do_attack_on` (attaques de MONSTRE) ne porte pas de profil d'arme.

### Sorts — PM, composants, écoles
Doc `sort:*` : `{nom, icon, description, vocation, magie, niveau, cout_pm (>0 obligatoire), cible, jet, portee, effets, composants[]}`. `effets` = clés d'effets + **`degats`** (notation dés, `roll_dice` composite). Logique pure `utils/sorts.py`.

**Composants** `[{item, consomme:bool, bonus:{même schéma}}]` : **consommé** = retiré du sac (gros bonus) ; **catalyseur** (`consomme:false`) = il suffit de le porter, sac ou équipé (bonus moindre). Bonus **additifs cumulables** (`fusionner_effets`, dés concaténés `2D6+1D6+2`).

**Contexte dérivé, pas déclaré** : combat ⇔ part instantanée (degats/pv/pm) ; exploration ⇔ `cible != "ennemi"` + (pv/pm/buffs+durée).

**Apprentissage** : `character["sorts_connus"][]`. Sort de niveau n achetable si `vocations_niveaux[voc] ≥ n` + **grimoire porté** (`sous_categorie:"grimoire"`, champ `sorts:[ids]`, ⚠️ **non consommé**) + `attribute_points ≥ (n+1)×SORT_COUT_COEFF` → `POST /api/apprendre_sort`. À la **création**, les vocations de `SORT_VOCATIONS_DEPART` choisissent 1 sort niveau 0 (`characterinfo.sort_initial`, validé serveur) — ⚠️ la création filtre par **`vocation`**, pas par école.

**Accès par ÉCOLE** : l'apprentissage **post-création** filtre par l'école **`magie`** du sort (miroir du champ `magie` de `rules:vocations`), avec repli sur l'école dérivée de la `vocation` si le champ est absent → marche même sans réimport. Le perso pratique son **école native** (`ecole_native`, niveau = `vocations_niveaux[voc]`) ; seules les vocations `MAGIE_POLYVALENTE_VOCATIONS` peuvent **acheter** d'autres écoles → `character["magies_apprises"] = {ecole: niveau}`, ⚠️ niveau **par école séparé**, monté indépendamment et **sans impact sur les dérivées**. Coût = `(niveau+1)×MAGIE_ECOLE_COUT_COEFF`. Endpoints `POST /api/apprendre_magie {ecole}` (403 hors vocation polyvalente) et `POST /api/monter_magie {ecole}`. Helpers purs : `ecole_native`, `magie_de_sort`, `niveau_ecole`, `magies_pratiquees`, `ecoles_du_monde`, `peut_apprendre_magie`, `ecoles_achetables`, `cout_ecole`, `apprentissage_magies_payload`. ⚠️ Le découpage des écoles est **data-only** (`ecoles_du_monde` dérive de `rules:vocations`) : en ajouter ou en scinder une ne demande aucun code.

**Combat** : action `"sort"` (`sort_id` + `composants`, 1 action, compteur `sorts`). Cible ennemie = d100 ≤ `_magic_hit_threshold(toucher_magique, pm_def cible)` (dérivée `toucher_magique = (Int*3+Vol)//4`). ⚠️ **PM débités avant le jet** (raté = dépensés) ; dégâts **sans soustraction de PA** (la `pm_def` remplace esquive ET armure). Portée > 1 = règles ranged. Snapshots : `pm_def`/`toucher_magique` en `.get(...,0)`. ⚠️ Router = même séquence que consommer : pop des composants en mémoire → save combat → save character → finalize.

**Jet porté par la donnée** : champ **`jet`** (`cc`/`cd`/`magique`) partagé avec les compétences, `JETS` dans `utils/sorts.py`. ⚠️ **Le DÉFAUT diffère entre les deux familles, et c'est voulu** : compétence martiale par défaut (`cc`), sort **magique** par défaut (`JET_SORT_DEFAUT`) — sinon tous les sorts en base changeraient de stat de résolution. Contrepartie assumée d'un `jet:"cc"` : il contourne la `pm_def` mais **subit les PA**. ⚠️ Le mode de jet ne change **que** la résolution du toucher. Chokepoint **`_defense_physique(defenseur)`** = `ag + esquive`, partagé par les **trois** sites de jet martial (`_do_attack_on`, compétence, sort de contact) — sans lui, un buff d'esquive serait ignoré par les compétences alors qu'il compte face à une arme.

**Exploration** : `POST /api/lancer_sort` (409 PM insuffisants).

**UI** : onglet ⚡ (sorts connus + 📖 Apprentissage + 🏫 Écoles — `_renderSorts`/`_renderSortsApprenables`/`_renderSortsMagies`, `apprendreMagie`/`monterMagie`) ; en combat l'accès passe par les **slots**, ciblage **violet** (`pendingSort`/`.spellcast`). ⚠️ `sorts_epingles_effectifs` survit **uniquement** comme source de la migration à la lecture des slots ; le champ n'est plus écrit.

Contenu : `jsons/sort-exemples.json`, `update_sorts.json`, `magie_naturelle_sorts.json`, `sorts_nature_elementaire_a_importer.json`, `sorts_bataille_illusoire_noire_sainte_a_importer.json`.

### Compétences de vocation — passives + actives (miroir des sorts)
Doc `competence:*` : `{nom, icon, description, vocation, niveau, mode:"passive"|"active", cout_pm (≥0, contrairement aux sorts), cible, jet, portee, effets}` — **même schéma d'`effets` que les sorts**, sans composants. Champs perso : `competences_connues[]` + `competences_bonus`. Logique pure `utils/competences.py`.

**Choix à la création** : toute vocation **HORS `SORT_VOCATIONS_DEPART`** (complément exact ; `vocation_choisit_competence` = source unique, le client re-dérive de `SORT_VOCS`) choisit **1 compétence niveau 0** — ⚠️ un sort **OU** une compétence, jamais les deux. Sélecteur `#voc-comp-picker`, miroir de `#voc-sort-picker` ; champ `characterinfo.competence_initiale`, validé serveur (dégradé gracieux : contenu non importé → création sans compétence).

**PASSIVE = permanente** : buffs/régén dénormalisés dans `competences_bonus` (cf. §Effets à durée, source 3).

**ACTIVE = 1 action** (+ `cout_pm`). Combat : action `"competence"` (compteur `competences` — ⚠️ compté dans `_refresh_actions` ET remis à 0 par `_reset_turn_budget`, sinon action gratuite dès le 2ᵉ tour). Parts instantanée et durative s'appliquent. Cible ennemie → jet porté par la donnée : `cc`/`cd` = martial (`_hit_threshold` vs `_defense_physique`, **PA soustraits**) ; `magique` = `_magic_hit_threshold` vs `pm_def` (**sans PA**). Portée > 1 → règles ranged. Exploration : `POST /api/utiliser_competence`. ⚠️ **Règle de contenu** : toute active rendant PV/PM **doit coûter des PM** — il n'y a pas de cooldown, une active gratuite serait spammable hors combat.

**Apprentissage** : `POST /api/apprendre_competence` — `(niveau+1)×COMPETENCE_COUT_COEFF` points, `vocations_niveaux[voc] ≥ niveau`, compétence de sa vocation, **pas de grimoire**. Contenu : `jsons/competences_niveau0.json`, `new_comp0.json`.

**Furtivité & esquive** — deux clés d'effets **partagées sorts/compétences/consommables** :
- **`esquive`** (entier) = malus au seuil de toucher **physique** subi (cc/cd via `_hit_threshold`) — ⚠️ **jamais la magie**, qui passe par `pm_def`. Somme passives + effets actifs via `esquive_bonus()` → snapshot `joueur["esquive"]`.
- **`furtivite`** (>0 = état furtif ; la valeur est un bonus à l'Ag dans la difficulté de détection).

Champ **`condition`** top-level partagé : `{"battle_map_tags": [...]}`, actif en combat seulement s'il y a intersection avec (tags battle_map ∪ `zone_tags`) ; helper `condition_remplie`.

**Furtivité — règles** : jet de détection par monstre au début de son tour, seuil `50 + skill − (Ag joueur + bonus + cases × DETECTION_DISTANCE_FACTEUR)` clampé [5,95] (on repère mal de loin ; 0 = désactivé). `skill` = Vol du monstre, repli Int−10, repli Ag−30 (snapshot monstre : `vol`/`int`/`tags`/`detecte`). ⚠️ **Réussite = détection définitive** pour tout le combat. Raté → le monstre **ne vient pas au joueur** : tag `predateur` → il chasse la `proie` la plus proche (attaque généralisée `_do_attack_on` monstre→monstre ; victime `tue_par_monstre` = **xp_reward 0 mais carcasse au butin**) ; sinon **errance** (`_wander_step`).

**Rupture (chokepoint `_furtivite_apres_offensive`)** : le **corps à corps** révèle à tous (`_briser_furtivite` : attaque `ranged:false` — hast compris —, sort/compétence sur ennemi de portée 1, **touché ou raté**). À **distance** la furtivité **tient** et seule la **cible** tente un jet (`_tenter_detection`, réussite définitive) — cible **déjà détectante** ou **abattue par le coup** = aucun jet, l'embuscade continue. ⚠️ Se déplacer, consommer, ramasser ne brisent rien.

**Activation** : compétence active ou sort `cible:"soi"` avec `effets.furtivite > 0` (`_activer_furtivite` : re-furtive ET remet `detecte=False` partout) ; furtivité passive posée à l'entrée (`create_combat_doc(furtivite_initiale=…)`, calculée dans `routers/combat.py` contre les tags du terrain). UI : badge 🥷 dans l'en-tête de tour + **œil barré** `.ib-eye` sur chaque badge ennemi non-`detecte`, posé par `updateInitiativeStrip` (le doc combat part brut au client).

### Focalisation — 🧭 lieu / 🎯 quête
Un personnage focalise **UNE seule chose à la fois** : `character["focalisation"] = {type:"lieu"|"quete", cible, posee_at}`. Logique pure. `focalisation_effective` → intention `guidage`/`kill`/`collect`.

**Guidage (lieu)** : BFS sur le graphe des docs `connection` (cache TTL 60 s) → `prochaine_etape` + direction A\* (import lazy). Payload `{cible_nom, etape, link_id, porte, direction|None, distance}`.

**Biais (quête)** : `boost_zone_event` ×`FOCUS_EVENEMENT_MULT` sur les événements visés ; `espece_weights_focus` ×`FOCUS_CIBLE_MULT` sur le tirage d'espèce. Une carcasse (`item:<sub>` ↔ `espece:<sub>`) boost les combats qui la produisent.

**Effacement automatique** : arrivée au lieu, quête terminée/abandonnée, kill atteint, collect complété. `POST /api/focaliser` → `{focalisation, guidage}`. UI : boutons 🧭 (onglet 🤝) et 🎯 (onglet 📜), classe `.btn-highlight`, sidebar `#guidage-action`.

### PNJ de lieu — dialogues à choix + services
Un `lieu:*` porte `pnj:[{character:"pnj:xxx", portrait, image?, probabilite, description}]`. Tirage de présence à l'ENTRÉE (`poser_pnj_present`), champ transitoire `character["pnj_present"]`. Si un PNJ est présent, l'`image` de l'entrée remplace celle du lieu (repli silencieux sur la version `_vide`) et le bouton sidebar 🗣 apparaît.

Doc **`type:"pnj"`** : `{nom, race, vocation, portrait, description, dialogue, services}`. **Dialogue** = arbre embarqué `{noeud_depart, noeuds:{id:{texte, texte_gratuit?, choix:[{id, label, next?, action:{service}?, condition?, deplacer?}]}}}`. Choix **filtrés serveur** par condition (`relation_min:{lieux[…OU logique], seuil}`, `intro_raison`, ou tout **flag booléen** du contexte), adressés par `choix_id`. Placeholders `{prenom}`/`{cout}` + toute clé de `contexte["placeholders"]`.

**Service `soin`** : `{cout_cuivre, fraction_pv, gratuit_si:{lieux, seuil (défaut PNJ_REPUTATION_SEUIL), fraction_pv}, noeuds:{fait, sans_fonds, inutile}}` — gratuit ET plus efficace si une relation ≥ seuil ; routage des nœuds de résultat côté serveur (⚠️ PV pleins ou bourse vide = rien débité).

**Service `don`** : `{item, quantite, cout_cuivre, gratuit_si:{lieux, seuil}, noeuds:{fait, sans_fonds, trop_charge}}` — ⚠️ contrôle de **charge** avant remise. Helpers purs `don_effectif`/`appliquer_don`. ⚠️ `noeud_client` ne reçoit que le service **soin** → **pas de `{cout}` ni de `texte_gratuit` dans les nœuds de don**. Réponse `{don, purse, inventaire_payload}` (`_applyInventoryPayload` côté client).

**Hook `"deplacer": "lieu:xxx"` sur un CHOIX** (n'importe quel choix, aucun service requis) : le serveur résout la `connection` reliant le lieu courant à la destination (`_lien_vers`) et renvoie `reponse["deplacer"] = link_id` ; le client enchaîne sur **`moveTo(link_id)`**. ⚠️ **On ne déplace JAMAIS le personnage dans `routers/pnj.py`** : le déplaceur porte une quinzaine d'effets de bord (quêtes `visite`, focalisation, XP de découverte, sol transitoire, événement de zone y compris combat, conclusion d'intro, courses échues, régén de tour) que recopier ferait diverger — et sa garde 403 reste la seule autorité sur le passage. ⚠️ Résolu **APRÈS** l'action, sinon le laissez-passer que le gardien vient de poser ne serait pas encore là. Lien manquant = **silencieux** (le joueur y va à pied) ; c'est le linter et le BFS qui l'attrapent. ⚠️ Jamais sur un choix qui déclenche un combat (`combat_id` est testé avant `deplacer` côté client).

Endpoints **stateless** (`GET /api/pnj/dialogue`, `POST /api/pnj/dialogue/choix`) : actions revalidées et débitées à l'exécution. Logique pure `utils/pnj.py` (`relation_value_fn` injectée). UI : `#pnj-panel` ; portraits servis par le mount **`/pnj`**. Contenu : `jsons/dialogues_a_importer.json`, `pnj-*.json`.

### Accès conditionné à un lieu — PNJ gardiens
Un `lieu:*` peut porter un bloc **`acces`**, ⚠️ sur le lieu de **DESTINATION** et jamais sur la `connection` : un lieu peut avoir plusieurs portes, la barrière est une propriété du lieu, pas du chemin. `{gardien, refus, cycle, conditions:[...]}` — `gardien`/`refus` sont **informatifs** (lore, texte du 403). `conditions` = **ET logique** ; vide ou absent ⇒ lieu libre.

**Trois clés** :
- **`quete_active:{lieu?, types?, giver_categorie?, cible?, objectif_atteint?}`** — une entrée de `quetes_actives` doit satisfaire TOUS les filtres fournis (`lieu`/`cible` lus sur `q["objectif"]`, `giver_categorie` via `get_doc(q["giver"]).categorie`). ⚠️ **`objectif_atteint: false` = « quête encore À FAIRE », et c'est LUI qui ferme les boucles de donjon** : une quête accomplie reste dans `quetes_actives` jusqu'au turn-in, donc sans ce filtre elle continue d'ouvrir la porte et le joueur rejoue le combat (et encaisse le butin) autant de fois qu'il veut. `true` exige l'inverse ; absent ⇒ aucun filtrage. ⚠️ `quetes.objectif_atteint` est appelé par **import paresseux** (`utils.quetes` tirerait bois/expedition/recrutement/marche dans un module que `utils.lieux` importe).
- **`item:{item, lieu_parent?}`** — miroir de `recrutement.acces_autorise`.
- **`rang_min:{cite, rang}`** — le rang de guilde **dans cette cité** (`character["rangs_guilde"][cite]`, absent ⇒ `RANGS[0]`) doit atteindre `rang` sur l'échelle **`recrutement.RANGS`**, ⚠️ lue à sa source et jamais recopiée (elle a déjà changé de longueur une fois).

⚠️ **FAIL-CLOSED partout** : clé inconnue **refuse** ; `cite`/`rang` manquant ou hors échelle **de part ou d'autre** refuse aussi — on n'ouvre pas une porte sur une comparaison qu'on ne sait pas faire. Le garde-fou contre le contenu muet est le **linter**, pas une permissivité du moteur. `relation_min` = point d'extension documenté, non câblé.

**Laissez-passer PERSISTANT** : `character["laissez_passer"] = {lieu_id: {pose_at, par, cycle}}`. Il mémorise le **`cycle`** émetteur (`lieu["acces"]["cycle"]`, défaut 1) : ⚠️ changer le cycle du lieu périme le laissez-passer **sans une ligne de code** — il suffira d'incrémenter `cycle` pour rouvrir un donjon.

Logique pure `utils/acces.py` : chokepoint **`acces_autorise(character, lieu_doc, get_doc_fn) -> (ok, raison)`**, ordre `kill-switch → pas de barrière → laissez-passer valide → conditions`. World-var **`ACCES_GARDIEN_ACTIF`** = déverrouillage d'urgence, utile si un joueur s'enferme dehors ou pour isoler un bug de rendu d'un bug de condition.

**Verrou = lien caché + garde 403 autoritative.** `get_lieu_links` prend **`filtrer_acces: bool = True`** : un nœud dont le lieu est refusé fait écarter toute la connexion (⚠️ le lieu **courant** n'est jamais filtré — seul un nœud DESTINATION peut fermer le lien). ⚠️ **Ce filtre d'affichage n'est PAS un verrou** : `move_character` (branche « lien ») l'appelle en **`filtrer_acces=False`** et pose sa propre garde 403 juste après `if lieu_doc:` — sinon l'enforcement serait un effet de bord d'une fonction de rendu, avec pour message « Incorrect movement info » au lieu du texte de `acces.refus`.

**Service PNJ `acces`** (miroir de `services.rang`) : `{lieu, noeuds:{ouvre, refus, deja?}}` — ⚠️ `lieu` est le **SEUL lien** PNJ → lieu gardé (aucun `find_docs`, aucun id en dur). `_contexte` pose `acces_ouvrable`/`acces_refuse`/`acces_ouvert` + le placeholder **`{portail}`**. `_resoudre_acces` (op `passer`) : laissez-passer valide → `noeuds.deja` sans muter ; conditions non remplies → `noeuds.refus` sans muter ; sinon `poser_laissez_passer` → save → `noeuds.ouvre`. ⚠️ La réponse porte `acces` **et `links` = `get_lieu_links(current_user)`** : sans `links`, le lieu gardé n'apparaîtrait qu'au prochain rechargement de `/play` (la liste des sous-lieux a été rendue à l'ouverture de la page). Client : `if (data.acces) { toast + LINKS = data.links; buildLocationslist(); }`.

⚠️ **DEUX natures de porte, selon la `categorie` du lieu gardé.** Un lieu **explorable** reçoit un laissez-passer et apparaît dans la liste des sous-lieux. Une **salle de donjon** (`categorie:"battle_map"`) n'a rien à visiter : franchir la porte **OUVRE LE COMBAT** (`_declencher_combat_donjon`) et **aucun laissez-passer n'y est posé** — chaque descente est un engagement neuf, donc `noeuds.deja` y est structurellement inatteignable (ne pas l'écrire). La réponse porte `combat_id` → le client redirige **avant** de rendre le nœud suivant, qu'on ne verra pas.

⚠️ **L'état de la QUÊTE et l'état du LIEU sont deux choses.** **`acces_accompli`** = commission accomplie **mais pas encore rapportée** (un laps de temps, qui redevient faux au turn-in). **`acces_libere`** / **`acces_menace`** = la menace derrière la porte est éliminée ou non — l'état du **monde**, qui **survit au rapport** ; c'est lui qui permet à un gardien de raconter ce qui a changé une fois la commission archivée. Source : `donjon.donjon_purge` (commission active à objectif atteint **OU** archive d'une commission soldée visant ce lieu — d'où `source`/`lieu` dans l'entrée archivée par `solder_commission`, clés inertes ailleurs).

⚠️ **`acces_libere` et `acces_menace` sont un COUPLE, et c'est structurel** : `pnj.condition_ok` **n'a pas de négation**, donc la variante « la menace court toujours » a besoin de son propre flag. Patron à reprendre pour **toute** réponse de dialogue variant selon l'état : deux choix de **même label**, ids distincts, conditions complémentaires — le joueur n'en voit jamais qu'un.

⚠️ **Le gardien doit avoir un mot pour « c'est fait »** : sans `acces_accompli`, la barrière se referme (grâce à `objectif_atteint: false`) et le gardien récite son refus générique à un joueur qui vient d'abattre la cible. ⚠️ **`acces_refuse` EXCLUT ce cas** (`not ok and not accompli`), sinon le refus ET les félicitations s'afficheraient ensemble.

⚠️ **Ne jamais donner de `probabilite < 1` à l'entrée `pnj` d'un gardien** : un gardien absent au tirage rend le lieu **définitivement inatteignable**.

**Linter** : un lieu gardé n'a le plus souvent **AUCUN `dialogue`** → `analyser()`/`analyser_doc` traitent un doc comme concerné dès qu'il porte `dialogue` **OU** `acces`, sans quoi le contrôle fail-closed ne s'exécuterait jamais sur le lieu qui en a le plus besoin. `conditions_invalides(lieu_doc)` signale les clés inconnues **et les SOUS-FILTRES inconnus** (`SOUS_FILTRES_CONNUS`). ⚠️ Cette seconde vérification est **la plus importante** : une clé de 1er niveau inconnue refuse (donc visible en jeu), un sous-filtre inconnu est **ignoré** — la barrière devient plus PERMISSIVE, en silence. Un `objectif_atteint` mal orthographié rouvrirait la boucle du donjon sans aucun symptôme.

Contenu de référence : **`dev/gen_acces_donjon.py`**. ⚠️ `jsons/acces_gardien_george_dourdan_a_importer.json` est un **premier jet périmé** (il pose un `refus` et une condition `types` que le générateur a remplacés) — **ne pas le réimporter**. **Dette assumée** : l'objectif `eradication` multi-espèces n'existe pas (la condition `types` l'accueillera sans code) ; le cycle de reset n'est pas câblé (crochet `acces.cycle`/`acces.revoquer` en place).

### Donjons & commissions d'éradication
Un **donjon** est un lieu de combat FERMÉ : on n'y marche pas, on y **descend** par une porte gardée, et il faut un mandat. Doc **`donjon:*`** : `{nom, description, portail (informatif), niveau_max?, battle_maps:[{lieu, especes:[espece:*], niveau_max?}]}`. Logique pure `utils/donjon.py`.

⚠️ **POURQUOI un doc à part et pas des `rencontres`/`zone_influences` sur le lieu** : une salle est un `categorie:"battle_map"` — ni `connection`, ni `lieu_parent`, ni grille. Elle n'a donc pas de zones d'influence où placer des espèces, et `resolve_profil_weights` n'a rien à y résoudre. Le contenu d'un donjon est **CURATÉ** salle par salle, celui d'un lieu explorable est tiré par géométrie. `donjon_de_lieu(lieu_id, find_docs)` est le **SEUL** lien salle → donjon : une battle map ignore à quel donjon elle appartient (elle reste tirable comme décor ordinaire par `combat.select_battle_map`), c'est le donjon qui la revendique.

⚠️ **`niveau_max` EST LE BOUTON DE DIFFICULTÉ, et il n'est pas optionnel en pratique.** Un lieu explorable borne implicitement ses grades par la distribution de ses zones ; un donjon n'a pas de zones, donc **RIEN ne le borne** — sans plafond, l'élite reçoit le profil de plus haut niveau de TOUTE la base, imbattable pour un joueur de rang débutant. Il se pose par **salle** (elle prime) ou pour le donjon entier (`niveau_max_de`), et vaut pour **toute** la salle — élite **et** escorte (`_profils_sous_plafond`) —, sinon l'accompagnement pèserait plus lourd que la cible mandatée. Un plafond n'admettant aucun profil retombe sur les plus bas niveaux : mieux vaut un donjon trop facile qu'un donjon vide. ⚠️ Le plafond ne rattrape pas une **espèce** hors calibre (un golem de pierre est un mur à tous les grades) — c'est un choix de casting, pas de réglage.

**La commission est une quête `chasse` ORDINAIRE**, pas un troisième système : `objectif = {type:"chasse", cible, lieu, profil, quantite:1}`, donc progressée par `quetes.maj_progress_chasse` et focalisable, **sans une ligne ajoutée dans `utils/combat.py` ni `utils/quetes.py`**. Seule sa GÉNÉRATION diffère (tirée dans le doc donjon, pas dans les zones). ⚠️ Elle se distingue d'une épreuve de rang par **`source == "commission"`** — `utils/chasse.py` filtrant partout sur `source == "rang"`, les deux familles ne se confondent jamais. Une seule commission active à la fois, **pas de `unique`** : c'est un contrat répétable. `solder_commission` paie XP + prime **sans promouvoir**.

⚠️ **Aucune `position` dans l'objectif** : on entre par le gardien, pas en marchant sur une case — `chasse.dans_zone_chasse` lit alors la seule contrainte de lieu. Corollaire : **`quetes._carte_chasse` refuse de rendre une carte 🗺️ sans `position`**, sans quoi l'overlay recadrerait sur (0,0) et enverrait le joueur au mauvais endroit.

**Service PNJ `commission`** (miroir de `services.rang`) : `{donjon, noeuds:{accepte, rapporte}}` — `donjon` est le SEUL lien PNJ → donjon. Flags `commission_offerte` / `commission_en_cours` / `commission_a_rapporter` (⚠️ « en cours » **exclut** « à rapporter » : l'élite abattue, ce n'est plus une relance mais un rapport à rendre) ; placeholders `{espece}`/`{lieu}`/`{xp}`/`{prime}`. Ops `accepter`/`rapporter` dans `_resoudre_commission`.

⚠️ **L'offre n'est PAS mémorisée** (pas de champ transitoire, contrairement à `transport`/`rang`) : `offre_commission_pour` la **rebâtit à chaque rendu de nœud**. La cible peut changer entre deux ouvertures du dialogue, et celle réellement engagée est celle du tirage de l'`accepter` — c'est le nœud de résultat qui la récite, jamais un texte périmé (assumé). ⚠️ Conséquence de perf : `tirer_cible` ne requête les profils **qu'une fois** (et non une fois par espèce), parce que `_contexte` l'appelle à chaque interaction.

**Combat** : `_declencher_combat_donjon` — miroir simplifié de `start_combat`, trois différences assumées : pool d'espèces curaté ; **élite GARANTIE** (franchir la porte EST l'événement de chasse, là où `start_combat` ne marque que si le tirage naturel a fait apparaître l'espèce) ; **aucune furtivité d'entrée**. ⚠️ L'anti-doublon de `start_combat` est repris tel quel — un combat déjà actif est REPRIS, sinon repasser devant le gardien laisserait des combats orphelins.

⚠️ **UN BLOC `acces` N'EST PAS UNE PORTE — il faut AUSSI un doc `connection`.** Le bloc dit à quelles conditions on franchit ; c'est la `connection` qui creuse. Sans elle, le gardien pose son laissez-passer, `get_lieu_links` ne trouve aucun lien à révéler, et le lieu est **structurellement inatteignable — sans aucun message d'erreur** : le dialogue réussit, le panneau se ferme, et le joueur est exactement où il était. Le piège s'est pris deux fois. Contrôle qui l'attrape en une passe : **BFS sur les docs `connection` depuis la cité, barrières ignorées** — un lieu à zéro voisin est un cul-de-sac, quoi que dise son `acces`. Gabarit d'une porte entre deux sous-lieux : `pos: [0,0]` de part et d'autre (aucun n'a de grille) et un **`label` par nœud** nommant le GESTE (« monter l'escalier du fond ») et non le lieu, car `get_lieu_links` en fait le libellé du bouton (`node["details"]["label"] = node.get("label") or doc.get("label")`). ⚠️ La vue `reseau/liens_cases` lit **`nodes[0]` et `nodes[1]` en dur** : une connexion a exactement DEUX nœuds.

Contenu : `dev/gen_acces_donjon.py` génère `acces_donjon_saint_austrelin_a_importer.json`, `acces_donjon_mine_a_importer.json` et `acces_donjon_bureau_connexion_correctif.json`. Chaîne : rang D à Auxerre → **Borin** ouvre le bureau (`rang_min`) → **Gautier de Valcroix** mandate la commission → **George Dourdan** contrôle le PRINCIPE (mandat de guilde, sans filtre de lieu) → **Armand de Vaucremont** contrôle la DESTINATION (`lieu` = la mine) et ouvre le combat.

### Intro narrative — fuite du village natal
Bloc **`intro`** sur le doc lieu de la cité : `{titre, texte, texte_conclusion, xp_conclusion, position_depart:{x,y}, zone_securite:"zone::coeur_ville", raisons:[{id, label, texte_suite}]}` (placeholders `{prenom}/{nom}/{race}`).

**Création** (`add_character`) : si la cité porte le bloc → spawn à `position_depart` (périphérie, zones à monstres sur le chemin) + `character["intro"] = {statut:"en_cours"}` ; ⚠️ clé absente = rétro-compat totale. **Premier `/play`** : overlay `#intro-overlay` (non fermable) → choix de la **raison** via `POST /api/intro/raison` (persistée, sert aux conditions `intro_raison`) → l'overlay ne revient plus.

**Conclusion** dans `move_character` (les 2 branches) : `conclure_si_en_securite` quand la position entre dans `zone_securite` (helper géométrique `est_dans_zone`, `utils/zones.py` ; ⚠️ zone absente = conclusion au 1er déplacement) → statut `terminee` + XP + overlay (`intro_terminee` dans la réponse ; ⚠️ la branche « lien » est rejouée après reload via `sessionStorage` `intro_fin_notif`). Logique pure `utils/intro.py`. Contenu : `jsons/ville_a_importer.json` (docs complets avec `cells` — ⚠️ **généré par script, jamais écrit à la main**).

### Mode « Lieux » — éditeur de carte
6ᵉ mode d'`/admin/editor` : affiche les **points cliquables** aux positions des connexions du lieu courant. `GET /api/lieu/{id}/connections` = requête range sur la vue `reseau/liens_cases`, chaque node enrichi de `details` (doc lieu sans `cells`/`_rev`/`_id`). ⚠️ **Ne peint jamais la grille** (drag désactivé) ; le clic sélectionne la case (`lieuxSelectedCell`) et filtre la liste latérale. **Overlay fiche** `#lieu-fiche-overlay` = réplique de `play_town` : image (cascade `towns→battle_maps→maps`), sous-lieux cliquables (`.lf-subbtn`, rechargent la fiche sur le voisin, idempotent), destinations sans `cells` en image fit.

Le sélecteur de mode est une **liste déroulante** (`#mode-select`), pas des onglets. `setMode` reste le seul writer d'`editMode` ; ⚠️ `updateBattleMapTabs` pose `hidden` **ET `disabled`** sur les `<option>` Zones/Rencontres/Ressources — Safari ignore `hidden` sur une option.

**Création d'un sous-lieu** (`➕`) → overlay `#lieu-add-overlay` qui écrit **deux docs** par `PUT /admin/doc` : le `lieu:<slug du label>` (image seule — ni `dimensions` ni `cells`, comme toutes les boutiques : il n'apparaît donc **pas** dans le sélecteur de lieux, `get_lieux_ids` filtrant sur `cells`) **puis** le `link:<categorie><NN>_to_<parent>` (`NN` = 1 + le plus grand présent dans `lieuxConnections`). ⚠️ **Le lieu d'abord** : une connexion orpheline ferait échouer l'enrichissement `details` de `get_lieu_connections`.

Le `character` du PNJ est déduit en `pnj:marchand_<categorie>` (avertissement si le doc manque) ; ⚠️ `nom`/`portrait` vides ne sont **pas écrits**, pour que `pnj_payload` retombe sur le doc PNJ — d'où un portrait **générique** (`marchand_<race>_<sexe>_<cat>.png`) qui ne déduit aucun nom, là où un portrait **nommé** (`marchand_<prenom>_<nom>_<cat>.png`) en donne un. ⚠️ **La convention de nommage des images de lieu n'est PAS dérivable de la catégorie** (`laboratoire_d_alchimie` → `cabinet_alchimie_*.png`, `fletcher` → `archerie_*.png`) : le filtre est un **recouvrement de jetons** qui retombe sur la liste complète quand il ne rend rien — ne jamais le durcir en préfixe.

**Édition/suppression** (`🧾 JSON`) : deux `<textarea>` (doc lieu + doc connexion) avec 💾 `PUT /admin/doc` et 🗑 `DELETE /admin/doc?id=` — supprimer la porte et supprimer la boutique sont deux gestes distincts. ⚠️ **`node.details` est RETIRÉ avant affichage et écriture** (`_connNu`) : c'est une injection à la volée de `get_lieu_connections`, réécrire l'objet tel quel persisterait la copie enrichie du doc lieu dans le doc connexion.

**`GET /api/lieux/creation_options`** (admin) = source unique du formulaire : catégories (distinct `lieu.categorie` ∪ `recette.lieu_categorie`), fichiers de `templates/resources/towns` et `/pnj`, docs `pnj:*`, `lieu_ids`. ⚠️ **`lieu_ids` sert au contrôle de collision d'`_id`** parce que `GET /api/lieu/{id}` ne peut pas le faire : son `raise HTTPException(404)` est *dans* son propre `try/except Exception` et ressort en **500**. ⚠️ Les `find_docs` y sont **projetés** (`fields=[...]`) — sans quoi lister les lieux rapatrierait les `cells` de chaque carte.
