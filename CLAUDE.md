# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Telluris is a browser-based medieval-fantasy RPG. The backend is a FastAPI server serving Jinja2 HTML templates; the database is CouchDB. There is no separate JS framework — all interactivity is vanilla JavaScript embedded in the templates.

## Running the app

```bash
docker compose up
```

FastAPI listens on `http://localhost:8000`. CouchDB listens on `http://localhost:5984`. The compose file installs Python dependencies at container start (no pre-built image).

## Running tests

```bash
pytest tests/
```

Tests only cover pure-Python logic (stats, combat à distance, marché/recettes, consommables, sorts) and have no DB dependency.

> **Environnement de l'agent : Python EST disponible en local (2026-07-03)** — lancer `pytest tests/` directement depuis le shell pour valider la logique pure (Python 3.12, pytest installé). CouchDB reste injoignable en local : `db/config.py` tolère l'absence de connexion à l'import (`server`/`db` = `None`, les helpers renvoient `None`) pour que les tests purs se collectent. Docker/l'app tournent côté utilisateur (`docker compose up` dans le conteneur).

## Inspecting live DB values

La CouchDB live tourne sur un hôte distant, généralement NON joignable en local. Pour connaître les valeurs réelles des documents (races, espèces, profils, lieux, items…), lire le dump JSON committé à la racine : `telluris-dump-YYYYMMDD-HHmmss.json` (le timestamp change ; produit par l'export admin `GET /admin/exports/couchdb` / `db.config.dump_all_docs()`). C'est un objet `{"db","exported_at","doc_count","docs":[...]}` ; `docs` exclut les `user:*`. Repérer un doc via grep sur `"_id": "rules:races"`, etc. Export ciblé d'un seul type : `GET /admin/exports/by-type?type=<type>` (`find_docs({"type": t})`, `user:*` exclus) → fichier `<type>-AAAAMMJJ-HHMMSS.json` ; la page `/admin/exports` propose une liste à saisie libre des types présents en base. **Édition en tableau** : la page `/admin/table` (`admin_table.html`, carte « Mise à jour en tableau » dans `/admin`) liste les docs d'un type choisi en tableau (colonnes choisies/ordonnées par drag, triables, filtrables, redimensionnables) ; cliquer une ligne ouvre le JSON dans un overlay fixe à droite, **Save** = `PUT /admin/doc` (réattache le `_rev` courant) / **Cancel** ferme / **Delete** = `DELETE /admin/doc?id=…` après `confirm()` (le `_rev` est relu en base, jamais celui du client ; `db.delete_doc` renvoyant `None` succès comme échec, le serveur vérifie par relecture → 409 ; la ligne est retirée localement, sans rechargement du type). Données : `GET /admin/table/data?type=<t>` (`user:*` exclus). Les préférences d'affichage (colonnes/ordre/tri/filtres/largeurs) sont mémorisées **par type** dans `localStorage` (`telluris.admin_table.v1.<type>`). **Export** : deux boutons au-dessus du tableau exportent les lignes **actuellement affichées** (filtres+tri, `computeVisibleRows`) — **⬇ Export JSON** (docs complets, tableau JSON) et **⬇ Export Excel** (`POST /admin/table/export.xlsx` → writer OOXML partagé `utils/xlsx.py`, une colonne par clé de 1er niveau, valeurs imbriquées en JSON). Nom de fichier commun `exportFilename(ext)` = `<type>_filtre_<col>_<val>…_AAAAMMJJ-HHMMSS.(json|xlsx)` (horodatage **UTC**, format `AAAAMMJJ-HHMMSS` aligné sur les exports serveur `datetime.utcnow()`).

### Échelle des caractéristiques (×10, sauf V)
7 caractéristiques à l'échelle ×10 (F/R/Ag/Vol/Int/Cha/Ch ≈ 10-100). V = 1-10 (base raciale ~4-5, max ~7-8), `deplacement = V` cases/tour. Formules (joueur + monstres) : `cc = (F + Ag*3)//4`, `cd = (Ag*3 + V*10)//4`, `initiative = (Ag + V*20)//3`, `actions_max = max(1, ceil(Ag/40 + V/2))` → **Ag est la god-stat**.

### Références d'items & poids
Entrée d'inventaire = **string legacy** `"item:xxx"` (poids = min) **ou object** `{"item": "item:xxx", "poids": <nb>}`. Doc `item:*` `poids` = nombre OU `[min,max]`. Helpers : `item_ref_id`, `poids_bounds`, `item_ref_weight`, `resolve_item_ref`. Actions client adressent par **index+item_id** (instances d'un même item peuvent peser différemment). Une référence peut aussi porter **`lieu_parent`** = le lieu qui a délivré CET exemplaire (`item_ref_lieu`) : le doc item reste **générique** (une seule `item:carte_aventurier` pour toutes les guildes) et `resolve_item_ref` — chokepoint d'affichage, le client ne rend que `nom` — en dérive le label **« Carte d'aventurier (Auxerre) »** (`item_label`). Jamais de `lieu_parent` sur le doc item.

### Charge & surcharge
`charge_max_of(character)` = `F*5`. `carried_weight(character)` = inventaire + équipés. Exploration : déplacement bloqué si surcharge, au pickup items tombent au sol. Combat : demi-charge = déplacement ÷2. Sol (`objets_au_sol`) = transitoire, vidé à chaque déplacement.

### Combat & butin
Doc `combat:*` = snapshots `joueurs[]`/`monstres[]`, `ordre_initiative`, `battle_map_id`. Stats monstres = `espece:*` (min/max) modulées `profil:*` (niveau, deltas). `finalize_combat()` : XP/PV + butin (idempotent atomique). Butin victoire = pas auto-ajouté, proposé overlay, encaissé `POST /api/combat/{id}/collect`. Carcasses = `item:<sub_id>`.

### Attaques par mode — corps à corps / jet / tir
Mode via tag : `tir` (arcs), `jet` (lancer), sinon **cac** (hast = cac `portee ≥ 2`). Champs item : `portee` (défaut 1), `restriction:{caract:min}` (ET). `restriction_satisfaite` → blocage dur `equip_item` (422). `_weapon_attacks` = `joueur["attaque_profils"]` (1 par mode, meilleure portée, poings portée 1 toujours présent). Chaque profil : `mode`, `portee`, `ranged`, `toucher` (cc/cd), `degats` (cc/cd). **cac** = cc/F, portée item ; **jet** = cd/F, portée `item + F//JET_PORTEE_F_DIV` ; **tir** = cd/Ag, portée item. `resolve_action` sélectionne profil. **Règles ranged** : interdit si engagé (1 case), exige ligne de vue (Bresenham `seeThroughCell` — falaise transparente, mur seul bloque —, `nav` ignoré). UI (refonte 2026-07-07) : **plus de sélecteur de mode** ; **3 boutons d'attaque directs** `.atk-mode-btn` (⚔ Mêlée `cac` / 🪃 Jet / 🏹 Tir) dans la barre d'action, chacun **visible seulement si le mode est équipé** (`updateAttackButtons`) et **actif seulement s'il a une cible attaquable** (`updateButtons` : `targetableMonsters(mode)`) → tous les modes possibles dispo simultanément. `triggerAttack(mode)` fixe `currentMode` puis attaque directe (1 cible) ou ouvre le sélecteur de cible (masque les boutons via `.hidden-selecting`). `currentMode` pilote la visibilité des cibles ; les **badges du bandeau d'initiative** (`.init-badge.monstre`) servent aussi de ciblage — bordure grise hors portée, **rouge + cliquables** (attaque, `refreshBadgeTargets`) uniquement quand attaquables (tour + action + portée), miroir du clic sur `.monster-token.adjacent`. Monstres = mêlée seule. Tests purs `tests/test_combat_ranged.py`.

**UI panneaux combat** (`combat_telluris.html`, refonte 2026-07-04) : panneau perso = reprise du `<section class="character-panel">` de play_town — portrait recadré du joueur (`#left-portrait.pt-crop` via `applyPlayerPortrait`, carré, barres PV/PM verticales), identité, pips d'actions + jauge de charge (pas de mini-stats). Vie des ennemis = **anneaux PV** sur les badges du header (`setRing`/`MONSTER_CIRC`) + grand portrait du dernier ciblé (plus de liste d'ennemis). Carte iso : `MAX_H`=10 rangées, `--step` borné à la **seule largeur** (`max(8, w/17)`) → hauteur agrandie sans toucher la largeur, page défilable.

## Core Design Patterns

### CouchDB document IDs
Pattern `type:identifier` — e.g. `user:email@example.com`, `lieu:lutecia`, `rules:races`. Characters = `character:<user_id>_<uuid>`.

### Derived stats are never stored
`DerivedStats` recalculated by `compute_derived_stats()` at request time. Never persist derived values.

### Character document vs. Pydantic model
`models/character_document.py` = reference spec. Ground truth = `routers/user.py` creation code. Field names differ: `voc`, `sex`, `caracteristiques_standard`/`current`, `cite`.

## Core Mechanics

### Échelle des caractéristiques (×10, sauf V)

### Navigation bitmask
8-direction via `nav` dict (bit 1=HAUT, 2=HAUT_DROITE, …, 128=HAUT_GAUCHE). `VALID_MOVES` (source unique, `utils/lieux.py`) → `MOVE_OFFSETS`. **Combat partage** : `_find_path` (A*) et `_reachable_region` (flood fill) utilisent mêmes directions + `nav_allows`. ⚠️ **Pas 4 directions** (îlots diagonaux). `create_combat_doc` : `grid = {dims, cells, nav}` — sans `nav`, placement ≠ déplacement. Même jeu + même masques.

### Charge & surcharge
`charge_max_of(character)` = `F*5` (dérivée, jamais stockée). `carried_weight(character)` somme les poids effectifs de l'inventaire **+ équipés** (pas le sol). En **exploration**, si `carried_weight > charge_max` le déplacement est bloqué (garde 409 dans `move_character`, flèches désactivées côté client) ; au pickup, le dépassement fait tomber des items **aléatoires** au sol. En **combat**, au-delà de la **demi-charge** le déplacement est divisé par deux (`utils/combat.py`). Les objets au sol (`objets_au_sol`) sont **transitoires** : vidés dès un déplacement réel.

### Combat & butin (`utils/combat.py` + `routers/combat.py`)
Un combat est un doc `combat:*` (snapshots `joueurs[]`/`monstres[]`, `ordre_initiative`, `battle_map_id`). Les **stats dérivées des monstres** viennent de `espece:*` (min/max) modulées par `profil:*` (niveau, deltas). `finalize_combat()` applique XP/PV **et** le butin ramassé en combat, de façon **idempotente atomique** (id du combat dans `character["combats_recompenses"]`, même doc que l'XP). Le butin de victoire n'est **jamais** auto-ajouté : `butin_disponible` (poids tiré au niveau du profil via `random.choices`) est proposé dans l'overlay, encaissé par `POST /api/combat/{id}/collect` (borné par `charge_max`). Carcasses = `item:<sub_id>` (1-pour-1 avec `espece:<sub_id>`), créées à la volée si absentes.

### Critiques pilotés par la Chance (2026-07-18)
**Ch enfin mécanique.** Tout jet d100 offensif (arme cac/jet/tir, sort, compétence — quel que soit son `jet` cc/cd/magique — et attaque de monstre, y compris monstre→monstre) passe par **deux helpers uniques** de `utils/combat.py`, au lieu du `seuil → roll → if` qui était copié-collé sur 4 sites :
- **`_seuils_critiques(attaquant, defenseur)`** → `(seuil_reussite, seuil_echec)`. `delta = Ch_att − Ch_cible`, les **deux** fenêtres glissent de `delta // CRIT_CHANCE_DIVISEUR` : la chance élargit la réussite critique ET repousse l'échec, **symétriquement**. Les world-vars génériques `CRIT_REUSSITE_MAX` (5) / `CRIT_ECHEC_MIN` (96) restent des **garde-fous bornants** (`max(base_ok, …)` / `min(base_ko, …)`) → le glissement ne peut que jouer en faveur du plus chanceux, un jet ≤ 5 est toujours un crit et un jet ≥ 96 toujours un fumble. `CRIT_CHANCE_DIVISEUR = 0` désactive tout.
- **`_resoudre_jet(attaquant, defenseur, seuil)`** → `{roll, seuil, touche, critique, fumble, mult_degats}`. Le **critique PRIME sur le seuil de toucher** : une réussite critique touche même si le seuil était raté, un échec critique rate même si le seuil passait.

**Réussite critique = dégâts ×2**, multiplicateur appliqué **AUX DÉS, avant la soustraction des PA** (`roll_dice(...) * mult - pa`) : le crit double le coup, pas la pénétration d'armure. La magie n'ayant pas de PA à soustraire, le ×2 y joue seul.

**Échec critique = une action de plus perdue** (`_appliquer_fumble`). ⚠️ `actions_restantes` n'est **jamais décrémenté**, il est **recalculé** par `_refresh_actions` depuis des compteurs → une pénalité DOIT être un compteur (poser `actions_restantes = 0` serait écrasé au prochain refresh). Deux champs : **`penalites`** (compté dans `used`, remis à zéro au reset de tour) et **`dette_actions`** (ce qui n'a pas pu être payé faute d'action restante, **survit au reset** : `_reset_turn_budget` le convertit en `penalites` du nouveau tour puis l'efface — c'est le « reporté au tour suivant »). `penalites` entre aussi dans les **projections de déplacement** (`projected > actions_max`), sinon un fumble serait indolore pour qui se contente d'avancer. Un perso à `actions_max == 1` qui fumble perd donc tout son tour suivant (assumé).

⚠️ **`_do_attack_on` décompte désormais l'action de l'attaquant lui-même** (`attaques += 1` + `_refresh_actions`), au lieu de laisser ses 2 appelants le faire après coup : le test de fumble a besoin d'un budget déjà à jour. Aux 3 sites joueur, `_appliquer_fumble` est appelé **après** l'incrément du compteur d'action.

Snapshots : `ch` ajouté aux **deux** constructeurs (`build_joueur_snapshot` = valeur **avec buffs**, `build_monster_snapshot`). Tous les accès en `.get("ch", 0)` → un combat déjà en base tourne avec delta 0 = comportement d'avant. ⚠️ **Données** : beaucoup d'`espece:*` ont encore `Ch = {min:0, max:0}` → delta large en faveur du joueur, à peupler. Log : nouveaux `kind` **`crit`** (raffiné `j-crit`/`m-crit` côté client, la classe brute `crit` servant au rendu Jinja initial qui ne connaît pas cette bascule) et **`fumble`**. Tests purs `tests/test_combat_crit.py` (18).

### Monnaie & marché
3 paliers : Or/Argent/Cuivre (1 or = 100 ag = 10k cu). Helpers : `money_to_cuivre`, `cuivre_to_purse`, `credit_character`/`debit_character` (mutent, **sans save**). **Éligibilité marchand** : `lieu_buys(lieu, item)` = item sous-cat ∈ recettes du lieu OU produit du lieu (rachat ≤ pmin ≤ achat). `params_vente_lieu` = source unique prix. **Vente des objets du groupe** (2026-07-14, étendue aux montures 2026-07-19) : `_marchand_vendables(character, lieu, relation, porteurs_tiers)` agrège le sac du principal PUIS de chaque porteur — compagnon **OU monture** (une bête de somme est là pour rapporter du butin lourd : ce qu'elle porte doit être vendable sans transfert préalable) — chaque entrée porte `compagnon_id` (None=principal) + `porteur_nom` + `porteur_icon`. Les 3 appelants (`marchand_quotes`, `sell_item`, `buy_item`) passent **`recrutement.porteurs_effectifs(character, get_doc)`** = SOURCE UNIQUE de « qui porte pour moi » (`groupe_effectif` + `montures_effectives`, compagnons d'abord — le client range les montures en fin de liste), dont `routers/recrutement._porteurs_du_groupe` n'est plus qu'un relais. ⚠️ `routers/recrutement` importe `routers/user` → le helper doit vivre dans **`utils/recrutement.py`**, pas dans un router. `sell_item`/`marchander` passent par le chokepoint `_acteur` (`compagnon_id` optionnel — il résout désormais les **deux** types de porteur ; preuve d'appartenance = statut + lien vers CE personnage, `embauche`/`embauche_par` ou `acquise`/`acquise_par`) → l'objet quitte le sac du **porteur** mais **l'argent va TOUJOURS au principal** (`credit_character(principal)` ; il rétribue déjà ses compagnons via la part de butin, et une monture n'a pas de bourse). Sauvegarde bi-doc `_save_acteur` (porteur autoritatif d'abord → pas de double vente). Relation/marchandage = ceux du principal. UI (`play_town`) : badge `.sell-owner` `👤 <prénom>` / `🐴 <nom>` selon `porteur_icon` (posé serveur via `montures.est_monture`, le client ne devine pas), `compagnon_id` fileté par `_cgArg` dans sell/marchander. **Coût revient** : doc `valeur` explicite → autoritaire ; sinon récursif via recettes (transformations = bien plus cher). Feuilles (matières brutes) = `poids × MULT_RARETE × PRIX_DERIVE_BASE`. **Prix marché** = `prix_courant × facteur_stock`, re-clampé `[pmin,pmax]`. Stock target = `stock_cible_pour(lieu, item)` (item > sous-cat > catégorie > défaut). **Tick atelier** (vente/achat/visite) : (0) appro feuilles, (1) production (multi-matières, tirage pondéré ; **pool unifié** : consomme `stock_matieres` PUIS le **surplus du rayon** au-dessus du `stock_cible` → un intermédiaire produit est à la fois **en vente ET réutilisable comme matière** pour la recette de niveau supérieur, chaînage intra-tick, sans duplication ; `resolve_fn` injectable), (2) **écoulement PNJ objet par objet** (chaque produit en rayon tire indépendamment sa demande `VENTE_PNJ_PROBA` → certains s'écoulent, d'autres non ; surplus au-dessus de la cible seulement). **Dépeçage** : poids instance × poids/REF (plus lourd = plus de matière) ; **tendons/boyaux/foie… gated par tags d'espèce** (`DEPECAGE_TAGS`) — la recette boucherie ne fixe que la *quantité*, pas l'appartenance (tendons = tags `monture`/`draconique`/`geant`). Une entrée de `DEPECAGE_TAGS` peut être une **sous-cat** OU une **clé item-ref `item:*`** ciblant un item précis (ex. `demon` → `item:Sang_demon_seche` : la matière traverse jusqu'au rayon telle quelle, `matiere_item_id` la laisse intacte) → une créature démoniaque « loote » ainsi son sang en plus de ses matières charnues. Les matières de dépeçage qu'aucune recette du lieu ne consomme sont **déplacées en rayon (`stock_vente`) et vendues au joueur** — c'est le canal par lequel le joueur obtient sang/griffes/os/etc.

### Marchandage & relations
`prix_courant` = prix négocié OU base pondéré relation (0-100 neutre 50, `frac = 0.5 + (val−50)·coeff/100`). **Prix appliqué** = `prix_marche` (courant × facteur_stock, re-clampé). Négociation persistée **FRACTION** de fourchette (pas montant fixe) → poids différent = prix différent. **Relation** = doc CouchDB `type:"relation"` (char×lieu, 0-100, `prix_negocies`, blocage epoch). `POST /api/marchander` : jet bonus=`(rel−50)·coeff` ; **réussite** = prix persisté ; **crit ok** = +1 rel ; **crit fail** = −1 rel + blocage. `CRIT_*` = génériques. UI : badge relation, bouton 🤝, toast affiche `prix_marche` exact (pas `prix_negocie` sans facteur_stock).

### UI — listes scrollables de la fiche perso (2026-07-14)
Une liste longue de la fiche ne pousse plus le panneau : elle **scrolle chez elle**. Deux briques, à réutiliser telles quelles pour toute nouvelle liste :
- **`.sh-rel-scroll`** = le conteneur scrollable (`overflow-y:auto`, scrollbar fine, `position:relative`). Une classe de **hauteur** l'accompagne, par liste : `.sh-quest-list-active` (40vh), `.sh-quest-list-ended` (35vh) — les relations gardent la leur.
- **`<div class="sh-list-shadow-overlay"></div>`** = **l'ombre générique de bas de liste**, `position:sticky; bottom:0` : c'est le **dernier enfant** du conteneur scrollable (et non un `::after` sur le conteneur, qui ne suivait pas le défilement). ⚠️ Elle est **dans le flux** : un rendu client qui construit la liste doit l'émettre lui-même, après les lignes.

Conséquence pour les listes à **double rendu** (Jinja au chargement + JS au resync) : le markup wrapper + overlay doit exister **des deux côtés**, sinon l'ombre disparaît au premier resync. C'est le cas de l'onglet 📜 (`renderFicheQuetes` réémet `.sh-quest-list-active` / `.sh-quest-list-ended` + l'overlay).

Usages : `#grp-compagnons-list` (👥 Groupe), `#rec-groupe-list` + `#rec-recrues-list` (board). Registre `_cardViewports` (clé = **la carte**, pas le porteur : un compagnon peut avoir une carte dans deux panneaux), purgé par `clearCharacterCards`.

### Quêtes — guilde + moteur
**Lieu guilde** : `categorie:"guilde_aventurier"` + `lieu_parent` (ex. `auxerre`). Extérieur intermédiaire (`guilde_aventurier_exterieur`) inerte. Tableau généré = espèces rencontres → quêtes `kill` ; `ressources` lieu + carcasses → quêtes `collect`. Docs `quete:*` = générées (`source:"genere"`, max `QUETE_BOARD_TAILLE`) + authorées (`source:"authoree"`, affichées côté). **État joueur** : `quetes_actives[]` (snapshot + `progress`), `quetes_terminees[]`. **Hooks progression** : `kill` en combat (exactly-once), `visite` en déplacement, `collect` en dépôt guilde. **Dépôt progressif** : `POST /api/quetes/deposer` retire pièces portées, incrémente `progress` (plusieurs voyages OK). **Pas d'arbre entier** : `cibles_collect` découpe si `> QUETE_COLLECT_POIDS_MAX`. UI : bouton 📜, panneau AJAX, onglet fiche resync client `renderFicheQuetes`. CSS factorisé `.panel-frame`/`.board-panel`. Mode Ressources éditeur → `PUT /api/lieu/{id}/ressources`. World-vars : `QUETE_BOARD_TAILLE`, `QTE_MIN/MAX`, `XP_FACTEUR`, `CUIVRE_PAR_XP`.

**Le tableau tourne — d'autres aventuriers prennent les contrats** : une offre **générée** porte un **`expire_at`** posé à la génération (`_duree_de_vie` = `QUETE_BOARD_DUREE_SECONDES` **jittée** de ±`QUETE_BOARD_DUREE_JITTER` → 30 min-1 h 30 par défaut ; les 6 offres naissant au même instant, sans jitter le tableau basculerait **d'un bloc**). Péremption **PARESSEUSE** (aucun tick de fond) : `remplir_tableau` appelle `purger_offres_perimees` avant de compléter → le doc périmé est **SUPPRIMÉ** (`delete_doc` ; personne ne le référence, celui qui accepte en garde un snapshot) et la place est aussitôt repeuplée. `offre_perimee` ne vise **que** `source:"genere"` + `statut:"offerte"` : une quête **authorée** ne périme jamais, une **acceptée** a déjà quitté le tableau. Repli sans `expire_at` (offres d'avant la feature) : `genere_at` + durée nominale → les tableaux existants tournent sans migration. Tests `tests/test_quetes_board.py` (12 tests).

**Renoncer fâche toute la MAISON du donneur** (`quetes.sanctionner_renoncement`, chokepoint unique) : **abandonner** une quête (n'importe quel type — `POST /api/quetes/abandonner`) **ou** laisser filer le délai d'une course (`transport.traiter_expirations`) coûte `QUETE_TRANSPORT_RELATION_DELTA` de relation chez le donneur **et chez tous les lieux de sa maison**. La **réussite**, elle, ne récompense que le donneur (`+1`, asymétrie assumée : la maison punit collectivement, elle ne remercie pas collectivement). **Maison = donnée, pas code** : `lieux_solidaires` = tous les lieux de **même `sous_categorie`** (champ sur les `lieu:*`, même orthographe que sur les items) **ET de même `lieu_parent`** que le donneur. La **conjonction** est indispensable : le `lieu_parent` des lieux d'une guilde est la **CITÉ** (`lieu:auxerre`), donc seul il ramènerait les 36 lieux d'Auxerre ; et la seule `sous_categorie` ramènerait les guildes des autres cités. Un donneur **sans `sous_categorie`** (un magasin) n'est solidaire que de lui-même → comportement historique inchangé. La **façade** `guilde_aventurier_exterieur` ne porte pas le champ : elle est hors maison (lui poser le champ suffirait à l'y faire entrer, sans toucher au code — toute faction future s'y branche pareil). `find_docs` indisponible → repli gracieux sur le donneur seul. Tests `tests/test_quetes_relation.py` (15 tests).

### Quêtes de transport — magasins + tenancier générique
Un magasin X confie une **cargaison** à livrer à un magasin Y qui **rachète** ces biens (`lieu_buys`), dans un **délai réel** (`QUETE_TRANSPORT_DUREE_SECONDES`, 1 h). Réussite → **+1 relation avec X** (donneur seul) + XP + prime ; **échec (délai dépassé) ou abandon** → **−1 relation avec X *et avec tous les lieux de sa maison*** (cf. `sanctionner_renoncement`, §Quêtes — guilde), la **cargaison reste dans le sac** (revendable — tentation assumée). Logique pure `utils/transport.py` (DB injectée), tests `tests/test_transport.py` (40 tests, suite 355 verte).

**Magasin** = `marche.besoins_categorie(categorie)` non vide (28 catégories à recettes ; l'auberge n'en est pas une). **Tenancier générique** : aucun doc `lieu:*` marchand ne porte de champ `pnj` → `transport.entree_marchand(lieu)` dérive `pnj:marchand_<categorie>` (proba 1.0), injecté via `marchand_fn` dans `pnj.entrees_pnj` / `tirer_pnj_present` / `entree_pnj_active` (le champ `pnj` explicite prime toujours). Docs générés par `dev/gen_marchands.py` → `jsons/marchands_a_importer.json` (28 marchands, même arbre de dialogue, ambiance par métier). ⚠️ **Portraits = placeholders** (rotation sur les fichiers existants de `templates/resources/pnj/`) — à remplacer par un portrait par métier.

**Offre** : tirée à l'**ENTRÉE** du magasin (`QUETE_TRANSPORT_PROBA` = 10 %), persistée en champ transitoire `character["transport_offert"] = {lieu, quete|None}` — **même sémantique que `pnj_present`** (un refresh ne re-tire pas ; ressortir/rentrer re-tire). Pas d'offre si une course est déjà active (pas d'empilement). **Confiance requise** : `confiance_suffisante` — un marchand ne confie **aucune** cargaison si sa relation est **< `QUETE_TRANSPORT_RELATION_MIN`** (50, la valeur neutre ; 0 = garde-fou désactivé) **OU** si son **marchandage est bloqué** (`marche.marchandage_bloque`, crit d'échec récent : brouille datée, indépendante de la cote — elle ferme la porte même à relation ≥ seuil et même garde-fou désactivé, sa durée a sa propre world-var `MARCHANDAGE_BLOCAGE_SECONDES`). Relation absente en base = neutre → le tout-venant reçoit des offres. Ne vaut que pour les courses **générées** : une course **écrite** est confiée par son scénario, quelle que soit la cote du joueur.

**Deux sources d'offre** (aiguillage dans `poser_transport_offert(…, pnj_doc=…)`, qui reçoit le PNJ déjà arrêté pour cette entrée — `main.py` le résout AVANT le tirage) : (1) **générée** — le donneur est un magasin, tout est tiré au sort ; (2) **AUTHORÉE** — le **PNJ présent** porte une course écrite dans **`services.transport.offre`** = `{id, destination, cargaison:[{item, quantite, poids?}], duree?, proba?, unique?, titre?, description?, recompenses?}` (miroir de `services.soin`/`services.don`). Alors **n'importe quel PNJ peut confier une course** : le donneur n'a **pas** à être un magasin (`est_magasin` n'est plus le seul test) et rien n'est tiré au sort — les bornes `POIDS_MAX`/`NB_MAX` **ne s'appliquent pas** (seul le contrôle de charge à l'acceptation reste). L'`id` doit être **stable** : c'est le gate de `unique:true` (`deja_reussie` — un **échec ne bloque pas**, le donneur repropose). Le **destinataire**, lui, reste un magasin (c'est son tenancier qui a les nœuds `livre`/`incomplet`).

**Course à `retour`** (`spec.retour:true`) : le destinataire prend la marchandise mais **ne paie pas** (`livrer_en_attente_de_retour` → nœud `livre_retour`, repli `livre` ; `livree_at` posé, **`expire_at` retiré** — le délai portait sur la livraison, pas sur le retour) ; la quête **reste active** jusqu'à ce que le joueur revienne **rendre compte au donneur** (op `rapporter` → `rapporter_transport` → nœud `rapporte`), qui solde alors tout : XP, prime **et `recompenses.items`** (entrés au sac par `quetes.appliquer_recompenses`). `transport_a_livrer` exclut les courses déjà livrées ; `retour_attendu(character, lieu)` les retrouve chez le donneur. Flags de dialogue : `transport_a_rapporter`, `transport_en_cours` (confiée par CE lieu, **non encore livrée** → relance) et `transport_accompli` (course `unique` déjà réussie). `porte_effective` (BFS) donne la direction cardinale depuis un lieu **imbriqué** qui n'ouvre pas lui-même sur la grille de la ville (comptoir → réception → façade). **Items de récompense** (`recompenses.items` d'une offre écrite) = des références d'**instances**, fabriquées par `items_recompense(spec_items, giver_doc)` : une entrée peut demander `"lieu_parent": "auto"` (sentinelle `transport.LIEU_PARENT_AUTO`) → l'exemplaire remis porte le **`lieu_parent` du donneur** (repli : son `_id`). L'objet en base reste **générique** (`item:carte_aventurier`, un seul doc pour toutes les guildes) et c'est l'instance qui dit d'où elle vient → label `Carte d'aventurier (Auxerre)` (cf. §Références d'items) ; la même mission copiée dans une autre guilde délivre la carte de **sa** cité. Contenu de la **première mission de la guilde** — **2 fichiers** : `jsons/premiere_mission_a_importer.json` (lieu `le_bastion_de_l_yonne_comptoir`, sa connexion à la réception, `item:viande_sanglier_gobelin`, `item:carte_aventurier` **générique**) et `jsons/pnj-*.json` (**tous les docs PNJ**, Borin + les 28 tenanciers — seule source à jour) ; `jsons/carte_aventurier_correctif.json` = le correctif qui a rendu la carte générique (nouveau doc, `_deleted` de l'ancien `item:carte_aventurier_auxerre`, Borin corrigé). Borin (réceptionniste) confie 2 caisses de viande au fumoir `lieu:fumee_de_l_yonne`, puis **remet au retour** la carte d'aventurier de la cité dont relève son comptoir (`lieu:auxerre`). Le nœud **`livre_retour`** est porté par **les 28 marchands** (gabarit `dev/gen_marchands.py`) : n'importe quel magasin peut donc être la destination d'une course à retour, sans promettre une prime qu'il ne verse pas (le repli sur `livre` le ferait). **Cargaison** : items que X fournit (`stock_vente` + `produits_categorie`) ET que Y rachète ; empilage instance par instance, **arrêt AVANT de franchir** `QUETE_TRANSPORT_POIDS_MAX` (100 kg) **ou** `QUETE_TRANSPORT_NB_MAX` (10 objets) — la borne la plus contraignante gagne ; objet unique trop lourd → **pas d'offre**.

**Géographie** : aucune coordonnée monde sur les `lieu:*`, mais chaque doc `connection` boutique↔ville porte la **porte dans la grille de la ville** → `focalisation.charger_graphe` l'expose déjà, `portes_du_parent` + `direction_cardinale` (8 octants, **y croît vers le BAS** → nord = dy<0) + `repere_proche` (magasin le plus proche de la destination) donnent « au nord-est d'ici, tout près du Fumoir ». Hors ville : nom de la ville + distance BFS. XP = `QUETE_TRANSPORT_XP` (même ville) ou `× (1 + distance)`.

**Dialogue** (`services.transport.noeuds`) : `pnj.condition_ok` traite toute clé inconnue comme un **flag booléen** du contexte → conditions `transport_offert` / `transport_a_livrer` posées par le router ; `_substituer` remplace en plus toute clé de `contexte["placeholders"]` (`{destination}`, `{direction}`, `{colis}`, `{poids}`, `{delai}`, `{xp}`, `{prime}`, `{expediteur}`). Actions : `accepter`, `livrer`, `rapporter` — proposer/informer sont de simples `next` conditionnés. ⚠️ Les enseignes portent leur article (« Le Saloir ») : **jamais de préposition devant `{destination}`** (« à Le Saloir » serait fautif), toujours un deux-points. **Refus parlé** : flag `transport_mefiance` (`transport.mefiance` — magasin, aucune course écrite/en cours, `confiance_suffisante` fausse : relation sous le seuil **ou** marchandage bloqué) → choix `course_refus` des 28 marchands vers le nœud `transport_mefiance` (« je ne confie pas mes colis à n'importe qui »), sinon la sanction serait un simple **silence**, indiscernable d'un tirage négatif. Un **seul** nœud pour les deux causes → son texte parle d'**entente**, jamais d'une cause précise (il doit rester vrai dans les deux cas). **Placeholders hors course** : ils sont posés dès qu'une offre est **écrite** (`spec`), même sans course vivante — `_contexte` reconstruit alors l'aperçu par `generer_transport_authore` (déterministe) ; sans ce repli, un nœud qui ne s'affiche **qu'après** la réussite (le « vétéran » de Borin) rendrait `{destinataire}` en clair.

**⚠️ RÈGLE — un dialogue ne cite JAMAIS un nom de PNJ en dur.** Les docs `pnj:marchand_*` sont **génériques** (un par catégorie, partagé par toutes les boutiques) et **chaque lieu peut rebaptiser son tenancier** via `nom` dans son entrée `pnj` (Lucinda Mortecroix à La Flèche d'Argent, **Hermine Valcorbe** au fumoir…) : un nom écrit dans un texte mentirait. Placeholders de nom, posés par le router : **`{pnj}`** = celui à qui l'on parle (source unique **`pnj.nom_effectif(entree, doc)`** — l'entrée du lieu prime, repli doc ; c'est aussi ce que rend `pnj_payload`), **`{destinataire}`** / **`{donneur}`** = les PNJ des deux bouts d'une course (**`pnj.nom_pnj_du_lieu(lieu, get_doc, marchand_fn)`** — nomme le PNJ d'un lieu **sans y être**, 1re entrée = priorité). `{destination}`/`{expediteur}` restent les **enseignes** (lieux), `{pnj}`/`{destinataire}`/`{donneur}` sont des **personnes**. ⚠️ **Aucun pronom genré** autour d'eux : le tenancier peut être une femme.

**Mise en rayon à la livraison** : `deposer_en_rayon(dest, cargaison, get_doc_fn, rand_fn)` — chaque objet livré a `QUETE_TRANSPORT_STOCK_PROBA` (50 %) de rejoindre le `stock_vente` du destinataire, **à condition qu'il vende ce produit** (`marche.lieu_produit` : ses recettes le produisent). Un item qu'il n'achète que comme **matière première** ne monte jamais sur l'étal. Le doc `lieu` est **annexe** → persisté par `reussir_transport`, comme le doc `relation`.

### Quêtes de « chasse » (élite à profil élevé) + rang de guilde

**Grade résolu À LA GÉNÉRATION** (`resoudre_profil_chasse`), jamais au combat : `position_de_chasse` = centre d'un placement d'une zone qui contient l'espèce (présent seulement si le lieu a une `dimensions`/grille) ; zones actives à ce point → `resolve_profil_weights` (extrait de `routers/combat.py` vers **`utils/zones.py`**, partagé) → profils **filtrés `restriction_tags ⊆ tags espèce`** (un loup sans tag `magie` ne devient jamais un profil `magie`) → niveau `max`/`max−1`, égalité `random.choice`. `profil_id` stocké dans l'objectif ; le combat l'applique tel quel.

Focalisation 🎯 = mode `kill` (biais d'espèce ; `"chasse"` ∈ `OBJECTIFS_FOCALISABLES`).

### Montures de transport (étables)
Premier **moyen de transport de charge** : jusqu'ici seule la Force (`charge_max_of` = `F*5`) et les 2 compagnons augmentaient l'emport d'une expédition. Une **étable** (`categorie:"etable"` OU tag `"montures"` — `montures.lieu_vend_montures`, miroir de `recrutement.lieu_recrute`) vend des montures ; l'entrée `pnj` du lieu porte la liste `montures:[espece:*]` (`especes_offertes` = union des entrées, dédupliquée). Logique pure `utils/montures.py` (DB injectée, pattern `utils/recrutement.py`), router `routers/montures.py`, tests `tests/test_montures.py` (30) + `tests/test_combat_montures.py` (13).

**Doc `monture:*` = MIROIR du character** (comme `aventurier:*`) : `caracteristiques_current` tirées uniformément dans `espece.base_attributes`, `currentPV/PM` = max dérivés, `inventaire`/`slots`/`effets_actifs`/`combats_recompenses` → `compute_derived_stats`, `carried_weight`, `build_joueur_snapshot`, `_apply_world_turn_regen` marchent dessus **sans code neuf**. Type DISTINCT d'`aventurier` → jamais ramassé par les boucles de recrutement (board, affinités, part de butin). Appartenance = `statut:"acquise"` + `acquise_par` (pas de `user_id`), via `montures_effectives` — miroir exact de `groupe_effectif`. ⚠️ Les **`tags` d'espèce ne sont PAS recopiés** sur le doc ni sur le snapshot : plusieurs montures portent `proie`/`predateur`, qui pilotent l'IA de prédation en furtivité (elle ne scanne que `monstres`, mais un acteur rangé dans `joueurs` qui les porterait créerait une interaction qu'aucun code n'attend).

**Charge = chokepoint `montures.charge_max_porteur(porteur)`** : aiguille entre `charge_max_of` (F×5) et `charge_max_of × espece.proprietes.charge_mult` pour une monture. Multiplicateur **relu à chaud** sur le doc espèce (jamais dénormalisé). `recrutement.peut_porter` (l'admission) délègue à lui (la capacité) → **un seul endroit décide de chacun**. Étendus au même chokepoint : `_charge_view` et `_inventory_payload` (sinon le client griserait ses flèches sur 100 kg au lieu de 400). `proprietes` porte aussi `prix_cuivre` (achat via `debit_character`) — les 19 espèces `monture` sont peuplées par `jsons/montures_proprietes_a_importer.json`.

**Groupe** : `character["montures"]` est un index SÉPARÉ de `character["groupe"]`, plafond propre `MONTURE_GROUPE_MAX` (une monture n'est pas une épée : les mettre en concurrence forcerait un arbitrage absurde). Endpoints `GET /api/montures/etable`, `POST …/acheter`, `POST …/relacher` (autorisé partout, **409 si la bête est chargée** — la relâcher pleine ferait disparaître le butin en silence). **Aucun endpoint d'inventaire** : `GET /api/groupe` et `POST /api/groupe/transferer` sont porteur-agnostiques (garde factorisée `_porteur_du_groupe` = compagnons PUIS montures). Régén PV/PM au tour monde via le chokepoint existant `_apply_world_turn_groupe`.

**Combat — ciblable mais pas jouable.** `create_combat_doc(..., montures=[...])` les snapshote dans `joueurs` (donc placées, rendues, **ciblables**) avec `jouable:False`, `est_monture:True`, `deplacement:0` et `charge_max` multiplié, puis **exclut leurs ids d'`ordre_initiative`** → jamais de tour. ⚠️ **DEUX prédicats distincts, à ne surtout pas confondre** : `_joueurs_vivants` (ciblage, inchangé, inclut les montures) vs **`_combattants_vivants`** (défaite, filtré sur `jouable`). Si la défaite comptait la monture, un groupe entièrement à terre avec une bête indemne ne perdrait **jamais** et, plus personne ne pouvant jouer, le combat resterait bloqué indéfiniment (régression couverte par `test_monture_debout_n_empeche_pas_la_defaite`). À 0 PV : `morte:True` sur le snapshot, puis **`_finalize_monture`** (passe dédiée, hors de la boucle des compagnons — sinon XP + affinité + relevé à 1 PV) fait quitter le troupeau et verse la **cargaison dans `butin_disponible`** sous des ids `cargo_<snap_id>_<n>`, récupérables par l'overlay de fin (`/collect` les indexe par `monstre_id` sans exiger de monstre). Placé **APRÈS** l'affectation `butin_disponible = dispo`, qui l'écraserait. `butin_disponible` n'existant qu'en **victoire**, une défaite emporte la cargaison (prix assumé du risque). Une monture morte est exclue des bénéficiaires de `/collect`.

**UI** : bouton sidebar `🐴 Montures` (`est_etable`, `main.py`) → `#montures-panel` (clone du panneau de recrutement ; offres en lignes `.mnt-offre`, pas en cartes — on achète une espèce, pas un individu). Panneau `👥 Groupe` : les montures ferment la marche sous un sous-titre `🐴 Montures` (`_rendreCartesMontures`, cartes **non éditables** — une monture n'est pas dans `groupe_effectif`, `_acteur` refuserait son cadrage — et **non cliquables**, elle n'a pas de fiche) ; le sélecteur de sac les range dans un `<optgroup>`. Le portrait vient de l'image d'**espèce** servie par `/monsters` : `setSujet` accepte une `base` (défaut `/characters`), le serveur la fournit (`image_base`, `portraits_joueurs[].base`) — le client ne devine pas. ### Contrôle des dialogues PNJ (linter)
Un arbre de dialogue est de la **donnée** : ni typée, ni exécutée à l'import. Un `next` vers un nœud inexistant, un nœud de service mal nommé (`services.transport.noeuds.accepte` pointant à côté) ou une condition mal orthographiée ne se voient **qu'en jouant la branche** — et un choix conditionné qui ne s'affiche jamais est indiscernable d'un tirage malheureux. D'où un contrôle préalable.

**`utils/lint_dialogues.py`** = logique PURE (aucune DB, aucun I/O), **source unique** consommée par deux appelants — même précédent que `utils/xlsx.py` : le CLI **`dev/lint_dialogues.py`** (`python dev/lint_dialogues.py [fichiers]` ; sans argument, tous les `jsons/*.json` **sauf les `telluris-dump-*` qui sont des archives d'états passés** ; sort en code 1 s'il reste une erreur) et le bouton **🔍 Vérifier les dialogues** de la carte d'import de `/admin` (`POST /admin/lint-dialogues`, admin-only, **lecture seule**, mêmes deux formats de corps que `/admin/import-bulk` → il porte sur ce que contient déjà la zone de saisie). `analyser(payload)` → `{analyses, ignores, erreurs, avertissements, trouvailles[]}` ; un doc sans bloc `dialogue` est *ignoré*, pas fautif (la plupart des docs du jeu n'en ont pas).

**Erreurs** : `noeud_depart` absent/introuvable · `next` vers un nœud inexistant · nœud **inatteignable** (ni `next` ni service n'y mène) · nœud sans aucun choix · deux choix de même `id` dans un nœud (`choix_valide` renvoie le premier, le second est mort) · nœud de service déclaré mais absent · placeholder hors liste · **condition inconnue du moteur** (un flag absent vaut False → le choix ne s'affiche JAMAIS) · **action `livrer`/`rapporter` non conditionnée** par son flag (`transport_a_livrer`…) — le PNJ proposerait « je vous apporte une livraison » à qui n'a rien à remettre · **nom de PNJ en dur dans un doc `pnj:marchand_*`** (générique : chaque lieu renomme son tenancier via `nom` dans son entrée `pnj` — cf. la règle ⚠️ du § Transport).

**Avertissements** : choix sans `next` ni `action` (ferme le dialogue comme `fin` — idiome valide, juste implicite) · nœud de service manquant. ⚠️ Le transport a **deux rôles** et presque aucun PNJ ne tient les deux : **donneur** (`accepte`/`trop_charge`, + `rapporte` si `offre.retour`) — n'importe quel PNJ peut l'être ; **destinataire** (`livre`/`incomplet`) — seul un magasin, donc en pratique un `pnj:marchand_*`. Les exiger de tous ferait crier au défaut sur un donneur correct (le réceptionniste de guilde ne reçoit jamais de colis).

⚠️ Les listes de référence (`PLACEHOLDERS_CONNUS`, `FLAGS_CONNUS`, `NOEUDS_REQUIS`, `ACTIONS_A_CONDITIONNER`) décrivent ce que `routers/pnj.py` consomme **réellement** : les tenir à jour en même temps qu'un nouveau service ou un nouveau flag, sinon le linter signalera du code correct. Le `_rev` d'un doc n'est **pas** signalé : `admin_import_bulk` réattache toujours le `_rev` courant, un `_rev` périmé est sans effet.

### Découpe du bois
Chaîne joueur (distincte recettes PNJ). Item coupable = tag `a_couper` + sous_cat ∈ `BOIS_A_COUPER` (ordre petit→grand). Tailles même essence = tag `essence_<xxx>`. `cible_coupe` = tier immédiatement plus petit de l'essence. **Couper = 1 niveau** : `repartir_poids` découpe instance en pièces ≈ max tier (poids conservé exact, borné `COUPE_MAX_PIECES`). Pièces → sol. Terminal = `branche` (pas `a_couper`). **Outil requis, PARTAGÉ par le groupe** (2026-07-14) : `bois.a_outil_coupe(character, get_doc, compagnons=None)` scanne sac + équipement du personnage ET de chaque compagnon fourni → il suffit qu'**un** membre de l'expédition porte le tag `outil_coupe_bois` (compétences/équipements mis en commun en exploration). `/couper` et `/recolter` passent `groupe_effectif(...)` ; l'acteur reste le principal (pièces au sol du lieu). `compagnons=None` = comportement historique (tests purs `tests/test_bois.py`). Endpoints : `POST /api/couper` (409 sans outil, 422 non coupable), `/api/recolter` étendu (si ressource coupable → abat niveau vers sol). UI : boutons 🪓 Couper / 🪓 Abattre. World-vars : `BOIS_A_COUPER`, `OUTIL_COUPE_BOIS_TAG`, `COUPE_MAX_PIECES`.

### Buffs de caractéristiques — chokepoint unique + « Profil modifié »
**3 sources**, toutes au même format `{buffs:{caract:Δ}, regen_pv, regen_pm, esquive}`, repliées par le chokepoint **`utils/consommables._sources_de_buffs`** (donc par `caracts_avec_buffs`/`regen_bonus`/`esquive_bonus`, donc effectives PARTOUT — fiche, exploration, snapshot de combat — sans autre code) :
- **`effets_actifs[]`** — TEMPORAIRE (consommables, sorts, compétences actives), décrémenté au tour monde.
- **`equipment_bonus`** — champ item **`bonus` = `{caract: Δ}`** (147 items en base) **+ `bonus_malus_depl`**, qui est lui aussi un **delta sur V** (données : `-1`/`-2` pour les armures lourdes) et se cumule avec `bonus.V` ; les deux sont agrégés dans `EquipmentBonus.buffs` par `recompute_equipment_bonus`. ⚠️ `compute_derived_stats` **ne soustrait plus** `malus_depl` du déplacement (`deplacement = max(1, V)`) : il est déjà dans V — le soustraire à nouveau le compterait deux fois. Le malus pèse donc désormais aussi sur l'**initiative** et le **cd**. Le champ `EquipmentBonus.malus_depl` reste exposé à titre informatif (fiche objet, marché). ⚠️ **Dénormalisé sur le perso par `utils/characters.sync_equipment_bonus(character)`, à appeler AVANT tout `caracts_avec_buffs`** (source unique : tous les appelants passent par lui, plus jamais `recompute_equipment_bonus` directement → le champ n'est jamais périmé). Distinct des `bonus_pa`/`bonus_cc`/… qui, eux, buffent les **dérivées** (pas de double comptage).
- **`competences_bonus`** — passives permanentes (`recompute_competences_bonus`).

**V est buffable comme les autres** (à son échelle 1-10 : une dague `bonus:{Ag:3,V:1}` donne +1 case de déplacement). Buffs toujours **EXCLUS** de `charge_max_of`, des plafonds/coûts d'XP et de `restriction_satisfaite` (anti-exploit) — ces trois-là lisent `caracteristiques_current` **brut**.

**UI** : les deux agrégats portent un `buffs_sources:[{nom, icon, buffs}]` (détail nommé), ce qui permet à la fonction pure **`consommables.caracts_detail(character)`** → `{code: {base, total, delta, sources:[{origine, nom, icon, delta}]}}` de ventiler par origine sans DB. Rendue dans la **2e grille « ✨ Profil modifié »** de l'onglet ⚔ (`play_town_telluris.html`, `#sh-mod-grid`, rendu 100 % client `_renderCaractsMod` → une seule valeur = la courante, delta coloré, tooltip nommant chaque source). Resync par `caracts_detail` dans les réponses de spend_xp / equip / unequip / consommer / lancer_sort / utiliser_competence / apprendre_competence / déplacement (helper `_caracts_payload`).

### Consommables & effets temporaires
Item `categorie:"consommable"` + champ `effets:{pv, pm, regen_pv, regen_pm, buffs:{caract:Δ}, duree}`. `pv`/`pm` = instantanés ; `buffs`/`regen_*` = actifs sur `character["effets_actifs"][]` (empilable), tick monde = décrément. Buffs applicables à **toutes** les caracts, V comprise (à son échelle 1-10). Portée buffs : appliqués dérivées partout ; EXCLU de charge_max/XP/restriction = anti-exploit. **Régén PM naturelle** = `ceil(Vol/20)`/déplacement. **Exploration** : `POST /api/consommer` (index+item_id) → payload+vitals+effets+consomme. UI : bouton 🍽️, chips ✨ effets_actifs. **Combat** : action `"consommer"` (1 action, part instantanée **ET** part à durée — cf. § Effets à durée en combat). Ordre écriture : combat → character → finalize. Tests purs.

### Effets à durée EN COMBAT (2026-07-19)
Un effet à durée est un effet à durée, **qu'il soit lancé en exploration ou en combat** — un sort « Armure de givre » (`{esquive, buffs, duree}`) était jusqu'ici refusé par `sort_utilisable_combat`, donc toute la famille buffs/régén/esquive était morte là où elle a le plus de sens.

**Le snapshot devient RECALCULABLE.** `build_joueur_snapshot` figeait les dérivées : `caracts_avec_buffs` une fois, puis `cc`/`pa`/`pv_max`/`degats_cc` dérivés — sans conserver ni les caracts de base ni l'`equipment_bonus`, donc rien n'était recalculable. Il porte désormais **`caracts_base`** (caracts + buffs **permanents** seuls : équipement + passives, via le nouveau paramètre `origines` du chokepoint `consommables._sources_de_buffs`), **`equipment_bonus`**, **`voc_niveau`**, **`esquive_base`** et une liste **`effets_actifs` VIVANTE** (copie de celle du personnage). **`_refresh_snapshot_stats(acteur)`** = chokepoint unique qui recompose `cc/cd/ag/ch/pa/pm_def/toucher_magique/degats_*/initiative/pv_max/pm_max/deplacement_base/esquive` depuis `caracts_base` + Σ buffs des effets vivants, puis re-clampe PV/PM. ⚠️ **Trois valeurs restent FIGÉES à l'entrée** : **`actions_max`** (`_refresh_actions` recalcule `actions_restantes = actions_max − Σ compteurs` → un `actions_max` mouvant offrirait des actions gratuites au cast puis un budget négatif à l'expiration), **`charge_max`** (même exclusion anti-exploit qu'en exploration) et **`attaque_profils`** (les recalculer relirait les docs d'items en base à chaque tour, pour un gain d'une case de portée de jet). Snapshot sans `caracts_base` (combat déjà en base) → la fonction sort sans rien toucher : **aucune migration**.

**Durée = TOURS DU PORTEUR.** `_tick_effets_combat(combat_doc, acteur)` est appelé depuis **`_reset_turn_budget`** (seul hook « début de tour d'acteur ») : (1) régén `regen_pv`/`regen_pm` clampée, (2) décrément + purge, (3) `_refresh_snapshot_stats`. Chaque entrée porte un **`pose_tour`** → le tick du tour de pose l'épargne, sinon un effet lancé pendant son propre tour perdrait un point avant d'avoir servi. Expiration et régén sont **journalisées** (`kind:"sys"`), sans quoi la perte d'un bonus serait invisible.

**Les effets ENTRANTS tickent aussi** : une potion bue juste avant d'entrer ne dure plus tout le combat (exploit fermé). **Les effets restants REMONTENT** : `_finalize_membre` recopie les entrées à `restants > 0` dans `doc["effets_actifs"]` (sans `pose_tour`), pour le principal **et** les compagnons — écrasement, jamais `extend` (ces entrées SONT celles du personnage, copiées à l'entrée).

**Empilement** : `_empiler_effet_combat(acteur, source, effets, tour)` produit **exactement la même forme d'entrée** que `consommables.empiler_effet` — c'est ce qui rend la remontée triviale. Appelé dans les 3 branches « sur soi » de `resolve_action` (sort, compétence, consommer), toujours sur l'**acteur actif** (compagnon compris). Le test « y a-t-il quelque chose à empiler ? » est la SOURCE UNIQUE **`sorts.part_durative(effets)`** (`duree > 0` ET un bénéfice prolongé), partagée par `sort_utilisable_combat`, `competence_utilisable_combat`, `consommables.effet_instantane` et les deux `empiler_effet_*` — un critère qui divergerait entre « lançable » et « empilable » produirait un sort accepté puis sans effet. UI : chips ✨ `#joueur-effets` dans le panneau perso de `combat_telluris.html` (`renderEffetsActifs`, markup repris de `_renderEffetsActifs` de play_town). Tests purs `tests/test_combat_effets.py` (16).

### Compétences de vocation — passives + actives (miroir des sorts)
Doc `competence:*` : `{nom, icon, description, vocation, niveau, mode:"passive"|"active", cout_pm (≥0, contrairement aux sorts), cible:"soi"|"ennemi", jet:"cc"|"cd"|"magique", portee, effets}`. `effets` = **même schéma que les sorts** (`{degats, pv, pm, regen_pv, regen_pm, buffs, duree}`). Pas de composants. Logique pure `utils/competences.py` (DB injectée).

**Choix à la création** : toute vocation **HORS `SORT_VOCATIONS_DEPART`** (complément exact, `vocation_choisit_competence` = source unique ; le client re-dérive de `SORT_VOCS`) choisit **1 compétence niveau 0** — on choisit un sort **OU** une compétence, jamais les deux. Sélecteur `#voc-comp-picker` dans l'étape 3 du wizard (`user_home_telluris.html`), miroir de `#voc-sort-picker` ; champ `characterinfo.competence_initiale`, validé serveur dans `add_character` (même dégradé gracieux : contenu non importé → création sans compétence). Champs perso : `competences_connues[]` + `competences_bonus`.

**PASSIVE = permanente.** Ses buffs/régén sont **dénormalisés** dans `character["competences_bonus"]` (pattern d'`equipment_bonus`), recalculé par `recompute_competences_bonus` à la création et à chaque apprentissage, puis replié par **`utils/consommables._sources_de_buffs`** → `caracts_avec_buffs` / `regen_bonus`. C'est le **chokepoint unique des buffs** : une passive est donc effective partout (fiche, exploration, snapshot de combat) sans autre code, et hérite des exclusions anti-exploit (pas de charge_max, ni plafonds/coûts d'XP, ni restriction d'équipement).

**ACTIVE = 1 action** (+ `cout_pm`). **Combat** : action `"competence"` (`ActionRequest.competence_id`, compteur `competences` — ⚠️ compté dans `_refresh_actions` ET remis à 0 par `_reset_turn_budget`, sinon action gratuite). Part **instantanée** (degats/pv/pm) **et** part à **durée** s'appliquent (cf. § Effets à durée en combat). Cible ennemi → jet **porté par la donnée** : `cc`/`cd` = frappe martiale (seuil `_hit_threshold` vs Ag, **PA soustraits**) ; `magique` = `_magic_hit_threshold` vs `pm_def` (**sans PA**). Portée > 1 → règles ranged (engagé interdit + ligne de vue). **Exploration** : `POST /api/utiliser_competence` (cible soi seulement, buffs → `effets_actifs`). ⚠️ **Règle de contenu** : toute active rendant PV/PM **doit coûter des PM** — il n'y a pas de cooldown, une active gratuite serait spammable à l'infini hors combat.

**Apprentissage** : `POST /api/apprendre_competence` — coût `(niveau+1)×COMPETENCE_COUT_COEFF` points, `vocations_niveaux[voc] ≥ niveau`, compétence de sa vocation, **pas de grimoire**. Onglet ⚡ de `play_town_telluris.html` (rendu client `_renderCompetences`/`_renderCompetencesApprenables`, à côté des sorts). À terme : arbre de compétences (cette étape en pose déjà le coût et l'endpoint). Contenu : `jsons/competences_niveau0.json` (20 vocations × 1 passive + 1 active) + `jsons/new_comp0.json` (furtivités + esquive). Tests purs `tests/test_competences.py` (49 tests, suite 252 verts).

**Furtivité & esquive (2026-07-11)** — deux clés d'effets **partagées sorts/compétences/consommables** (dans `_bonus_dict`/`fusionner_effets`, `utils/sorts.py`) : `esquive` (entier, malus au seuil de toucher **physique** des attaques subies — cc/cd via `_hit_threshold`, **jamais la magie** qui passe par `pm_def`) et `furtivite` (>0 = état furtif, valeur = bonus à l'Ag dans la difficulté de détection). Se déplacer/consommer/ramasser ne brise rien. **Activation** : compétence active ou sort `cible:"soi"` avec `effets.furtivite > 0` (`_activer_furtivite` : re-furtive ET remet `detecte=False` partout) ; furtivité passive posée à l'entrée du combat (`create_combat_doc(furtivite_initiale=…)`, calculée dans `routers/combat.py` contre les tags du terrain).
